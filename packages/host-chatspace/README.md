# `@cg/host-chatspace` — адаптер ChatSpace (R09, части A и B)

Адаптер к OnlyMonster ChatSpace: всё, что расширение знает о странице и делает с ней
(architecture.md §6.1–§6.10). Своих запросов к OnlyMonster нет: только память страницы,
DOM, мост ChatSpace для вставки и — для отправки из превью (X8) — один вызов очереди
самого ChatSpace.

## Что внутри

**`main/` — мир страницы (MAIN), без зависимостей.**

- `installMainBridge(win, { runtime? })` — «загрузчик» на
  `document_start`: запоминает нативные функции, рукопожатие, проверка конверта, повтор
  записи по id не исполняется, события не чаще 50 в секунду на тип. Сам отвечает на `probe`,
  остальное отдаёт «рантайму». 1,7 КиБ gzip, установка 0,02 мс.
- `guard.ts` — правило мира страницы (решение X22): каждый колбэк, который зовёт ChatSpace
  или браузер, обёрнут в `guard(site, fn)`. Сбой нашего кода не уходит в страницу и не
  пишется в консоль; он считается по месту, а событие `fault` уходит при счёте 1, 2, 4, 8….
  Изолированная сторона пишет его в лог вкладки (`main-fault`, `CG-UNKNOWN`). Загрузчик
  одалживает рантайму `guard`, `fault` и уже защищённые `setTimer`, `frame`, `emit`.
  Скрипт тапа отдаёт свои сбои в тот же счёт через `LiveHost.fault`. Чужие функции, через
  которые идёт вызов (прежний `fetch`, конструктор `WebSocket`), под guard не попадают:
  их ошибки доходят до ChatSpace как есть. Проверки: гейт `main-world-guard`, тесты
  `main/faults.dom.test.ts` и `main/faults-tap.test.ts`, e2e `sentry-gate`.
- `createMainRuntime` — «рантайм»: поиск `#app.__vue_app__` (100 мс до 15 с, потом 2 с до 60 с,
  потом `CG-HOST-NOT-READY`), маршрут и эпохи, сторы через `pinia.use()` (свои не создаёт),
  кэш Colada и `$onAction`, аккаунты, окно и хвост чата (только подтверждённые сообщения с
  числовым id), фан, список чатов, активный composer, ревизия черновика из транзакций
  Tiptap, CAS-вставка в одном синхронном шаге, сверка после микрозадачи и кадра, фокус,
  `router.push` по действию человека и отложенная вставка «Открыть и вставить».
- `installWsTap(win)` — «тап» и всё, что без него не имеет смысла (часть B, ниже): отдельный
  скрипт, который фон регистрирует только при флаге `wsTap`. Без него запросы `checkpoint`
  и `previewSend*` отвечают `disabled` до исполнения, а `flags` — «оба выключены».

**`isolated/` — изолированный мир.**

- `startChatSpaceHost({ win, redeem, drafts, … })` — одна точка запуска для корня композиции:
  менеджер монтирования и тема синхронно, мост и `HostPort` — после рукопожатия.
- `createChatSpaceHostPort` — `HostPort` из контрактов: состояние из снимка и событий MAIN,
  синхронные чтения из кэша (ответ — и `null` «у ChatSpace этого пока нет», и неудача —
  стоит до события MAIN, геттер второй раз не спрашивает; серия одинаковых неудач — одна
  запись `read-failed` с `requestKind`, затем на 10-й, 100-й… раз, конец — `read-recovered`),
  вставка и переход тратят `actionToken` до моста и не передают
  его в MAIN, `BRIDGE_WRITE_FAILURES` для записи, которая могла выполниться, сверка
  применённой вставки по ключу черновика цели. `configure()`, `checkpoint()`,
  `previewSend` — часть B, ниже.
- `connectMainBridge` — клиент моста: синхронно только рукопожатие, схемы грузятся лениво
  (`validate.ts`) при первом кадре; три ступени проверки, счётчики отброшенного, тайм-ауты.
  `null`, который схема ответа допускает, — ответ, а не `invalid-answer`.
  Откуда взять модуль схем, говорит тот, кто запускает хост (`validation`): тесты и обвязка
  e2e передают `loadValidation` (модуль рядом, через `import()`), а расширение — загрузчик
  своего ленивого чанка `lazy/bridge-validation.js`. Контент-скрипт собирается одним
  классическим файлом, динамический импорт в нём встраивается целиком, и схемы моста вместе
  с долей zod (около 6 КиБ gzip) заняли бы место в раннем бандле, у которого 30 КиБ на всё.
- `createMountManager` — док первым ребёнком корня рамки активного composer, строка
  «только копировать» у заблокированного фана, фиксированный оверлей без рамки, слои
  оверлеев 900/950/960, `data-dismissible-open`, реестр закрытых корней для хоткеев.
  `onRenewed` — док 100 мс стоит над другими узлами, чем те, над которыми встал для
  composer, названного MAIN, а MAIN молчит (ChatSpace перерисовал composer без события
  хранилищ; о смене чата MAIN сообщает сам, и она сюда не попадает): `HostPort` просит
  MAIN посмотреть ещё раз (`snapshot`), ответ не применяет и ждёт события `composer` —
  идентичность называет новый composer до клика «Вставить».
- `createKeyboardProbe(doc, registry)` — сторона страницы для раннего диспетчера хоткеев
  (R17, `@cg/core/application/hotkeys`): где фокус (наше поле, наш UI, поле ввода ChatSpace,
  другое поле, страница), открыто ли окно самого ChatSpace, и передача клавиши нашему
  элементу копией, которая не выходит из закрытого корня. У копии `isTrusted` — `false`, но
  для правила «запись — только по доверенному действию» (§14) она считается нажатием
  человека; на ней стоит метка `DELIVERED_KEY_MARK` (`Symbol.for('cg.key.delivered')`),
  по которой её узнаёт наш интерфейс (`ui-contract.md`, решение 12). `routeOfLocation` — маршрут по
  адресу, пока MAIN ещё не ответил. `createKeyPendingMark(host)` ставит на хост дока
  `data-pending` и `aria-busy`, пока нажатая клавиша ждёт ленивую часть или первое
  состояние чата (HK-024, HK-025): до загрузки интерфейса это единственный знак ожидания.
- `buildContractReport`, `createThemeReader`, `readStoredDraft`, `host-contract.ts` (все
  строки ChatSpace в одном месте; копия MAIN закреплена тестом).
- `receiptModules` / `matchReceiptProfile` / `loadedScriptUrls` — отпечаток модулей пути
  отправки; `aiGeneratedMark` — правило ChatSpace для отметки «сгенерировано ИИ».

## Часть B: X8, квитанция, отправка человеком, тап (§6.6–§6.8)

**Где лежит код.** Тап, порт отправки, наблюдатель квитанции и наблюдение отправки
человеком едут в **скрипте тапа** (`chatspace-ws`, `installWsTap`), а не в бандле
`document_start`: без тапа ничего из этого не работает (нет свежести — нет отправки), а в
10 КиБ основного бандла оно не помещается. В основном бандле — только связка: рантайм один
раз берёт ручку тапа под `Symbol.for('wsTap')` (`handle.attach(liveHost)`),
отдаёт ему чтения страницы и канал событий (`main/live.ts`: `LiveHost`) и получает «живой
порт» (`LivePort`). Порядок двух скриптов на `document_start` не важен (e2e гоняет оба):
пока ручки нет, рантайм ищет её при каждой следующей надобности, так что запрос,
пришедший раньше скрипта тапа, тап не отключает. Ручку может забрать страница (MAIN не
доверенный) — тогда живого порта нет, как без тапа.

- `main/ws-tap.ts` — `Proxy` над конструктором `WebSocket`; слушатели `message`/`close` только
  на сокете ChatSpace (путь `/api/chat-space/ws`); фильтр подстрокой до `JSON.parse`; счётчики
  сообщений фана по (аккаунт, фан) без повторов по id; эпохи сокета и подписки. Аккаунт
  «вооружён», когда сокет открыт и прошёл `authenticated`, аккаунт есть в
  `subscribedAccountIds` ChatSpace и на этом сокете был его кадр. Покрытие `unknown`, старые
  контрольные точки несравнимы:
  - новый сокет, потеря подписки, сон (тик раз в 30 с и проверка при каждом чтении),
    переполнение (5000 чатов);
  - кадр, который называет `account_new_message`, но не читается как сообщение: не JSON,
    длиннее 262 144 символов, другой конверт (`event` не тот, сообщение вложено глубже),
    непонятные id или направление. Числовой id больше 2^53 — тоже не id: два разных
    сообщения не должны читаться как одно;
  - второй сокет на том же пути, пока прежний ещё открыт. ChatSpace закрывает сокет раньше,
    чем создаёт следующий; чужой сокет страницы с таким же концом адреса может только
    удержать отправку, но не скрыть сообщение фана.

  Кадры аккаунтов, которые порт не обслуживает (другая платформа на том же сокете —
  ChatSpace подписывает и `telegram_v2`), не считаются, не пересылаются и «нечитаемыми» не
  бывают: рантайм отдаёт тапу только подписанные аккаунты OnlyFans. Наружу уходят только
  метаданные (`incoming`), текст сообщения из файла не выходит; сообщение фана — один раз,
  исходящее — как пришло (повторную доставку исходящего тап не отличает). Время слушателя
  на кадр ограничено длиной кадра и меряется: `handle.frameTime()` → `[кадров, всего мс,
  худший кадр мс]` (§6.8 п. 3; бюджет §11 — 0,1 мс в среднем — проверен тестом).
  «Выключись» (`flags {wsTap:false}`) возвращает конструктор, если он ещё наш.
- `main/send-port.ts` — единственный файл с именем действия очереди. `preflight` — условия
  §6.7.4 п. 5–14 из памяти страницы без побочных эффектов; `commit` — те же проверки и
  ровно один `enqueue` в том же синхронном шаге, аргументы §6.7.1 (HTML как у `setText`).
  Всё, что сломалось до вызова очереди (наше чтение бросило исключение, наблюдатель не
  встал), — `held` с `CG-SEND-HOST`, и preflight говорит то же: опека снимается, потому что
  очередь точно не вызвана. После вызова: `null` — `notEnqueued`; запись с ключами §6.2
  (`id, accountId, chatId, platform, status, error, createdAt, payload`), чей запрос взял
  наблюдателя, — `nativeEnqueued`; исключение очереди, запись без id или без одного из
  ключей — `uncertain`, и X8 в этом документе выключен (`CG-SEND-HOST`). Повтор
  `attemptId` получает первый ответ: ответ, после которого очередь могла быть вызвана,
  помнится до конца документа, из ответов `held` — последние 256. Защёлка флага
  `previewSend` закрыта, пока изолированная сторона не скажет «включено».
- `main/receipt.ts` — наблюдатель `fetch` только на время синхронного вызова очереди: нашего
  и человеческого из composer'а с нашей вставкой при свободной очереди аккаунта. Все вызовы
  проходят дальше без изменений; копии запроса и ответа — только для точного `POST
  …/accounts/{acc}/chats/{chat}/messages`: читаются целиком, а разбираются, только если не
  длиннее 65 536 символов; заголовки и куки не читаются; прежнее значение возвращается,
  только если глобал ещё наш. Итог: 2xx с id → `nativeAccepted`; квитанция + исходящее эхо
  с тем же id → `sentObserved`; доказанный отказ (перехваченный 4xx кроме 401 и запись
  `FAILED`, или Message Guard) → `rejected`; 5xx, сеть, тайм-аут 30 с, исчезнувшая запись,
  второй или чужой POST, не тот текст → `uncertain`. Повторной отправки нет нигде.
  - **Взял ли клиент наблюдателя.** Клиент ChatSpace берёт `fetch` для запроса через
    `fetch.bind(globalThis)` (§6.7.6 п. 2; модуль закреплён профилем квитанции).
    Наблюдатель слышит этот `bind` на самом себе. Запрос очереди наблюдателя не взял —
    путь отправки не тот, что в профиле: `uncertain` сразу и X8 выключен
    (`CG-SEND-RECEIPT`). Запись исчезла до того, как её запрос дошёл до `fetch` (нативный
    Cancel, сброс, выход, пока клиент ждёт токен), — только `uncertain`, X8 работает дальше.
  - **`fetch`, который нельзя подменить** (нет функции, свойство не принимает
    присваивание): X8 отказывает до очереди с `CG-SEND-RECEIPT` — это видно уже на preflight;
    отправка человека идёт как обычно, её факт — без квитанции.
  - **Раннее эхо** хранится при самой отправке (исходящие id её чата с момента вызова
    очереди, до 64): исходящие сообщения других чатов вытеснить его не могут.
  - **Отправка человеком (TL-004).** Факт `humanSend` с `platformMessageId` — это уже
    связанная пара: квитанция именно этой отправки **и** исходящее эхо с тем же id,
    аккаунтом и фаном. Он уходит, когда пара собрана (эхо раньше ответа или позже — всё
    равно), и событие `incoming` этого эха всегда идёт перед ним. Без квитанции (занятая
    очередь, не наша вставка, отказ, 5xx, цепочка 401) факт уходит сразу, с
    `platformMessageId: null` — атрибуция неизвестна, `sent` нет. Потребителю свой буфер
    эха не нужен: `op.reportSent` можно звать по факту с id.
- `isolated/host-port.ts`:
  - `host.configure({ wsTap, previewSend, markAiGenerated, receiptProfiles })` — флаги и
    профили из bootstrap; зовётся при старте и при каждой их смене.
  - `host.checkpoint(chat)` — контрольная точка свежести или `null`.
  - `host.previewSend` — `PreviewSendPort` (`preflight`, `commit`, `onState`), не `null`
    только когда способность `previewSend` включена: флаг, якоря пути отправки, скрипт тапа
    в странице и не выключен, совпавший профиль квитанции. «Вооружён» ли аккаунт цели, в
    способность не входит (иначе она мигала бы при каждом переподключении) — на это
    отвечает `preflight`: `CG-SEND-FRESHNESS`. `actionToken`, `binding` и `ticket` в MAIN не
    уходят. Повтор `commit` получает первый ответ; забываются только ответы `held`
    (помнятся последние 64).
  - Профиль перестал совпадать посреди отправки (§6.2: страница догрузила другую версию
    модуля пути отправки): слушатели попыток, которые уже в очереди, получают `uncertain`
    (`CG-SEND-UNCERTAIN`), следующие X8 закрыты способностью. Из того, что MAIN скажет об
    этих попытках потом, проходит только `sentObserved` — поздняя связанная пара (§6.7.7).
    Выключение флага несовпадением не считается: начатая отправка прослеживается до конца.
  - события `HostEvents`: `incoming`, `coverage`, `humanSend`; способности `incoming`,
    `sendObserve`, `receipt`, `previewSend`; якоря `wsFrames`, `receiptProfile`.
- Профиль квитанции: адаптер читает из DOM и `performance` адреса загруженных модулей
  (ничего не скачивает), берёт хеши из имён `/assets/<роль>-<хеш>.js` для ролей
  `notificationEntry, composables, onlyfans, accounts, inbox` и сверяет с
  `limits.previewSendReceiptProfiles` (все роли и `adapterVersion`). Нет совпадения — X8
  выключен с `CG-SEND-RECEIPT`, остальное работает. Роли — по раскладке ChatSpace
  0.195.0 (адаптер 0.3.0): модуля `messages` там нет, его содержимое во втором модуле
  `onlyfans` (`docs/architecture.md` §6.2).

**Подключить (интегратору).** В `chatspace-main.content.ts` —
`installMainBridge(window, { runtime: createMainRuntime })`; `chatspace-ws.ts` уже зовёт
`installWsTap()`. После bootstrap и при его обновлении —
`host.configure({ wsTap: flags.wsTap, previewSend: flags.previewSend, markAiGenerated:
flags.previewSendMarkAiGenerated, receiptProfiles: limits.previewSendReceiptProfiles })`.
Отметку ИИ для запроса считает вызывающий: `aiGeneratedMark(отправляемыйТекст,
исходнаяЧасть)`; при выключенном флаге адаптер сам шлёт `false`. Порт верит булеву
значению запроса (контракт несёт только его), поэтому правило ChatSpace против исходной
AI-части (X8-02) обязан применить контроллер отправки (R10/R15) — сейчас это делает
только e2e-обвязка.

**Известные ограничения части B.**
- **«Права загружены» (условие 5).** Из памяти страницы видно только, что
  `["userPermissions"]` — массив. ChatSpace 0.172.0 кладёт туда `[]` и после неудачной
  загрузки прав, и после `clearPermissions`; настоящий признак `isLoaded` — замыкание, его
  не прочитать. Роль с запретом отправки, у которой права не загрузились, условия 5 и 8
  пройдёт. Нативная кнопка Send ведёт себя так же, так что это не шире нативного; отказ
  сервера придёт как `rejected`.
- **Якорь `composerTranslator` до первого чата.** ChatSpace создаёт этот стор только с полем
  ввода чата и держит до перезагрузки. Пока в документе не было ни одного поля ввода, MAIN
  отдаёт его в `ContractWire.notYet` (в отчёте — `notYet`), после первого — в `missing`, если
  стора так и нет (`main/page.ts`, `main/runtime.ts`). X8 при этом выключен с
  `CG-SEND-HOST` (причина — `composerTranslator`); поломка другого якоря отправки называется
  раньше (`isolated/contract.ts`). Чат, где ChatSpace поле ввода не показывает (роль без
  права отправки, фан не принимает сообщений, Mimic), стор не создаёт.
- **Якорь `pendingMessages`.** Действия и оба состояния очереди проверяются якорем; ключи
  записи — на записи, которую очередь вернула нашей отправке (у отправки человека
  проверяется только `id`). Записи, уже лежащие в очереди, якорь не разбирает.
- **Время на кадр** меряется в MAIN и читается с ручки тапа; в `client_health` оно не
  уходит: для этого нужен запрос моста (изменение контракта) — вопрос к R18.
- **Несовпадение профиля посреди отправки** замечает изолированная сторона и только для
  отправок, про которые MAIN уже ответил «в очереди» (помнит до 64 таких). Если профиль
  разошёлся в те миллисекунды, пока MAIN ещё не ответил на команду, эта отправка
  неопределённой не объявляется: она ещё может оказаться `held`.
- **Действие очереди перестало быть синхронным** (не профиль 0.172.0): эхо, пришедшее
  раньше, чем очередь отдала запись отправки человека, с ней не свяжется — факта с id не
  будет.

**`tools/host-contract-check`** — только локально, не в CI и не в `pnpm check`:
`node tools/host-contract-check/index.ts [--dir <копия>] [--against <другая копия>] [--json]`.
Сверяет все строки `host-contract.ts` с локальной копией бандлов ChatSpace: `--dir` — папка
`pretty/` нужной версии; без него — новейшая версия под `$CG_CHATSPACE_BUNDLES` (корень
копий, architecture.md §6.2). Печатает «есть / нет» с `файл:строка`, сборку и отпечаток
профиля квитанции. С `--against` — какие модули пути отправки и их импорты сменились и
где изменился код вокруг якорей внутри этих модулей (сравнение по «форме»: имена, которые
минификатор меняет от сборки к сборке, не считаются) — чтобы новый хеш большого общего
модуля можно было отличить от настоящей правки пути отправки. Код ChatSpace не печатает.
Профиль из вывода — кандидат: в hub он попадает только после чтения пути отправки этой
сборки (§6.2). Ключ кэша `onlyfansBuyingPowers` с 0.200.0 ChatSpace собирает по платформе
(фабрика с шаблоном `` `${платформа}BuyingPowers` ``, её зовут для каждой платформы), в
странице ключ тот же. Инструмент засчитывает литерал или шаблон целиком: суффикс ключа от
единственного параметра фабрики, шаблон в теле этой фабрики, и тот же модуль зовёт её с
`onlyfans`. Остальные ключи — только литералом, как раньше.

## Как подключить (интегратору)

```ts
// MAIN, document_start:
installMainBridge(window, { runtime: createMainRuntime });
// изолированный мир, document_start (после removeStaleHosts):
const started = startChatSpaceHost({
  win: window,
  validation: () => /* import() ленивого чанка со схемами моста; в тестах — loadValidation */,
  redeem: (r) => /* token.redeem через порт вкладки, surface по месту вызова */,
  drafts: { getItem: (key) => window.localStorage.getItem(key) },
  navInsertTimeoutMs: bootstrap.limits.navInsertTimeoutSec * 1000,
});
// UI: started.mounts.dock.root, started.mounts.overlay('modal').root …
// хоткеи: started.mounts.registry; HostPort: await started.host
```

**Как поставляется рантайм MAIN (решение X11, `docs/decisions.md`).** Один бандл на
`document_start`: `installMainBridge(window, { runtime: createMainRuntime })`. Загрузчик —
1,7 КиБ gzip. С рантаймом и guard — 9,87 КиБ при бюджете MAIN 10 КиБ (`pnpm size` меряет
собранный `content-scripts/chatspace-main.js`); скрипт тапа — 4,97 из 5 КиБ. Оба бандла
собираются без обёртки входа WXT (`apps/extension/build/main-world-entry.ts`, решение
X22): она пробрасывала сбой старта в страницу и стоила ~170 Б gzip на бандл. Запаса почти
нет: новая логика MAIN — только вместо старой. Работа на `document_start` по-прежнему
≤ 1 мс: рантайм ничего не делает до `DOMContentLoaded`.

Второй MAIN-скрипт (`attachMainRuntime(createMainRuntime)` после
`exposeMainRuntimeHook(handle)`) отклонён: крючок лежит под `Symbol.for` на `window`,
страница может забрать его первой — тогда хост навсегда «не готов». Сам API остаётся в
пакете отдельной функцией, расширение его не вызывает, и в его бандл он не попадает.

Время выполнения бандла на `document_start` e2e пишет в `.cache/e2e/host-adapter.json`
(`mainEvalMs`, обвязка без расширения) и проверяет на собранном расширении
(`integration-m1.e2e.ts`: метки начала и конца бандла тестовой сборки, медиана ≤ 1 мс),
кроме `installMs` загрузчика.

**Отмена «Открыть и вставить»** (§6.5): `navigate(intent, { signal })` — R10 прерывает
сигнал при выходе, смене персоны или привязки и при закрытии превью; MAIN не пишет
отложенную вставку, если ещё не записал (контракты 1.1.0, запрос моста `cancelInsert`).

**Чей это composer.** Composer привязан к чату, для которого ChatSpace его нарисовал:
активная вкладка чата аккаунта маршрута (`chatTabEntries`). Пока вкладка и маршрут
называют разные чаты (переключение в пути: ChatSpace показывает composer новой вкладки
раньше, чем асинхронные проверки роутера пускают маршрут), composer'а нет — ни чтений,
ни записи. Вкладки не читаются (новая сборка) — только копирование (`composerBridge`
`missing`).
