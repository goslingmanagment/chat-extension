# `@cg/host-chatspace` — адаптер ChatSpace (R09, части A и B)

Адаптер к OnlyMonster ChatSpace: всё, что расширение знает о странице и делает с ней
(architecture.md §6.1–§6.10). Своих запросов к OnlyMonster нет: только память страницы,
DOM, мост ChatSpace для вставки и — для отправки из превью (X8) — один вызов очереди
самого ChatSpace.

## Что внутри

**`main/` — мир страницы (MAIN), без зависимостей.**

- `installMainBridge(win, { runtime?, exposeRuntimeHook? })` — «загрузчик» на
  `document_start`: запоминает нативные функции, рукопожатие, проверка конверта, повтор
  записи по id не исполняется, события не чаще 50 в секунду на тип. Сам отвечает на `probe`,
  остальное отдаёт «рантайму». 1,7 КиБ gzip, установка 0,02 мс.
- `createMainRuntime` — «рантайм»: поиск `#app.__vue_app__` (100 мс до 15 с, потом 2 с до 60 с,
  потом `CG-HOST-NOT-READY`), маршрут и эпохи, сторы через `pinia.use()` (свои не создаёт),
  кэш Colada и `$onAction`, аккаунты, окно и хвост чата (только подтверждённые сообщения с
  числовым id), фан, список чатов, активный composer, ревизия черновика из транзакций
  Tiptap, CAS-вставка в одном синхронном шаге, сверка после микрозадачи и кадра, фокус,
  `router.push` по действию человека и отложенная вставка «Открыть и вставить».
- `installWsTap(win)` — «тап» и всё, что без него не имеет смысла (часть B, ниже): отдельный
  скрипт, который фон регистрирует только при флаге `wsTap`. Без него запросы `checkpoint`
  и `previewSend*` отвечают `disabled` до исполнения, а `flags` — «оба выключены».

**`isolated/` — изолированный мир.**

- `startChatSpaceHost({ win, redeem, drafts, … })` — одна точка запуска для корня композиции:
  менеджер монтирования и тема синхронно, мост и `HostPort` — после рукопожатия.
- `createChatSpaceHostPort` — `HostPort` из контрактов: состояние из снимка и событий MAIN,
  синхронные чтения из кэша, вставка и переход тратят `actionToken` до моста и не передают
  его в MAIN, `BRIDGE_WRITE_FAILURES` для записи, которая могла выполниться, сверка
  применённой вставки по ключу черновика цели. `configure()`, `checkpoint()`,
  `previewSend` — часть B, ниже.
- `connectMainBridge` — клиент моста: синхронно только рукопожатие, схемы грузятся лениво
  (`validate.ts`) при первом кадре; три ступени проверки, счётчики отброшенного, тайм-ауты.
- `createMountManager` — док первым ребёнком корня рамки активного composer, строка
  «только копировать» у заблокированного фана, фиксированный оверлей без рамки, слои
  оверлеев 900/950/960, `data-dismissible-open`, реестр закрытых корней для хоткеев.
- `buildContractReport`, `createThemeReader`, `readStoredDraft`, `host-contract.ts` (все
  строки ChatSpace в одном месте; копия MAIN закреплена тестом).
- `receiptModules` / `matchReceiptProfile` / `loadedScriptUrls` — отпечаток модулей пути
  отправки; `aiGeneratedMark` — правило ChatSpace для отметки «сгенерировано ИИ».

## Часть B: X8, квитанция, отправка человеком, тап (§6.6–§6.8)

**Где лежит код.** Тап, порт отправки, наблюдатель квитанции и наблюдение отправки
человеком едут в **скрипте тапа** (`chatspace-ws`, `installWsTap`), а не в бандле
`document_start`: без тапа ничего из этого не работает (нет свежести — нет отправки), а в
10 КиБ основного бандла оно не помещается. В основном бандле — только связка: рантайм один
раз берёт ручку тапа под `Symbol.for('chatgoose.wsTap')` (`handle.attach(liveHost)`),
отдаёт ему чтения страницы и канал событий (`main/live.ts`: `LiveHost`) и получает «живой
порт» (`LivePort`). Порядок двух скриптов на `document_start` не важен (e2e гоняет оба).
Ручку может забрать страница (MAIN не доверенный) — тогда живого порта нет, как без тапа.

- `main/ws-tap.ts` — `Proxy` над конструктором `WebSocket`; слушатели `message`/`close` только
  на сокете ChatSpace (путь `/api/chat-space/ws`); фильтр подстрокой до `JSON.parse`; счётчики
  сообщений фана по (аккаунт, фан) без повторов по id; эпохи сокета и подписки. Аккаунт
  «вооружён», когда сокет открыт и прошёл `authenticated`, аккаунт есть в
  `subscribedAccountIds` ChatSpace и на этом сокете был его кадр. Новый сокет, потеря
  подписки, сон (тик раз в 30 с и проверка при каждом чтении), переполнение (5000 чатов),
  нечитаемый кадр сообщения — покрытие `unknown`, старые контрольные точки несравнимы.
  Наружу уходят только метаданные (`incoming`), текст сообщения из файла не выходит.
  «Выключись» (`flags {wsTap:false}`) возвращает конструктор, если он ещё наш.
- `main/send-port.ts` — единственный файл с именем действия очереди. `preflight` — условия
  §6.7.4 п. 5–14 из памяти страницы без побочных эффектов; `commit` — те же проверки и
  ровно один `enqueue` в том же синхронном шаге, аргументы §6.7.1 (HTML как у `setText`).
  Повтор `attemptId` получает первый ответ; защёлка флага `previewSend` закрыта, пока
  изолированная сторона не скажет «включено».
- `main/receipt.ts` — наблюдатель `fetch` только на время синхронного вызова очереди: нашего
  и человеческого из composer'а с нашей вставкой при свободной очереди аккаунта. Все вызовы
  проходят дальше без изменений; копии запроса и ответа — только для точного `POST
  …/accounts/{acc}/chats/{chat}/messages`, ограниченные по размеру; заголовки и куки не
  читаются; прежнее значение возвращается, только если глобал ещё наш. Итог: 2xx с id →
  `nativeAccepted`; квитанция + исходящее эхо с тем же id → `sentObserved`; доказанный
  отказ (перехваченный 4xx кроме 401 и запись `FAILED`, или Message Guard) → `rejected`;
  5xx, сеть, тайм-аут 30 с, исчезнувшая запись, второй или чужой POST, не тот текст →
  `uncertain`. Повторной отправки нет нигде.
- `isolated/host-port.ts`:
  - `host.configure({ wsTap, previewSend, markAiGenerated, receiptProfiles })` — флаги и
    профили из bootstrap; зовётся при старте и при каждой их смене.
  - `host.checkpoint(chat)` — контрольная точка свежести или `null`.
  - `host.previewSend` — `PreviewSendPort` (`preflight`, `commit`, `onState`), не `null`
    только когда способность `previewSend` включена: флаг, якоря пути отправки, вооружённый
    тап и совпавший профиль квитанции. `actionToken`, `binding` и `ticket` в MAIN не уходят.
  - события `HostEvents`: `incoming`, `coverage`, `humanSend`; способности `incoming`,
    `sendObserve`, `receipt`, `previewSend`; якоря `wsFrames`, `receiptProfile`.
- Профиль квитанции: адаптер читает из DOM и `performance` адреса загруженных модулей
  (ничего не скачивает), берёт хеши из имён `/assets/<роль>-<хеш>.js` для ролей
  `notificationEntry, composables, messages, accounts, inbox` и сверяет с
  `limits.previewSendReceiptProfiles` (все роли и `adapterVersion`). Нет совпадения — X8
  выключен с `CG-SEND-RECEIPT`, остальное работает.

**Подключить (интегратору).** В `chatspace-main.content.ts` —
`installMainBridge(window, { runtime: createMainRuntime })`; `chatspace-ws.ts` уже зовёт
`installWsTap()`. После bootstrap и при его обновлении —
`host.configure({ wsTap: flags.wsTap, previewSend: flags.previewSend, markAiGenerated:
flags.previewSendMarkAiGenerated, receiptProfiles: limits.previewSendReceiptProfiles })`.
Отметку ИИ для запроса считает вызывающий: `aiGeneratedMark(отправляемыйТекст,
исходнаяЧасть)`; при выключенном флаге адаптер сам шлёт `false`.

**`tools/host-contract-check`** — только локально, не в CI и не в `pnpm check`:
`node tools/host-contract-check/index.ts [--dir <копия>] [--against <другая копия>] [--json]`.
Сверяет все строки `host-contract.ts` с локальной копией бандлов ChatSpace: `--dir` — папка
`pretty/` нужной версии; без него — новейшая версия под `$CG_CHATSPACE_BUNDLES` (корень
копий, architecture.md §6.2). Печатает «есть / нет» с `файл:строка`, сборку и отпечаток
профиля квитанции. С `--against` — какие модули пути отправки и их импорты сменились и
где изменился код вокруг якорей внутри этих модулей (сравнение по «форме»: имена, которые
минификатор меняет от сборки к сборке, не считаются) — чтобы новый хеш большого общего
модуля можно было отличить от настоящей правки пути отправки. Код ChatSpace не печатает.
Профиль из вывода — кандидат: в hub он попадает только после чтения пути отправки этой
сборки (§6.2).

## Как подключить (интегратору)

```ts
// MAIN, document_start:
installMainBridge(window, { runtime: createMainRuntime });
// изолированный мир, document_start (после removeStaleHosts):
const started = startChatSpaceHost({
  win: window,
  redeem: (r) => /* token.redeem через порт вкладки, surface по месту вызова */,
  drafts: { getItem: (key) => window.localStorage.getItem(key) },
  navInsertTimeoutMs: bootstrap.limits.navInsertTimeoutSec * 1000,
});
// UI: started.mounts.dock.root, started.mounts.overlay('modal').root …
// хоткеи: started.mounts.registry; HostPort: await started.host
```

**Как поставлять рантайм MAIN.** Загрузчик — 1,7 КиБ gzip; с рантаймом — 9,8 КиБ при
бюджете 10 КиБ на бандл `document_start`; скрипт тапа — 4,8 из 5 КиБ. Запаса почти нет:
новая логика MAIN — только вместо старой. Точка входа расширения сейчас ставит только
загрузчик (корни композиции — интегратора), поэтому до подключения хост в собранном
расширении отвечает `not-ready` на всё, кроме `probe`. `pnpm size` меряет оба варианта
поставки (10 и 9 КиБ):
1. **Один бандл на `document_start`**
   (`installMainBridge(window, { runtime: createMainRuntime })`) и новый бюджет MAIN
   ~10 КиБ. Рекомендуем: работа на `document_start` по-прежнему ≤ 1 мс (рантайм ничего
   не делает до `DOMContentLoaded`), а перехватывать нечего.
2. **Второй MAIN-скрипт** на `document_end` с `attachMainRuntime(createMainRuntime)` и
   своей строкой бюджета (загрузчик — с `exposeRuntimeHook: true`). Риск: крючок лежит
   под `Symbol.for` на `window`, страница может забрать его первой — тогда хост навсегда
   «не готов» (ничего не пишется, но и не работает).

Время разбора и выполнения бандла на `document_start` e2e пишет в
`.cache/e2e/host-adapter.json` (`mainEvalMs`), кроме `installMs` загрузчика.

**Отмена «Открыть и вставить»** (§6.5): `navigate(intent, { signal })` — R10 прерывает
сигнал при выходе, смене персоны или привязки и при закрытии превью; MAIN не пишет
отложенную вставку, если ещё не записал (контракты 1.1.0, запрос моста `cancelInsert`).

**Чей это composer.** Composer привязан к чату, для которого ChatSpace его нарисовал:
активная вкладка чата аккаунта маршрута (`chatTabEntries`). Пока вкладка и маршрут
называют разные чаты (переключение в пути: ChatSpace показывает composer новой вкладки
раньше, чем асинхронные проверки роутера пускают маршрут), composer'а нет — ни чтений,
ни записи. Вкладки не читаются (новая сборка) — только копирование (`composerBridge`
`missing`).

## Проверка

- Юнит-тесты (`*.test.ts`, `*.dom.test.ts`): 281. У каждой защиты есть тест, который падает
  без неё. Часть A — 16 мутаций руками (повтор записи по id, чужая эпоха документа, обе
  половины CAS, эпоха маршрута в MAIN, эпоха входа и `platformAccountId` в идентичности,
  `seq` и эпоха кадра, предпроверки изолированной стороны, цель отложенной вставки, два
  стабильных наблюдения, вкладка чата, происхождение после добавления, сигналы событий;
  покрытие строк части A — 96,6 %). Часть B — 109 мутаций скриптом, по одной: каждое
  условие §6.7.4, защёлка флага, память попыток, срок билета, каждое правило исхода
  квитанции (401, второй и чужой POST, не тот текст, отказ без `FAILED`, слишком длинный
  ответ), возврат `fetch` и конструктора «только если ещё наш», каждое слагаемое
  «вооружённости» тапа, эпохи, сон, переполнение, границы памяти, наши ошибки внутри
  действий ChatSpace, профиль квитанции, срезание токена и билета перед MAIN. Защиты,
  для которых такого теста написать нельзя, убраны как мёртвый код.
- e2e на стенде R02 без расширения: `packages/testing/e2e/specs/host-adapter.e2e.ts` —
  MAIN в мир страницы и изолированная часть в песочницу WebDriver BiDi через preload-скрипты
  (до скриптов страницы, как `document_start`). Итоги — `.cache/e2e/host-adapter.json`.
- e2e части B: `packages/testing/e2e/specs/x8-send.e2e.ts` (32 теста) — строки матрицы
  §6.7.13, которые идут без хаба (опека, аренда и «обслуженный контекст» — R05/R10), отправка
  человеком с атрибуцией, тап в обоих порядках скриптов, сетевая ловушка: к стенду ходит
  только клиент самой страницы. Сборка стенда режется на модули с именами ролей ChatSpace,
  чтобы профиль квитанции читался из настоящих `modulepreload` и записей `performance`.
  Обрыв соединения в Firefox не воспроизводится (браузер сам повторяет POST после сброса) —
  сетевой сбой проверен юнит-тестом.
