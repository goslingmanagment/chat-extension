# R20: ChatGoose на fansly.com — план работ

Версия 1, 2026-10-12. Что строим — `docs/fansly/spec.md` (требования `FS-*`); факты о странице —
`docs/research/fansly-web.md`; решения владельца — X33 в `docs/decisions.md`.

## 0. Правила

- **Один PR — одна небольшая задача.** Draft; перед Ready — `pnpm check` и `pnpm e2e` локально (e2e — в
  Docker, `tools/ci/e2e-docker-local.sh`); в Ready — один раз. Работа — в отдельном worktree.
- **Ничего не включается при слиянии.** Всё Fansly-специфичное — за флагами страницы в хабе
  (`chatExtensionFeatures`) и за «Включить Fansly» в расширении. Пока флаги выключены, выпуски ChatSpace идут
  как обычно и Fansly-кода у чаттеров ChatSpace не касаются.
- **ChatSpace не ломаем.** Каждый PR, который трогает общий код (`core`, `ui`, `contracts`, `host-kit`),
  держит зелёными все e2e ChatSpace и его бюджеты размера.
- **Хаб — отдельный репозиторий**, свои PR по правилам `docs/hub-pr-plan.md`: каждый PR при слиянии ничего не
  включает; SDK в расширение — только из выложенного коммита.
- **Живой Fansly** — только на тестовой переписке владельца, только чтение и только с его участием.

### Этап 3. Спайк Fansly

Вопросы и как ответить (стенд, плюс живой Fansly только на чтение с владельцем):

1. Есть ли Navigation API в Firefox чаттеров; пропускают ли сигналы FS-RTE-2 смену адреса без изменений DOM и
   A→B→A до вызова наблюдателей — решает FS-RTE-3 (хук `history`).
2. Бывает ли `webRequest` опциональным в Firefox MV3; держит ли подписанное обновление с хостами Fansly в
   манифесте; будит ли слушатель `webRequest` event page — решает FS-PERM-2.
3. Регистрируется ли MAIN на `document_start` через `scripting.registerContentScripts` на fansly.com.
4. Не меняют ли Proxy над XHR и WS ответы, статусы, тайминги и порядок обработчиков страницы (стенд).
5. `execCommand('insertText')` из content script в `textarea` с `ngModel`: модель, кэш черновика, отмена, IME.
6. Ленивый relay во вкладке контейнера с прокси (стенд прокси, как в E149).
7. Какие события сокета означают удаление и правку сообщения (для хвоста, FS-TAIL-2).
8. Работает ли подтверждение прикрепления войса у старого вживую (якоря `waveform` в сборке нет).
9. HF-1: `external_page_id` против `account.id`.

Итог — `docs/fansly/spike.md` и правки спецификации, если ответы её меняют.

## 3. Риски

| Риск | Чем закрываем |
|---|---|
| Вставка в чужой чат (P1) | FS-INS-1, e2e на 200 переключений |
| Тихая потеря хвоста | §3 спецификации, e2e «сообщение за 0,5 с до клика», учёт долей |
| Двойное приветствие при переходе или откате | общая опека HF-3 |
| Новая сборка Fansly ломает якоря | контракт и деградация по одной функции, `host-contract-check` |
| Fansly переходит на `withFetch` | якоря ответов покажут; запасной наблюдатель `fetch` |
| Обёртки MAIN заметны скриптам страницы | минимум обёрток; инцидентов не было; уход в фон — только решением о правах |
| Запрос через чужую сессию или прокси | relay привязан к вкладке и документу, прямого запасного пути нет |
| AI беднее старого | HF-5…HF-8, сверка сформированного контекста |
| Память фона с двумя хостами | ленивые сервисы, журнал «Новых» в IndexedDB, сценарий 10 вкладок |
| Хаб не готов к пилоту | функции читаются «хаб пока не умеет», ничего не ломается |
| Объём растёт с выпусками старого | после 2.8.1 — после пилота (X33) |
