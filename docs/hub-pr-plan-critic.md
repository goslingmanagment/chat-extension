# Замечания критика к плану PR хаба (2026-10-03)

Вердикт критика: план нужно поправить. Исполнители PR хаба применяют эти правки поверх [hub-pr-plan.md](hub-pr-plan.md).

**Пробелы и ошибки плана хаба (проверено по hub 90b642e9 и по клиентским репозиториям)**

1. **H-7b/H-7c: возможен двойной привет фану, которого уже поприветствовал десктоп.**
   - Что в коде. Индекс `ofapi_commands_follower_outreach_uniq` (миграция 0195) держит команду `new-follower` навсегда. Он отпускает её только в двух случаях: отмена до захвата или отказ с `local_precondition`/`auth_gate`. Успешная (`succeeded`) команда тоже остаётся в индексе.
   - Что в плане. Шаг 5 `dispatch` смотрит только «неразрешённые» команды десктопа. Шаг 6 смотрит только `client_greetings`. Фаны, которых десктоп уже поприветствовал (19 приветствий с 21.09), будут показаны как «не поприветствован», и расширение даст отправить второе приветствие.
   - **Исправление.**
     - Для привета применять тот же CASE-предикат, что в индексе. Успешная команда → `greeting_done`, в ответе `greeting.state="confirmed"` и `source:"desktop-outbox"`. Неразрешённая → `custody_held`.
     - То же самое показывать в сводке H-7c `claim.greeting`.
     - Тесты: успешная команда десктопа блокирует привет; отмена до захвата и `local_precondition` не блокируют.

2. **H-1a: набор совместимости не проверяет реальные пути старых клиентов.**
   - **Fansly.** Строка Fansly должна вызывать Fansly-страницу с `clientContext`. Нужны: полный Recap на 3000 сообщений, `replyMode:"preferSplit"` на всех фичах, `personalMessageCount`. Без этого обещания H-6 («Fansly на 3000 без изменений») и H-10 («старые клиенты не меняются») набор не проверяет.
   - **Десктоп.** Строка десктопа должна идти по OF-полосе, где контекст собирает хаб.
   - **chat-extension, после H-3.** Строки нового клиента должны работать **узким** токеном. Плюс проверка `row.operations ⊆ CLIENT_TOKEN_PROFILES["chat-extension"].operations`. Иначе выпавший из разрешённого списка ключ найдётся только в проде.

3. **H-1a: реестр и фикстуры записываются по хешу контракта.**
   - Хеш — это sha256 OpenAPI (`generate.ts:62`). Сам план в H-4a меняет код SDK без смены хеша. Значит, два разных бандла могут иметь один хеш, и фикстуры `<hash12>` перезапишут друг друга.
   - **Исправление:** ключ строки и фикстуры — sha256 бандла; `contractHash` хранить полем; на один хеш допустить несколько строк. В health отдавать хеши без повторов.
   - **Ещё в этом же PR:** добавить `tests/fixtures/client-sdks/**` в `ignores` файла `eslint.config.mjs`. Сейчас `eslint .` проверяет `**/*.mjs`, и ~1 МБ zod-бандла сломает `pnpm check`.
   - **Мелочь:** в SDK нужен `auth:{mode:"bearer", token:()=>…}` (`sdk-runtime.js:82-83`), а не `{mode:"bearer"}`.

4. **H-4c: не учтён предел размера тела AI-запроса.**
   - `AI_FEATURE_STREAM_BODY_LIMIT_BYTES` = 12 MiB. Он закреплён против худшего допустимого тела в `tests/contracts-coach-body.test.ts`.
   - Схема не запрещает `liveTextContext` для Coach. С ним худший случай растёт с ~1,69M до ~2,0M символов UTF-16, ×6 байт ≈ 12,0 МБ при пределе 12,58 МБ.
   - **Исправление:** в H-4c обновить расчёт худшего случая и тест; при необходимости поднять предел.

5. **H-4b: `knownFanMessageId` не привязан к фану.**
   - Поиск в плане идёт по `(account_id, platform, message_ref)`. Id из чата другого фана той же страницы найдётся, а спецификация требует проверки страницы **и фана**.
   - **Исправление:** искать с `conversation_ref = conversationRef` (и тем же разговором в `dm_message_archive`). Id из чужого разговора → `absent` (или `context_conflict`). Добавить тест.

6. **H-2b/H-3: хаб сам не применяет `minVersion`.**
   - `chatExtensionMinVersion` только отдаётся в bootstrap. Плохой выпуск XPI нельзя остановить на сервере, а §8.3 требует, чтобы сервер сам проверял каждый метод.
   - **Исправление:** в `requireClientFeature` и в AI-выключателе для узкого токена проверять `x-client-version`. Если `chat-extension/<v>` ниже `minVersion` или версию нельзя разобрать → 409 `client_feature_disabled`, reason `client_outdated`. Bootstrap при этом отвечает 200. Добавить причину в константы и тест.

7. **H-7b: «мгновенный» выключатель и `flagRevision`.**
   - H-2b разрешает держать эффективный конфиг 5 с. `dispatch` обязан вычислять флаг из строк, взятых `FOR SHARE` внутри своей транзакции (с подстановкой значения по умолчанию), и никогда из этого кэша. Тест: выключили флаг и сразу `dispatch` (меньше 5 с) → отказ.
   - Смысл `flagRevision` в теле `dispatch` не задан. Либо определить (старая ревизия и флаг изменился → 409 `flags_stale`), либо убрать поле.

8. **Отсутствие запросов к OFAPI доказано только для H-9c.**
   - **Исправление:** общий тестовый помощник. В нём:
     - заглушка `fetch` и undici `disableNetConnect`;
     - счётчики строк `ofapi_request_attempts`, `ofapi_capture_jobs`, `ofapi_interactive_requests`, `ofapi_commands`, `history_requests`;
     - проверка, что `page_dm_threads.unread_count` не изменился.
   - Подключить его в integration-тесты bootstrap, recaps, from-generation, stats, awaiting-reply, claim GET/POST, audience-new, ai-usage. И в AI-поток со свежим текстом, `knownFanMessageId` и глубиной 3000: `loadTranscriptContext` сейчас ходит только в БД (проверено), это нужно закрепить тестом.

9. **Зависимости.**
   - H-9c использует `services/client-coverage.ts` из H-4b, и его тест сравнивает голову с `context_v1.servedHead`. Значит, H-9c зависит от H-4b. В плане поток «Чтения» идёт параллельно, и эта зависимость не указана.
   - У `services/signed-cursor.ts` нет одного владельца («из H-9c или вводится здесь»), а нужен он H-9c, H-8c и H-7c. **Исправление:** вынести его в H-9b или в отдельный маленький PR и поставить зависимость всем трём.

10. **H-7d меняет хеш контракта, а план этого не отмечает.**
    - `OFAPI_COLLECTION_CATEGORIES` питает `ofapiCollectionCategorySchema = z.enum(...)` в `routes-ofapi-collection.ts`. Новая категория `account_settings` меняет OpenAPI.
    - **Исправление:** отметить «хеш меняется» и запускать `contracts:generate`. Маршруты там только сессионные (`session`/`owner-session`), device-клиентов это не задевает.
    - Цену шаблона приветствия OFAPI отдаёт в долларах: явно переводить в `priceMills` и покрыть тестом.

11. **Приёмочный критерий «Hi доступен фану только с автоматическими сообщениями» (hub-plan §6) не покрыт ни одним PR.**
    - В коде `assertHiGreetingFreshness` на OF-полосе считает все сообщения: там нет признака автоматики («no automation signal»). `isFromQueue` хаб нигде не читает. Прод работает в режиме `serve` через union с `dm_message_archive`.
    - Если приветствия и рассылки попадают в архив или union, фан с больше чем 10 автосообщениями заблокирован для Hi.
    - **Исправление:**
      - read-only сверка на проде (есть ли рассылки и приветствия в `message_archive`/`dm_message_archive` у свежих подписчиков), результат — в описание PR H-4c или H-7c;
      - integration-тест гейта Hi на OF с автоматическими строками;
      - если такие строки там есть — отдельная правка хаба до M5.

12. **Детали опеки отправки (H-7b).**
    - В `sent`/`failed` нет `instanceId`: другой экземпляр того же пользователя может пометить чужую попытку как `failed`. Добавить поле и требовать совпадения для `failed`.
    - `failed: native_rejected` должен требовать `httpStatus` из 400–499, кроме 401 (§6.7.7/§6.7.13: 401 опеку не снимает).
    - Лимит 6 отправок за 60 с на пользователя не сериализован: блокировка в плане — по фану. Взять advisory-блокировку на пользователя перед подсчётом.

13. **Не хватает тестов на приёмочные пункты спецификации.**
    - **H-7b:**
      - второй привет другой генерацией после подтверждения → `greeting_done`/`generation_mismatch`;
      - после `registerNativeSend` при выключенном `previewSend` новый `dispatch` всё равно отклоняется;
      - `registerNativeSend` не снимает чужую опеку.
    - **H-7c:** награда «топ-фан» исключена; `renewed`/`returning` никогда не становятся `new`.
    - **H-8b:** покрытие при неизвестной истории (`coverage` partial/unknown, корзина молчания `unknown`).
    - **H-4c:**
      - сообщение, которого нет в архиве, попадает в промпт (проверить через подставной провайдер);
      - `params` генераций старых клиентов побайтно не меняются после обобщения `featureParams`;
      - в режиме `shadow` в манифест пишутся только id и счётчики.

14. **Формы контракта.**
    - В `clientBootstrapPageSchema.platform: platformEnum` и `identity.role: z.enum(userRoles)` — закрытые перечисления. Это нарушает собственное правило §4.0: новая платформа или роль ломает разбор всего bootstrap в уже выпущенных XPI. Сделать `clientOpenToken`, сужать на клиенте.
    - `ofMessageId` (`^[0-9]{1,30}$`) и CHECK в SQL расходятся с `^[1-9]\d{0,29}$` у ленты, свежего текста и `fanRef`. Свести к одной форме.

15. **H-9c: `summaryWindow` до 3000 при потолке читателей 1500.**
    - Читатели упираются в `ARCHIVE_AI_TRANSCRIPT_MAX_ROWS` = 1500, а 3000 из H-6 действует только для полного Recap. Иначе первая страница ленты будет делать глубокое чтение.
    - **Исправление:** ограничить окно 1500 (или окном Ping).

16. **H-4c: гигиена текста.**
    - Пропускать элементы свежего текста через тот же `normalizeDmMessageText`, что и строки архива: в hub-plan §3.4 сказано «без HTML, ссылок».
    - Сообщение ошибки `context_conflict` — только с id, без текста фана в логах.
