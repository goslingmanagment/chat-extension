# Слой хаба (`@cg/hub`, пакет работ R08)

Как расширение разговаривает с хабом. Обязательная часть — `architecture.md`
§5.8, §7, §8.1–§8.7, §13, §14 и `docs/protocols/hub.md`; здесь — как это
устроено в коде и что нужно знать интегратору и разработчику.

## Где живёт и кто им пользуется

- Пакет `packages/hub`, только фон: токен, сеть и вендоренный SDK не попадают
  ни во вкладку, ни на страницы расширения (это проверяют `pnpm lint` и
  `pnpm gates`).
- Вход один — класс `ChatExtensionHub`. Он реализует замороженный
  `HubFacade` из `@cg/contracts` и добавляет то, что нужно службам фона:
  события входа, статус связи, привязку аккаунта к странице, доску Spenders,
  эхо промпта, квоту.
- Ошибки — два вида (контракты 1.1.0): `HubCallError` — ответ хаба или сбой
  сети, уже прочитанный резолвером (`resolution`: код CG и что делать);
  `HubCheckError` — отказ самого слоя без запроса (не вошли, страница не
  выдана, функция выключена, у хаба нет нужной возможности…). Резолвер чистый,
  он в `packages/core/src/domain/errors/hub-map.ts`.

## Один транспорт: вендоренный SDK

Все вызовы хаба идут через вендоренный SDK (`src/sdk-transport.ts`, сборка вызова —
`src/transport.ts`): вход и выход, `health`, `me`, каталог персон, поток AI, рекапы,
Spenders v2, корзины, ingest и все маршруты `client/*` — bootstrap, общие рекапы, досье
из генерации, расходы AI, а с перевендорингом из `main` хаба `c8514c5c` (2026-10-08) и
лента архива, статистика Spenders, «ждут ответа», бронь и её статус, «Новые». Метод и
путь — из манифеста SDK (`kernelOperations`), авторизация — его, ответ сначала проверяет
схема SDK для этого статуса, потом наша схема контракта: ответ не той формы или статус
успеха, которого SDK для маршрута не объявляет, — сбой хаба (`CG-HUB-REQUEST`), а не
данные. Ошибочный ответ (4xx, 5xx) читается по своему телу, схемой не проверяется.

Запрос маршрута `client/*` приходит от фасада одним объектом и сначала проверяется
строгой схемой контракта: не прошёл — это наша ошибка, в сеть он не уходит. Параметры
пути берутся из него по пути манифеста SDK (`sdkInputOf`), остальное — query (GET) или
тело (POST; у брони тело лежит в поле `body`). Сам SDK запрос не проверяет, поэтому
схема контракта не должна пропускать то, на что хаб ответит 400: поддельный хаб в e2e и
в тестах проводки проверяет каждый запрос `client/*` настоящими схемами хаба (`routeSchemas`
вендоренного SDK — параметры пути, query и тело), а свои ответы — его схемами ответа.

Раньше, пока PR хаба для ленты, статистики, брони и «Новых» не были слиты, эти шесть
маршрутов шли отдельным модулем RouteTransport; с перевендорингом из `c8514c5c` он
удалён. Маршрут контракта, которого нет в SDK, не отправляется вовсе (сбой контракта до
сети); когда он приходит в SDK, у него в `HUB_ROUTES` ставят `since: 'sdk'` — тест
`sdk-alignment` падает в тот день, когда ключ появился в SDK, а мы его не перевели.

Маршрут `client/*` вызывается, только если bootstrap объявил нужную
возможность; иначе `CG-HUB-CAPABILITY` без запроса — так хаб, у которого
маршрута ещё нет, о нём не спрашивают.

То же для поля, а не маршрута (R20 F6b, чтения по разговору): рекапы, сохранение досье
из генерации и лента называют разговор (`conversationRef`), только когда это не фан (на
Fansly — группа), и только хабу с `conversation-recaps-v1`. Без возможности такое
чтение отказано слоем (`CG-HUB-CAPABILITY`) и не уходит: ленту или рекапы фана вместо
группы слой не читает. Страница ленты, чей `target.conversationRef` не тот, что в
запросе, — сбой контракта. Досье — фана: где чат и есть фан (`CHAT_IS_FAN`, OnlyFans),
оно читается по разговору (`pageConversationProfile`), иначе — по фану
(`pageFanProfile`). На ChatSpace разговор не назван никогда, и запросы прежние байт в
байт (`docs/protocols/hub.md` п. 18).

**Хаб старше SDK** (прод выкладывают позже, чем сливают `main`). SDK не шлёт хабу
свой хеш контракта: в заголовках запроса его нет (только `authorization`,
`content-type`, наш `x-client-version` и у потока AI `x-kernel-ai-capabilities`), и
хаб клиента по версии SDK не отвергает. Список `compatibleClientSdks` в `health` —
справка для гейта выпуска; слой хаба только показывает его в «Аккаунте» («Совместимость»:
несовместимо) и в выгрузке диагностики, больше ни на что он не влияет. Хаб отвергает
клиента только по `x-client-version` ниже минимума владельца (`client_outdated`), а это
версия расширения, не SDK. Поэтому на хабе со старым контрактом всё, что он умеет,
работает, а функции его новых маршрутов читаются из bootstrap как `hub_not_ready` и не
вызываются: так сборка из `c8514c5c` работала против прода `27ef8a3d…`, пока хаб не
выложили 2026-10-08 (`apps/extension/test/wiring-background.test.ts`, «a hub older than
the vendored SDK»).

Особенность вендоренного SDK: путь `spenderBatch` — `/api/v2/spenders:batch`,
а сборщик путей SDK читает `:batch` как параметр и падает. Такой путь слой
отправляет сам, с тем же методом, авторизацией и заголовками (`sdk-transport.ts`).

На каждом запросе — `x-client-version: chat-extension/<версия>`. Никогда не
вызываются: `/ofapi/*`, поток событий, полные персоны, сырой шлюз AI,
маршрут Fansly `followerOutreachAttempt`, `pageTopSpenders`, маршруты кабинета для
зависших отправок `clientSendCustodyResolve` и `clientSendCustodyList` (в SDK они есть,
но это сессия кабинета владельца, токен устройства до них не доходит).

## Поток AI и возможности заголовка

- Поток идёт через `streamAiFeature` вендоренного SDK. Что запрос объявляет
  хабу (`debug-input-v1`, `context-v1`, `split-all-v1`), SDK кладёт в заголовок
  `x-kernel-ai-capabilities` своей опцией `capabilities` и сам разбирает все
  кадры, включая `context_v1`, своей схемой; потом кадр проверяет наш контракт.
  Кадр `context_v1` нестрогий с обеих сторон: новый ключ более нового хаба
  поток не ломает; кадр, который схема SDK не приняла, — сбой контракта
  (`CG-HUB-REQUEST`), а не падение.
- **Хаб бывает старше SDK** (прод выкладывают позже, чем сливают `main`).
  Запросу доступно только «объявлено bootstrap хаба ∩ умеет транспорт»
  (`streamCapabilities()`): возможность, которую хаб не назвал, не объявляется
  никогда. Функции, которым она нужна, читаются как `hub_not_ready` — «хаб
  пока не умеет эту функцию»: свежий текст страницы не уходит, Split в Ping,
  Hi и Coach не запрашивается, генерация идёт по архиву. Запрос, который всё
  же просит необъявленную возможность, слой отклоняет сам (`CG-HUB-CAPABILITY`)
  и не отправляет. Возможность, которой не знает эта сборка, ничего не меняет.
- `AiStreamTransport` (`src/ai-stream-transport.ts`) остался тонким портом над
  SDK: тесты подставляют через него сбои, а два его события — «запрос отдан
  сети» и «хаб ответил» — дают журналу и операции знать, где стоит запрос
  (ниже, «Где стоит запрос»).
- Кадры читаются строго: до `meta` ничего; неизвестный кадр, второй `meta`,
  `context_v1` после текста или без запроса — сбой. Чужая персона в `meta` —
  результат отбрасывается, каталог перечитывается, `CG-PERSONA-CHANGED`.
- Повтор один: структурированный 503 `service_unavailable` до первого кадра,
  через 5 с (событие `onStreamNotice` — «Сервис недоступен, повтор через 5 с…»).
  Больше ничего само не повторяется. Обрыв без `done` — `CG-STREAM-TRUNCATED`.
- Повтор уходит с тем же телом и тем же `clientRequestId`. Так мы читаем §7
  «у попытки своя корреляция»: §8.4 задаёт `clientRequestId = opId`, и по нему
  сверяется `meta`; хаб резервирует `clientRequestId` только после своих
  проверок на 503, а вторая резервация того же id получает 409
  (`apps/runtime/src/services/ai-gateway.ts` хаба). Значит, двух принятых
  платных запросов на одну операцию быть не может, а новый id на повтор
  сломал бы сверку `meta`. Новый id мы не чеканим.
  429 `quota_denied` — `CG-QUOTA-DAILY` до 00:00 UTC.

## Где стоит запрос: журнал и код ошибки

Первая живая проверка кончилась `CG-HUB-TIMEOUT` через 30 с, и по журналу
нельзя было сказать, ушёл ли запрос вообще. Теперь это видно всегда — в
журнале `bg.hub` и в технической строке ошибки. В журнал идут только факты:
маршрут, фича, номер попытки, статус, миллисекунды — ни тела запроса, ни
текста ответа, ни токена. Каждое значение — одно слово без пробелов, иначе
чистка журнала заменила бы его длиной.

| Что случилось | Строка `bg.hub` | Что видит человек |
|---|---|---|
| запрос отдан сети | `stream request sent` (`prepareMs`) | — |
| хаб ответил на рукопожатие | `stream answered` (`status`, `answerMs`) | — |
| слой отказал сам до запроса (страница не выдана, функция выключена, нет возможности, персона) | `stream refused before the request` (`kind`, `code`, `reason`) | код отказа сразу |
| запрос не удалось собрать или отдать (сбой до сети) | `stream request not sent` (`error` — имя ошибки) | `CG-HUB-REQUEST` сразу |
| браузер не смог отправить (нет сети, DNS, сброс соединения) | `call failed` (`failure: network`) | `CG-NETWORK` сразу |
| хаб ответил отказом | `call failed` (`failure: http`, `status`, `error`, `reason`) | код по карте ошибок |
| срок операции вышел, запрос ушёл, ответа нет | `stream aborted before the hub answered` (`waitedMs`) | `CG-HUB-TIMEOUT`, в технической строке `until-meta: no-answer` |
| срок вышел раньше, чем запрос ушёл | `stream aborted before the request was sent` (`waitedMs`) | `CG-HUB-TIMEOUT`, `until-meta: not-sent` |
| любой вызов хаба длился 3 с и больше | `slow call` (`route`, `ms`, чем кончился) | — |

Планировщик операций (`bg.ops`) пишет в строку `stream deadline passed`, на
каком шаге стоял запрос: `not-sent`, `no-answer`, `no-frames` (хаб ответил, но
кадров нет), `silent` (кадры были и кончились). Если срок вышел без единого
ответа, а браузер говорит, что сети нет (`navigator.onLine`), код —
`CG-NETWORK` («нет связи»), а не `CG-HUB-TIMEOUT`: запрос не дошёл, а не хаб
медлил. Когда браузер сам ничего не говорит (запрос висит в сети), остаётся
`CG-HUB-TIMEOUT` с шагом в технической строке.

Сбой до запроса никогда не ждёт срока: что бы ни бросило исключение — сборка
тела, проверка схемы, сам слой хаба, отказавшее обещание в настройке потока, —
операция кончается сразу с `CG-HUB-REQUEST` и строкой в журнале
(`operation failed before the hub request`, `stream failed outside the facade
contract`).

## Вход

- Переходы входа строго по одному. Токен, адрес хаба и пользователь пишутся
  одной записью `auth.token`, метаданные — `auth.meta`. Пароль в памяти только
  на время запроса; токен в логи не попадает никогда.
- Вход стирается только при 401 `token_revoked` / `token_expired` того же
  токена и той же эпохи. 401 без причины — `CG-AUTH-REJECTED`, 403 — вход
  остаётся. Ответ на старый токен новый вход не трогает.
- Выход: стереть → отозвать на хабе-издателе (5 с) → стереть ещё раз.
- Каждая смена входа увеличивает эпоху: `epochSignal()` прерывается, все
  операции прошлого входа отменяются, событие `onSessionChange` несёт новую
  эпоху и причину.
- Узкий токен (H-3): хаб должен вернуть эхо `client: 'chat-extension'`, а
  bootstrap — `identity.tokenClient`. Иначе выданный токен сразу отзывается и
  показывается `CG-HUB-OUTDATED` — кроме режима совместимости ниже.

## Часы (HB-008)

- Двое часов в `HubClock`: настенные (`now`, `Date.now`) — для показа,
  абсолютных границ UTC (сброс квоты в 00:00 UTC) и отметок, которые
  переживают фон (кэши в хранилище); монотонные (`monotonic`,
  `performance.now`) — для прошедшего времени внутри жизни фона: срок
  bootstrap и каталога, возраст кэша доски, интервал обновления по фокусу,
  30 минут досылки досье, срок снимков эха.
- Отметка из хранилища (другая жизнь фона) меряется настенными часами; отметка
  из будущего (часы перевели назад) считается просроченной, а не свежей.
- Сроки от хаба — `Retry-After` и `serverNow`/`expiresAt` — переводятся в
  наши часы от момента ответа (`localDeadline`), часы никогда не сдвигаются.

## Режим совместимости (только для разработки)

Хаб без H-2 и H-3 не знает ни узкого токена, ни `client/bootstrap` (отвечает
404). Чтобы расширение можно было запускать против такого хаба, есть режим
совместимости. Прод-хабу он больше не нужен: на первой живой проверке
(2026-10-04) прод выдал узкий токен и ответил на `client/bootstrap`, вход
прошёл без этого режима. Режим остаётся для старого или локального хаба.

**Когда включён:** только в тестовой сборке (`CG_TEST_HOSTS=1`) и только при
`settings.debug.enabled` — оба условия сразу (`HubContext.compatAllowed`).
В выпускной сборке режима нет, что бы ни стояло в настройках: отладку может
включить любой чаттер, а ущерб от украденного входа ограничивает именно узкий
токен (`architecture.md` §14). Выпускная сборка на хабе без эха отзывает
выданный токен и говорит `CG-HUB-OUTDATED`, на хабе без bootstrap — тоже
`CG-HUB-OUTDATED`. Код режима в выпускном бандле остаётся (он в пакете `hub`),
но недостижим: его условие — признак тестовой сборки, которого у выпускной
нет. Тестовая сборка без отладки ведёт себя как выпускная.

**Что делает:**
- принимает полный токен (без эха `client`); в статусе `compat: true`;
- на 404 от `client/bootstrap` собирает bootstrap сам из `me` и списка
  страниц (`GET /pages`); каталог персон читается своей службой как обычно;
- все функции, которым нужны новые маршруты (рекапы хаба, лента, статистика,
  «Новые», свежий текст, Split везде), помечены недоступными с причиной
  `hub_not_ready`. Это касается и генерации Recap: флаг `recap` по контракту
  требует `shared-recaps-v1` и `recap-profile-v1`. Функции страниц собранного
  bootstrap включены, поэтому причина всегда «хаб не готов», а не «выключено
  владельцем»; возможностей нет; отправка из превью (X8) выключена;
  `minVersion` 0.0.0; пределы — `COMPAT_LIMITS`;
- у страниц прод-хаба нет `platformAccountId`. Привязать аккаунт можно только
  явной картой `compatPageAccounts` (`pageLabel` → id креатора OnlyFans),
  которую передаёт dev-сборка корня композиции. Подбора по имени нет.
- какие платформы клиент обслуживает, слой хаба сам не знает (R20 F9b): корень
  композиции передаёт `compatPlatforms` — платформы сайтов сборки (по
  рантайм-таблице хостов, сегодня `onlyfans`); страница другой платформы —
  `platform_unsupported`, как сказал бы хаб.
  Корень композиции фона берёт карту из `storage.local` (ключ
  `dev.compatPageAccounts`) только в тестовой сборке и следит за её
  изменениями; как её задать — README, «Живые проверки».

**Как выглядит:** статус `degraded`, источник bootstrap — `compat`.

**Как выключается:** если в тестовой сборке выключить отладку, синтезированный
bootstrap перестаёт приниматься, а запросы с полным токеном отклоняются
(`CG-HUB-OUTDATED`, статус `stopped`). То же — в выпускной сборке, где режима
нет вовсе: полный токен, оставшийся в хранилище, она не использует и стирает
при старте. Стирается и отзывается полный токен
только явным переходом `notifyDebugChanged()`: служба настроек вызывает его при
каждой смене `settings.debug.enabled` и один раз после загрузки настроек.
Чтение флага само ничего не стирает: после перезапуска фона настройки могут
прийти позже, и вход разработчика не должен пропасть из-за этого.

## Что подключает интегратор (корень композиции фона)

```ts
const hub = new ChatExtensionHub({
  env: { extensionVersion, testBuild: __CG_TEST_HOSTS__, os, hubOrigin: () => settings.hub.baseUrl, debugEnabled: () => settings.debug.enabled },
  local: createKeyValueStore('local'),      // R07, @cg/platform
  session: createKeyValueStore('session'),  // R07: общий кэш доски Spenders
  fetch: (input, init) => fetch(input, init),
  log: /* логгер R18, только факты */,
  // compatPageAccounts: только в dev-сборке
});
```

- события: `onSessionChange` → `session.changed`, `onBootstrapChange` →
  `bootstrap.changed`, `onCatalogChange` → `catalog.changed`,
  `onQuotaChange` → `quota.changed`, `onStreamNotice` → состояние операции
  (фаза `retry-wait` со временем повтора: `OpScheduler.noteRetry`);
- `notifyHubOriginChanged()` — служба настроек вызывает при каждой смене
  `settings.hub.baseUrl`. Обычно адрес меняется только без входа (ST-042), но
  если вход есть и смена делает его непригодным (другой хаб, AU-016) или снова
  пригодным, эпоха растёт, операции старого адреса отменяются, а
  `onSessionChange` приходит с причиной `hub-changed` (§7). Вход не стирается:
  выход отзывает токен у хаба-издателя, а возврат адреса снова его включает;
- `notifyDebugChanged()` — при каждой смене `settings.debug.enabled` и один
  раз после загрузки настроек: выключение в выпускной сборке стирает и
  отзывает полный токен режима совместимости и убирает эхо промптов,
  включение перечитывает bootstrap и каталог;
- `notifyFocus()` — на фокус вкладки ChatSpace (не чаще раза в 60 с сам);
  `checkConnection()` — «Проверить связь»; `status()` — строка «Связь» и раздел
  «Аккаунт»;
- `resolveBinding(account)` — `binding.resolve`; `bindingHolds(binding)` —
  сверка привязки в конце генерации и перед записью. Привязка — это
  идентичность, она разрешается и на истёкшем bootstrap (готовые результаты
  остаются читаемыми, §8.3);
- `flagState(flag, page)` — гейт каждого чувствительного действия (вставка,
  переход в чат, X8 и остальные): на истёкшем bootstrap он отвечает
  `bootstrap_expired`, пока не придёт обновление (владелец мог выключить
  функцию). Перед действием можно сначала вызвать `await bootstrap()`: он
  обновит истёкший bootstrap или откажет с причиной. Бронь и отправка из
  превью проверяют свежесть сами. Поток AI — единственное исключение: он
  идёт и по bootstrap, истёкшему не больше двух своих сроков назад, пока
  обновление идёт рядом (хаб проверяет каждый вызов AI сам); если такого
  нет — ждёт обновления, но не дольше срока операции. Что он ждал или шёл по
  истёкшему, написано в журнале (`docs/pilot-readiness.md`, раздел 5, п. 17);
- `cachedFlagState(flag, page)` — тот же выключатель по кэшированному bootstrap,
  свежему или истёкшему (решение X45): только для вставки готового результата,
  когда хаб не ответил на перечитывание;
- `stream(…)` — генерации (тело запроса собирает ядро: драйверы фич поверх
  `core/src/domain/ops/request.ts`); `promptEchoTicket` /
  `promptEcho` — эхо промпта для `debug-prompt.html`;
- `spendersBoard(…)` — `spenders.board` (до 1000 строк, кэш 10 мин общий для
  вкладок); `saveRecapProfile(…)` — сохранение досье по графику §7, сигнал
  вкладки отменяет и паузы, и запись в полёте;
- `ingest(events)` → `{ accepted, duplicates, healthRefused }`: события
  `ai_acceptance` уходят всегда и первыми; `client_health` без возможности
  `client-health-perf-v1` не отправляются и считаются в `healthRefused` —
  очередь R18 выбрасывает их, как пачку с ответом 400, и не повторяет. У отчёта
  `client_health` id выводится из вида, версии, сайта, сборки и окна: один отчёт
  на окно, а окно у фона — на пару (сайт, сборка) (R20 F7); без сайта и сборки в
  id хаб отбросил бы второе окно того же периода как дубль;
- `aiUsage(…)` — только в режиме отладки (иначе `CG-FEATURE-DISABLED` ·
  `debug_off`, без запроса);
- `clearCaches()` — «Очистить локальные данные»: доски Spenders, эхо промптов
  и последняя квота стираются, bootstrap и каталог перечитываются; вход
  остаётся.

Всё перечисленное подключено в `apps/extension/src/composition/background.ts`.
Гейт чувствительных действий для вставки и перехода стоит там, где фон выдаёт
токен действия (`background/token-gate.ts`): на истёкшем bootstrap токен не
выдаётся, пока хаб не ответит снова. Исключение — вставка готового результата
(решение X45, владелец отменил X12 п. 19 для вставки): если перечитать bootstrap не
удалось, потому что хаб молчит (CG-HUB-UNAVAILABLE, CG-HUB-TIMEOUT, CG-NETWORK,
CG-TIMEOUT), вставку решает кэшированный bootstrap этого входа (`cachedFlagState`):
выключатель там включён — токен выдаётся, выключен — отказ с его причиной. Хаб,
который ответил («вход отозван», «доступ запрещён», «клиент устарел», лимит), —
отказ с его кодом; переход в чат и новые генерации правило не меняет. Вкладка в это время сверяет
вставку с привязкой из последнего bootstrap этого входа (`TabEnvironment.pageWhileHubSilent`):
перечитать его она тоже не может, а без этой сверки после перезапуска фона вставка не
прошла бы ещё до запроса токена.
