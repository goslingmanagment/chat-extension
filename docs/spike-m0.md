# Спайк M0: итоги

Дата: 2026-10-03. Пакет работ R00 «Каркас», ветка `goslingmanagment/r00-scaffold`.
Где мерили: Mac владельца, Node 26.7.0, pnpm 10.33.1, Firefox 157.0 без окна.
Что проверяли — `docs/architecture.md` §3 «Спайк M0 проверяет до основной работы».
Итоги перепроверены после независимой проверки (исправления — в конце ветки).

## Коротко

- **Проверки пройдены, кроме двух пунктов, которые здесь не проверить:** подписи
  в настоящем AMO (нужны ключи и ваше «да») и настоящего ввода через метод ввода
  (IME). Весь путь подписи под Node 26 прошёл на локальном макете AMO.
  Откатываться не пришлось: остаёмся на **Node 26** и **Preact 11**.
- **Один бюджет уже под угрозой.** Синхронный старт изолированного скрипта,
  если мерить честно — весь бандл от первой строки до последней, — при первом
  запуске после установки занимает 4,2–4,5 мс. Это больше бюджета 3 мс, и это
  на быстром Mac. При повторных загрузках — медиана 1,4–1,5 мс. Разбирать в R09
  (подробности в проверке 2). Прошлая цифра «≤ 1 мс» мерила только нашу функцию
  и была неверной.
- Проверка идёт автоматически: `pnpm e2e` собирает обе сборки и в Firefox без
  окна ставит выпускной XPI (2 сценария) и тестовую сборку (9 сценариев на
  локальном стенде) — ~15 секунд вместе со сборками. `pnpm check` (типы, линт, тесты, сборка,
  `web-ext lint`, размеры, инварианты, паритет, архив) — зелёный после чистой
  установки, ~12 секунд.
- **Не проверено:** подпись в настоящем AMO, IME, замеры на winpc, обновление
  через фид, тап WebSocket после перезапуска Firefox, живой ChatSpace (ждёт
  вашего входа в dev-профиль). Таблица — в конце.

Что всплыло:
- `web-ext lint` даёт три предупреждения, ошибок нет. Два — `innerHTML` внутри
  самого Preact (его поддержка `dangerouslySetInnerHTML`; мы её не используем,
  гейт запрещает), одно — `import()` с переменной (так грузятся ленивые чанки).
  Для выпуска это не помеха; `pnpm check` падает только на ошибках линтера.
- В WebdriverIO 9.32 команда `uninstallAddOn` сломана: шлёт GET с телом, и
  `fetch` в Node такое отвергает. Это ошибка WebdriverIO, не Node 26 (так ведёт
  себя любая современная Node). Обошли командой BiDi `webExtensionUninstall`.
- geckodriver WebdriverIO скачивает сам при первом запуске (нужен интернет один
  раз); скрипты установки пакетов `geckodriver`, `edgedriver`, `esbuild` не нужны
  и выключены.
- Firefox 157 не даёт WebDriver открыть страницу расширения (`moz-extension://…`)
  без флага `--allow-system-access` у geckodriver. Он включён только в e2e
  (одноразовый профиль без окна): так проверяется выпускной XPI.
- WXT печатал ~210 ложных предупреждений «Could not get stats» при каждой
  выпускной сборке: список файлов архива исходников он проверяет не от той
  папки. Архив был в порядке. Теперь `pnpm build` запускает `wxt zip` из корня
  репозитория — предупреждений нет, содержимое архивов то же байт в байт.
- WXT загружает каждую точку входа в Node, чтобы прочитать её настройки. Node
  не понимает импорты без расширений в вендоренном SDK, поэтому первый же импорт
  `@cg/hub` в фоне ломал сборку. Исправлено настройкой WXT (SDK встраивается при
  этой загрузке); проверено пробным импортом — R08 на это не наткнётся.

## Проверка 2. Preact 11 в закрытом Shadow DOM — пройдена, кроме IME

На стенде (наша страница с той же структурой поля ввода, что у ChatSpace:
`div.relative > .composer-frame > полоса > слот переводчика`):

- **Док** встаёт в поток первым ребёнком корня рамки, над полем ввода, как в
  §6.3. Страница его shadow root не видит (`shadowRoot === null`).
- **Стили** через `adoptedStyleSheets` работают в content script Firefox сразу;
  запасной `<style>` не понадобился. Теперь это доказывает e2e: изнутри
  закрытого корня проверяется вычисленный стиль строки дока (`display: flex`,
  высота 36 px) и высота хоста на странице — 36 px (без наших стилей было бы
  ~22 px). Так же и при **строгом CSP** страницы; для него отдельный снимок
  `.cache/e2e/stand-dock-strict-csp.png`.
- **Замеры.** В e2e выключено огрубление таймера Firefox
  (`privacy.reduceTimerPrecision`), точность — 0,02 мс. Каждая цифра — медиана и
  максимум по 12 загрузкам стенда; прогонов было 5, в таблице — разброс по ним.

  | Что | Медиана | Максимум | Бюджет §11 |
  |---|---|---|---|
  | мост MAIN: установка | 0,02 мс | 0,06 мс | 1 мс |
  | **синхронный старт изолированного скрипта, первый запуск после установки** | **4,2–4,5 мс** (по одному замеру на прогон) | | **3 мс на winpc** |
  | то же, повторные загрузки | 1,4–1,5 мс | 3,4 мс | 3 мс на winpc |
  | из него — наша функция `composeTab` | 0,2–0,25 мс | 0,5 мс | |
  | загрузка чанка дока (`import()`) | 2,5–2,8 мс | 3,6 мс | |
  | первая отрисовка дока | 0,4 мс | 0,5 мс | |
  | список на 1000 строк, первая отрисовка | 5,7–6,6 мс | 9,7 мс | |
  | тот же список, обновление всех 1000 строк | 1,7–1,8 мс | 5,3 мс | |

  «Синхронный старт» мерится от первой до последней строки файла
  `content-scripts/chatspace.js` (метки `performance.now()` ставит тестовая
  сборка): верхний уровень бандла (схемы zod/mini, рантайм WXT, его
  `ContentScriptContext`) плюс наша `composeTab`. Разбор и компиляция файла
  происходят до первой метки и в цифру не входят — настоящая цена ещё чуть
  выше.

  «От отрисовки до следующего кадра» (было в прошлой версии таблицы) убрано:
  без окна это ожидание кадра (0,02–15 мс), а не наша работа.

  Список простой, без виртуализации: настоящие длинные списки будут
  виртуальными (не больше 150 строк в DOM, §10.1, пакет R13).

  **Вывод по бюджету 3 мс.** Повторные загрузки укладываются с запасом в 2 раза,
  первый запуск — нет, уже на Mac; на winpc будет медленнее. Почти всё время —
  верхний уровень бандла, не наша функция. Задача для R09 (до базовой линии на
  winpc): убрать из раннего старта создание схем и всё, что не нужно до
  появления поля ввода, и снова замерить первый запуск. e2e проверяет повторные
  загрузки (медиана ≤ 3 мс, максимум ≤ 16 мс) и записывает первый запуск в
  `.cache/e2e/spike-m0.json`; порог на первый запуск ставить рано — по одному
  замеру на прогон.

  **Найдено в R09 (отдельная правка корня композиции, на решение интегратора).**
  Причина оказалась не в наших схемах, а в первом обращении к API расширения:
  первое касание `browser.runtime` в новом документе стоит ~3 мс на холодную
  (0,35 мс потом). Его делал контекст content script'а WXT ещё при загрузке бандла:
  пустой content script с этим контекстом — 5,2 мс при первом запуске, без него —
  0,02 мс. Ещё ~1 мс на каждой загрузке давали схемы zod раннего пути. Правка:
  контекст WXT для `chatspace` заменён при сборке своей заглушкой
  (`apps/extension/src/composition/content-script-context.ts`), `@cg/platform` и схемы
  грузятся лениво, порт к фону открывается задачей позже. Замер того же e2e: первый
  запуск **0,38 мс** (было 4,46), повторные — медиана 0,34 мс, максимум 0,4 мс (было
  1,99 и 2,32). Следствие: `ctx.onInvalidated` в `tab.ts` больше не срабатывает
  (заглушка его не вызывает) — умершее расширение замечается только по
  `onDisconnect` порта к фону, который теперь открывается задачей позже.
- **Фокус:** клик по полю внутри закрытого корня ставит фокус туда (для

## Проверка 3. Ленивый ESM-чанк в Firefox MV3 — пройдена

- `import('moz-extension://…/lazy/dock.js')` из изолированного скрипта работает.
  Второй чанк (список спайка) берёт Preact из уже загруженного общего чанка —
  Preact грузится один раз.
- В `web_accessible_resources` — только файлы `lazy/`. Чанк спайка есть только в
  тестовой сборке; в выпускной — один чанк дока.
- **Строгий CSP страницы** (`script-src 'self'`, `style-src 'self'`, без inline)
  не мешает ни импорту чанков, ни стилям, ни мосту.
- **Выпускной XPI** ставится временным дополнением в Firefox 157 под своим id
  `chat-extension@gosling.agency`; его popup открывается, а фон отвечает на
  порт вкладки как выпускная сборка (`testBuild: false`). Это отдельный e2e.
- **Вкладка, открытая до переустановки расширения.** Проверяли удалением и
  повторной установкой поверх открытой вкладки:
  1. При удалении Firefox молча убивает старые скрипты: ни события порта, ни
     ошибки. Их DOM (док, оверлей) остаётся на странице мёртвым.
  2. При установке Firefox сам вставляет скрипты манифеста в уже открытую
     вкладку — но поздно, когда документ уже загружен, а не на `document_start`.
  3. Новый экземпляр убирает мёртвые хосты прошлого (сделано в R00) — док
     на странице один.
  4. Тап WebSocket прошлой установки остаётся в странице; новый тап в такую
     вкладку не встаёт (регистрация действует только на новые документы).

  Вывод для R09: «скрипт пришёл поздно» (`readyState` не `loading` при старте)
  = вкладка старше расширения → баннер «ChatGoose обновился — перезагрузите
  вкладку» (UP-009, `CG-RUNTIME-RELOADED`). Настоящее обновление через фид
  проверим на первом выпуске (R19); Firefox обрабатывает его так же, как
  установку, но своими глазами мы это ещё не видели.

## Проверка 4. MAIN на `document_start` и динамическая регистрация — пройдена в пределах одной сессии

- **Мост MAIN из манифеста** стартует, пока документ ещё грузится
  (`readyState = loading`), ставится за 0,02–0,06 мс (бюджет — 1 мс), отдаёт
  изолированному скрипту `MessagePort` через рукопожатие §5.3. Ответы моста
  изолированный мир проверяет схемой `zod/mini`; подделку отбрасывает (тест).
- **Динамическая регистрация** `scripting.registerContentScripts({world: 'MAIN',
  runAt: 'document_start', persistAcrossSessions: true})` в Firefox 157 работает:
  после регистрации тап уже стоит, когда в `<head>` выполняется первый скрипт
  страницы. `new WebSocket(...)` остаётся родным: `instanceof`, прототип и
  статические константы те же, счётчик тапа видит сокет.
- **Чего это не доказывает.** Проверено только внутри одной сессии браузера:
  временное дополнение не переживает перезапуск Firefox, поэтому главное, ради
  чего стоит `persistAcrossSessions` (§6.8 п. 10), — тап на `document_start`
  сразу после перезапуска — ещё не видели. И документ, открытый до того, как
  фон закончил регистрацию (сразу после установки или включения), идёт без тапа:
  тап встаёт только в новые документы. Для R09 это тот же случай, что вкладка
  старше расширения.
- В выпускной сборке тап не регистрируется: флага `wsTap` из bootstrap ещё нет
  (R08), поэтому он выключен. Тестовая сборка регистрирует тап только для
  локального стенда.

## Что сделано не совсем как в architecture.md

1. **«Первый чанк дока» — отдельный ESM-чанк**, который изолированный скрипт
   грузит сразу, как нашёл поле ввода. Сам content script остаётся без UI
   (7,57 КиБ). Так Preact один на док и на все ленивые экраны. В §11 это и так
   две разные строки бюджета; здесь это стало устройством сборки.
2. **Тестовая сборка — отдельное дополнение:** своё имя «… (тест)», свой id
   `chat-extension-test@gosling.agency`, без адреса обновлений. Так она никогда
   не обновится выпуском и не смешает хранилище с ним.
3. **`pnpm build` = `wxt zip -b firefox --mv3`** (внутри та же `wxt build`), чтобы
   у `archive-check` были настоящие XPI и архив исходников для AMO. Сборка
   удаляет архивы прошлых версий своего вида, а `archive-check` и e2e берут
   ровно те архивы, чья версия записана в только что собранном манифесте.
4. **Хоткеи вендорены из того же коммита хаба, что и SDK** (`44b05ad5`, он сейчас
   в проде). Файлы хоткеев там не менялись с `a667c62b`, откуда их брали
   Fansly-расширение и десктоп: sha256 совпадает (`953c6236…`), отличается только
   записанный коммит.
5. **Убираем мёртвые хосты прошлой установки** (`removeStaleHosts`) уже в R00 —
   иначе после переустановки на странице было два дока. Это кусочек R09.
6. **Иконки 48/96/128** — гусь Fansly-расширения с синим значком, чтобы два
   расширения не путались на панели. Окончательный вид — на ваше усмотрение.
7. **`pnpm parity` пока заглушка.** Манифеста паритета нет до R01, поэтому шаг
   только предупреждает — но лишь пока версия контрактов `0.0.0-r00`. R01
   поднимает версию, и с этого момента `pnpm check` без манифеста падает.
8. **Свой жизненный цикл вкладки вместо WXT** (ещё кусочек R09, причина — в
   следующем разделе): вкладка закрывается, только когда расширение
   действительно выгружено.

## Что ещё заметили

- **Страница может «выключить» content script, собранный на WXT.** WXT ждёт на
  `document` событие `CustomEvent` с именем
  `<id расширения>:chatspace:wxt:content-script-started` и по нему считает свой
  скрипт устаревшим. Имя не секрет: id расширения публичный, а WXT ещё и сам
  рассылает это событие на старте. В прошлой версии этого документа путь атаки
  был описан неверно (через `postMessage`): `postMessage` WXT только отправляет,
  а слушает именно `CustomEvent`, поэтому его выключение
  (`noScriptStartedPostMessage`) ничего не закрывает. Проверили на стенде: такое
  событие со страницы убирало док. Это только отказ в работе, без утечки.

  Сделано в R00: вкладка ведёт свой жизненный цикл. Firefox сам убивает скрипты
  удалённого или обновлённого расширения, поэтому настоящий сигнал WXT приходит
  только к экземпляру, у которого уже нет runtime; пока runtime жив, сигнал —
  подделка и игнорируется. e2e шлёт это событие со страницы и проверяет, что док
  на месте. Правило для R09: не полагаться на таймеры и обработчики
  `ContentScriptContext` — после подделки они мертвы.
- `performance.now()` в Firefox по умолчанию огрублён до 1 мс. Для замеров e2e
  включает полную точность; для профиля — Firefox Profiler.

## Что не проверено и почему

| Что | Почему | Когда |
|---|---|---|
