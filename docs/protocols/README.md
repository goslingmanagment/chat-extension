## Схемы: одна стратегия (D-06)

1. **Все схемы контрактов пишутся на `zod/mini`** (zod 4.6.5). Это одни и те же
   классы ядра zod 4, поэтому `safeParse` и `z.infer` одинаково работают в content
   script, на страницах расширения и в фоне. Классический `zod` в фоне остаётся для
   схем вендоренного SDK и внутренних нужд фона, но в `@cg/contracts` его нет: ни
   одна схема контракта не потянет классический zod в content script. DTO хаба
   тоже на `zod/mini`: их разбирают и вкладка, и фон.
2. **Наши границы строгие:** `strictObject`, лишний ключ — отказ. Это мост, протокол
   вкладки, настройки, `UiAction` и тела запросов к хабу.
3. **Ответы хаба — по правилу хаба** (план PR хаба §4.0): объекты нестрогие (новые
   ключи хаба отбрасываются), растущие словари — открытые лексемы, закрытые
   перечисления только у автоматов брони и опеки. Операции, которые уже есть в
   вендоренном SDK, повторяют схемы SDK как есть: SDK проверяет их первым.
4. **Открытые лексемы сужает клиент** (критик п. 14): платформа, роль, флаги, фичи
   страниц, возможности, источники и охват. `narrowPlatform` (неизвестная платформа —
   страница пропускается), `narrowRole` (неизвестная роль → `unknown` с правами
   чаттера), флаг с неизвестным именем — «выключено». В том, что фон отдаёт вкладке,
   неизвестная лексема становится `null` («неизвестно»), например `ServedContext`.
5. **Типы выводятся из схем** (`z.infer`). Интерфейсы с методами (`HostPort`,
   `PreviewSendPort`, `HubFacade`, `AppClient`, порты UI) и типы-объединения входов
   машин написаны на TS. Модели видов — типы TS, а не схемы: контроллер и UI живут
   в одной вкладке, модель не пересекает границу миров. `UiAction` — строгие схемы:
   это вход от UI в контроллер, поддельный клиент проверяет его на лету.
6. **Лёгкое отдельно от тяжёлого.** Конверты и списки типов лежат в лёгких
   модулях, реестры схем — в тяжёлых. Ранний старт изолированного мира импортирует
   только лёгкие (спайк M0: бюджет синхронного старта 3 мс уже под угрозой). Ранний
   бандл — 10,6 КиБ gzip, док — 6,1 КиБ.
7. **Фикстуры:** на каждую экспортированную схему — минимум одна верная и одна
   неверная (`test/fixtures/schemas.ts`, хаб — `test/fixtures/hub.ts`, UI —
   `test/fixtures/vm.ts`); на каждый запрос, ответ и событие обоих протоколов —
   тоже (`test/fixtures/protocols.ts`). Тест падает, если у новой схемы или нового
   типа сообщения нет фикстур. Все id в фикстурах синтетические: реальные id ловит
   `pnpm archive-check`.

## Один словарь: у каждого слова один владелец

Части R01 писались параллельно; при интеграции каждое общее слово оставлено в
одном модуле, остальные его импортируют. Новый код делает так же.

| Слово | Где живёт | Кто пользуется |
|---|---|---|
| платформа, роль, вид хоста, `Target` | `ids` | хаб (`HUB_PLATFORMS`, `HUB_USER_ROLES` — те же списки), протокол вкладки |
| `FeatureId`, `Tone`, фичи со свежим текстом, Split и отправкой | `features` | операции, хаб (`HUB_FEATURE_MAP`, `HUB_REPLY_TONES` = `none` + тоны), UI (`DOCK_ACTION_IDS`, `PREVIEW_ACTION_IDS` = `SENDABLE_FEATURES`) |
| `CgCode`, `CgKind`, `I18nKey` | `errors` | реестр, карта ошибок хаба, причины UI, каталоги |
| `Locale` | `i18n/keys` | настройка `ui.locale` (`system` + локали), порт `I18n`, переводчик core |
| тема, язык, «Вид ответа», авто-рекап Coach | `settings` (`UiTheme`, `UiLocale`, `UiResultStyle`, `CoachAutoRecap`) | модели видов |
| охват, читатель `context_v1`, статус свежего текста | `ops` (`COVERAGE_LEVELS`, `CONTEXT_SOURCES`, `LIVE_TEXT_STATUSES`, `KNOWN_FAN_MESSAGE_STATES`) | хаб, модели видов |
| назначение отправки | `send` (`SendPurposeSchema`) | опека H-7 в хабе |
| периоды доски, отправитель ленты, сегмент Ping | хаб (`HubSpenderPeriod`, `FeedSender`, `PingSegment`) | протокол вкладки, модели видов |

- **UI не держит `Target`.** Модели видов несут непрозрачные хэндлы
  (`TargetHandle`), контроллер сам знает цель; хаб получает `pageLabel` и `fanRef`.
- **Каждый текст — ключ каталога.** `Msg.key`, подписи `ActionCatalog`, причины
  недоступности и `send.reason.*` типизированы `I18nKey`; ключ, которого нет в
  каталоге, не компилируется ни в контрактах, ни в подделках. Тексты живут только
  в `core/domain/i18n`; поддельный `AppClient` строит ошибки через настоящий реестр
  и каталог.

## Мост MAIN ↔ изолированный мир (§5.3)

16 запросов в MAIN (`TO_MAIN_TYPES`; `cancelInsert` — с 1.1.0), 9 сообщений из MAIN
(`FROM_MAIN_TYPES`).

- **Конверт:** `{v: 1, kind, id, t, documentEpoch, seq, payload}`; ответ несёт тот
  же `t`, `ok: true` + `data` или `ok: false` + транспортную ошибку (`BRIDGE_ERRORS`,
  без кода CG; исходы вставки и отправки — это ответы со своими кодами). Ответ
  принимается, только если его `t` совпал с типом ждущего запроса.
- **Пределы кадра:** ≤ 256 КиБ UTF-8 JSON, строка и ключ ≤ 20 000, массив ≤ 1000,
  ключей ≤ 256, глубина ≤ 16; ключи `__proto__`/`constructor`/`prototype`, не-JSON
  значения и не простые объекты — отказ с причиной-счётчиком.
- **Три ступени проверки** всего, что пришло из MAIN: `checkBridgeFrame` (простой
  JSON в пределах) → конверт (`BridgeResponseSchema`, `BridgeEventEnvelopeSchema`)
  → схема полезной нагрузки своего типа (`parseBridgeData`, `FROM_MAIN[t]`).
- **MAIN без зависимостей.** MAIN не импортирует контракты: он проверяет запросы
  руками и повторяет нужные литералы (`host-chatspace/src/main/protocol.ts`), тест
  закрепляет их за контрактами. R09 обязан прогнать фикстуры моста
  (`BRIDGE_REQUEST_FIXTURES`) через ручные проверки MAIN.
- **MAIN не получает данных хаба и токенов** (§14 сильнее эскиза §5.3): в мост
  уходят `InsertWire` и `NavigationWire` (без `cause`) и `MainSendRequest` (без
  привязки, билета хаба и `actionToken`, но со сроком билета `expiresAt`: позже —
  `held`). Токены `insert` и `navigate` `HostPort` тратит запросом `token.redeem`
  до моста.
- **Запись, которая могла выполниться** (тайм-аут, потерянный ответ, `internal`),
  получает исход из `BRIDGE_WRITE_FAILURES`: вставка и отправка — неизвестный исход,
  навигация — `failed` с неизвестной вставкой. Повторно не отправляется, даже с тем
  же id. Отказы из `BRIDGE_ERRORS_BEFORE_EXECUTION` значат «не сделано».
- **Хвост переписки:** снимок моста — до 200 сообщений (`TailSnapshot`), к хабу —
  до 60 (`LiveTextTail`, предел хаба H-4c), с `capturedAt`.

## Протокол вкладки и страниц с фоном (§5.4)

45 запросов (`TAB_REQUESTS`) и 11 событий (`TAB_EVENTS`). Страницы шлют запросы
через `runtime.sendMessage`, события получают по порту `cg-page`. Ошибка ответа —
`kind: 'res'`, `ok: false`, `CgErrorWire` (код и факты): текст ошибки
(`CgErrorView`) строит получатель на текущем языке, язык переключается на лету.

- `tab.register`: фон выдаёт `tabSessionId` (§5.1); `tab.presence` — для звука и
  тостов «AI готово»; `op.reportShown` — телеметрия `shown` (§9.6).
- События фона о данных хаба — лёгкие уведомления (`bootstrap.changed`,
  `catalog.changed`, `newcomers.changed`): данные берутся запросом.
- Запросы данных хаба отвечают DTO хаба (`bootstrap.get`, `catalog.get`,
  `recap.status`, `recap.read`, `spenders.board`, `spenders.stats`,
  `spenders.queue`, `feed.read`, `fan.card`, `fan.dossier`, `newcomers.list`,
  `newcomers.claim`, `usage.get`); `spenders.board` — `SpendersBoard`, сборка фона
  до 1000 строк вместе с корзинами-полками (`tiers`); `spenders.stats` — только
  окно 30 дней, единственное в v1 хаба.
- Источники моделей видов, которых нет у хаба напрямую: `quota.get` и
  `quota.changed` (квота из последнего `meta`), `accounts.seen` (хранилище
  `presence`, его пополняет `tab.presence.accounts`), `journal.read` (журналы
  отладки), хэш SDK и совместимость в `diagnostics.get`.
- `settings.patch` не меняет адрес хаба и отладку: это делает только
  `settings.patchRestricted` со страницы настроек.

**Правила отправителей:**

| Кто | Проверка фона |
|---|---|
| любой | `sender.id === runtime.id`, `sender.frameId === 0`; тип запроса известен и разрешён этому виду отправителя (`TAB_REQUESTS[type].from`) |
| вкладка | происхождение — адрес ChatSpace из `apps/extension/src/hosts.ts` (в тестовой сборке ещё стенд); после `tab.register` каждый запрос несёт свою сессию, фон сверяет её с `sender.tab.id` и документом; данные хаба — только для страниц своей привязки |
| страница | `moz-extension://<свой uuid>/<страница>.html`, страница из `EXTENSION_PAGES`; если у запроса есть `pages` — только с этих страниц |

Пароль идёт только со страниц (`session.signIn`) и нигде не пишется.
`send.*` и `op.start` — только из вкладки: мост MAIN живёт там.

## Решения R01 (часть 1)

1. **id.** Числовые id хоста и платформы (аккаунт OnlyMonster, креатор и фан
   OnlyFans, сообщения) — строки одной формы `^[1-9]\d{0,29}$` (критик п. 14);
   `Number()` к ним не применяем, величина id — не порядок. Наши id (операция,
   попытка, намерение, сессия вкладки, событие) — UUID. Ссылки хаба и ChatSpace
   (`generationRef`, локальный id записи очереди) — непрозрачные `Ref`. Хабовые
   `pageId`/`userId` — целые > 0. `ChatKey` = `хост:аккаунт:фан`.
2. **Деньги — `MoneyMills`:** целое число mills (1 mill = $0,001) в пределах safe
   integer, со знаком — как `mills` хаба на проводе. Ни долларов с дробью, ни
   центов. Деньги AI — целые micro-USD и только в отладке.
3. **`null` = неизвестно, никогда не 0.** Необязательное поле — «не применимо».
4. **Время:** локальные моменты — epoch ms (`createdAt`, `expiresAt`,
   `observedAt`), всё, что уходит из браузера или приходит с хоста и хаба, — ISO
   8601 со смещением.
5. **Ошибка операции на проводе — `CgErrorWire`**; в `OpView` есть `toneUsed`
   (Regenerate повторяет тон).
6. **Метрики `client_health`:** 11 имён с фиксированными границами — девять из
   §5.7 и предложения плана хаба §4.8 (`requestOverheadMs`,
   `composerInputDelayMs`). Смена границ — новая `schemaVersion` метрики.
7. **X8:** таблица переходов `SEND_ATTEMPT_TRANSITIONS` по §6.7.7; новая попытка —
   только после `held` или `notEnqueued` и только по коду, который новый клик может
   снять (`isRetryableEnd`); `uncertain` переходит только в `sentObserved` по поздней
   связанной паре квитанции и эха.
8. **Настройки по умолчанию:** тема `host`, язык `system`, подсказки вкл, «Вид
   ответа» `bare`; Split выкл; окна 100/100/25/3000; Coach — история 10, авто-рекап
   выкл; звуки вкл, тоны как в Fansly-расширении (`chime` и `double`, планка пилота
   X5), громкость 50; отладка выкл.
9. **Коды CG** — полный список прил. А в его порядке; тест сверяет его с
   `docs/architecture.md`.

3. **`SEND_REASON_KEYS`** — код «Отправить» → текст `send.reason.*`; состояние
   `unavailable` принимает только эти коды. После ревью они покрывают все условия
   §6.7.4 и отказы `dispatch` хаба, а строку из попытки и preflight строит одна
   функция `previewSendStateOf`.
4. **`ServedContext` по `context_v1`:** `source` — читатель хаба
   (`archive | union | live_union`, `null` — незнакомый), свежий текст — отдельный
   блок `live` со статусом и счётчиками (поправка §5 плана хаба вместо
   `live-overlay` эскиза архитектуры).
5. **Поддельный `AppClient`** строит ошибки через настоящий реестр и каталог; тест
   целостности сверяет заголовок и пояснение каждой ошибки с каталогом.
6. **Переименование:** статусы приветствия «Новых» — `GREETING_STATUSES`
   (`GREETING_STATES` остаётся за словарём хаба `none | confirmed`).
7. **`CONTRACTS_VERSION = '1.0.0'`:** гейт паритета больше не пропускает
   отсутствие манифеста.

## Решения ревью (до тега)

Ревью R01 нашло пробелы в контрактах; ниже — что решено и почему, сами правки
перечислены в [журнале](../contracts-changelog.md).

1. **Пределы берутся у хаба.** Если наша граница шире тела хаба, клик проходит
   проверку вкладки и падает в фоне `CG-HUB-REQUEST`. Поэтому числа тела AI, входа
   и каталога персон — одни константы в `limits.ts`, их читают и наши схемы, и DTO.
2. **Условие 7 §6.7.4 получило код** `CG-SEND-HISTORY` (в приложении А и в таблице
   условий). Без кода «отправка вызвала бы чтение чата» нечем было показать.
3. **Строка «Отправить» — функция, а не договорённость.** `preparing` — «В очереди
   ChatSpace» (наш замок и `dispatch` до старта нативной отправки), `nativeEnqueued` —
   «Отправляется…» (X8 не встаёт в занятую очередь). Сбой `dispatch` — «Не
   отправлено» с повтором: ничего не дошло до MAIN, фон сообщает опеке
   `failed: not_enqueued`, сам `dispatch` не повторяется.
4. **Отложенная вставка не сравнивает чужой черновик.** До перехода черновик цели
   неизвестен; MAIN читает его после перехода в том же шаге, что и запись, и пишет
   только в пустой или наш. Иначе — подтверждение человека и обычная вставка по
   прочитанной ревизии.
5. **Токены записи по §14.** Вставка и переход тратят свой токен запросом
   `token.redeem` до моста; в MAIN токены по-прежнему не попадают.
6. **`checkpoint` и `preflight` асинхронные** — отступление от эскиза §5.2: счётчики,
   эпоха подписки и условия есть только в MAIN, а мост асинхронный. MAIN снимает
   точку в одном синхронном шаге своего обработчика; сообщение фана между кликом и
   этим шагом считается увиденным до Generate и проверяется обслуженным контекстом.
7. **Набор известных id фана** вместо одного (§6.7.5 «проверяется ограниченный
   набор»): до 10 id, удержание снимается, только если хаб включил все. План хаба
   §4.10.3 предлагал одно поле; H-4b ещё не сделан и берёт DTO из R01.
8. **Части в v1 не редактируются**: в `ui-design.md` нет редактора части. Текст части —
   разобранная часть AI, `textRevision` = 0; редактор — новая версия контракта.
9. **Чек-пойнт в `StartOp` необязателен**, хотя ревью просило обязательный: превью
   должно генерировать и тогда, когда MAIN не дал точки (вставка работает). Такой
   результат не отправляется: фон отказывает `CG-SEND-FRESHNESS`, если точки нет или
   `send.begin` принёс не ту, что была у операции.

**Не принято:**
- **Брендированные id** (`HostAccountId`, `PlatformFanId`…). §5.1 задаёт
  `NativeId = string` и различает пространства именами полей; все пары
  (`{acc, fan}`, `ChatRef`, `Target`) — именованные поля, а не позиции, и `Target`
  проверяет равенство `fanRef` и `chat.platformFanId`. Бренды дали бы только
  проверку типов ценой приведения на каждой границе (MAIN без зависимостей, JSON
  моста, фикстуры). Если владелец захочет их, это версия 2.0.
- **Свой класс повтора `never` для транспортных ошибок маршрута брони.** Класс
  повтора кода говорит, что может повторить человек; новый клик после сбоя
  `dispatch` безопасен — сообщение не ушло. Автоматически не повторяется ни один
  транспортный сбой (единственный автоповтор — `retry-once` у потока AI), это
  записано в `error-map.ts`.
- **Не проверять ответы фона во вкладке.** Схемы на обоих концах ловят расхождение
  сборок; на размер раннего старта это не влияет: реестр протокола грузит только
  код, который обрабатывает трафик.
