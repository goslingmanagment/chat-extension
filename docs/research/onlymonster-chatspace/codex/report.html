OnlyMonster ChatSpace как основа нового расширения

Техническая основа для аналога нашего Fansly-расширения есть. Рекомендую новый клиент поверх ChatSpace с общим ядром функций и отдельными адаптерами платформ. Полный отказ от собственного Electron-клиента возможен после проверки отправки, медиа, фоновой работы и жизненного цикла аккаунтов.

Ответы на три вопроса

1. Аналог Fansly — реализуем

Reply, Fix, Coach, Recap, Review, Ping, Spenders и настройки переносятся на общий продуктовый слой. Голос, загрузчик и «Новые» требуют отдельных адаптеров и испытаний. Стоп-фактора в устройстве веб-клиента не найдено.

2. Собственный десктоп можно заменить

OnlyMonster уже даёт чат, редактор, PPV и медиа. Мы избавляемся от поддержки своего полного интерфейса и Electron-дистрибутива. Взамен зависим от чужого UI, авторизации, прав и ограничений браузера.

3. Новое ядро — разумный выбор

Новую клиентскую реализацию писать с нуля; сохранить Hub, его SDK, общие хоткеи и проверенные правила поведения. Fansly подключить вторым адаптером. Сам переписанный код ещё не гарантирует быстродействие.

Три разных решения: заменить наш Electron; перестать использовать OnlyMonster Browser; отказаться от OFAPI в Hub. Первое выглядит реалистично. Второе не подтверждено для первоначального подключения и повторного входа аккаунтов. Третье требует самостоятельной миграции серверных данных и контрактов.

Практичный первый продукт: чаттер работает в chat.onlymonster.ai, наше расширение читает контекст, показывает AI-инструменты и вставляет проверенный человеком черновик. Сообщение отправляет штатный ChatSpace. Hub продолжает отвечать за AI, доступ к моделям и финансовые данные.

Что проверено непосредственно

Браузер Исследована авторизованная вкладка через Chrome DevTools Protocol. Сохранены только схемы данных, метаданные и результаты измерений. Содержимое переписок, имена, реальные идентификаторы, токены и подписанные ссылки в этот отчёт не включены.

OnlyMonster Browser был запущен на компьютере во время исследования. Его не закрывал и не переподключал аккаунты. Текст/PPV/голос не отправлял, загрузки не запускал, права и настройки не менял, платный AI не вызывал. Публичный API изучен по официальному контракту без создания или использования нового ключа.

Realtime, переподключение и фон

WebSocket работает с подписками на открытые внутри ChatSpace аккаунты. Код снимает подписку при закрытии аккаунта. Расширение не должно считать, что одна открытая вкладка гарантированно наблюдает все модели организации. HTTP и WebSocket имеют разные схемы: например, sent_at против sentAt, platform_metadata против platformMetadata; нужны отдельные нормализаторы.

Клиент переподключается с экспоненциальной задержкой до 30 с и jitter, учитывает offline/online и видимость. При восстановлении инвалидирует HTTP-кеши. Протокола гарантированного replay с последовательным offset в изученном коде не найдено. После обрыва нужно дочитывать историю и удалять дубли по ID.

Уведомления не равны постоянной доставке. Веб-клиент регистрирует notifications-sw.js, но текущий файл содержит только обработчик клика. Web Push указан как TODO. Новое событие обрабатывается живой страницей и затем показывается уведомление. Закрытие/выгрузку вкладки и сон системы нужно считать отдельными режимами отказа. В текущем Chrome разрешение на уведомления было default. Проверенный service worker.

Отправка, редактор и медиа

Штатная очередь отправки последовательна для аккаунта, ограничивает число pending-сообщений в чате и поддерживает ручной повтор. Локальный UUID не передаётся как серверный idempotency key в изученном POST. Подтверждение через WS может сопоставляться по нормализованному тексту. Поэтому поверх неё нельзя добавлять собственные «на всякий случай» повторы: timeout не доказывает, что сообщение не ушло.

Для первого релиза расширение должно вставлять черновик через корректную транзакцию редактора, сохраняя переносы, selection, undo и IME. Прямая запись в innerHTML может рассинхронизировать DOM и состояние Tiptap. Доступная сейчас ссылка .editor — внутренняя деталь, её существование нужно проверять, а при несовместимости отключать вставку с понятной ошибкой.

У нативного клиента есть флаги copied/AI/template и сведения о предыдущем сообщении. Вставка нашей AI-строки сама по себе не гарантирует корректную нативную атрибуцию. В организации активирована настройка Mimic; это не доказывает его работу в конкретном чате, но код запрещает отправку там, где Mimic взял управление. Нужна совместимость с Mimic, переводчиком, шаблонами и хоткеями.

В проверенном uploader ограничение файла — 4 ГиБ; поддерживаются изображения, видео и аудиоформаты. Есть подписанные ссылки, дедупликация и несколько стадий готовности. В отдельном публичном API другой upload/export-процесс; его нельзя подменить внутренним набором вызовов. Для Voice нужна реальная проверка MP3 → штатное вложение → ручная отправка. Для DRM-медиа найдены пути сертификата/лицензии, но воспроизведение защищённого контента не проверялось. Документированный публичный upload-процесс.

Вебхуки: серверная интеграция с оговорками

Документированы сообщения и результаты отправки, события загрузок, Message Guard, новые подписчики, PPV и tips. Подпись — HMAC-SHA256 по timestamp и сырому телу. Повторы ограничены; при устойчивых таймаутах доставка временно приостанавливается, события в паузе теряются. Нужна периодическая сверка с API.

x-om-webhook-id меняется при повторной доставке. Дедупликация должна использовать бизнес-ключ события: ID сообщения/отправки/типса и аккаунт; для upload — ID и updated_at. Обработчик сначала надёжно сохраняет событие, затем быстро отвечает. Событие new_subscriber означает первую подписку и не заменяет учёт продлений/возвратов. PPV/tip timestamps имеют минутную точность и не задают строгий порядок. Официальные правила доставки.

Fansly сейчас не является рабочим ChatSpace-адаптером: в коде разрешён набор onlyfans, telegram_v2, а Fansly отфильтрован и в просмотренной сессии. Документация позиционирует ChatSpace как OnlyFans-интерфейс. Поэтому будущий Fansly-адаптер следует строить для fansly.com, не ждать его появления у OnlyMonster. Поддержка Telegram найдена в коде, но в этой сессии не проверена. Описание ChatSpace, код выбора аккаунтов.

Плюсы и минусы относительно десктопа

Основное сравнение — с нашим Electron ChatGoose поверх OFAPI. Если речь о расширении внутри OnlyMonster Browser, оно дополнительно зависит от возможностей и обновлений этого браузера; его механизм установки здесь не исследован.

У ChatSpace высокая частота релизов: просмотренный changelog содержит множество обновлений за соседние дни, текущая сборка уже v0.167.0. Это усиливает ценность небольшого изолированного адаптера, диагностик несовместимости и предварительного тестирования обновлений. Changelog.

Документированный процесс первоначального подключения аккаунта пока использует OnlyMonster Browser. Рабочий веб-чат не доказывает, что браузер поставщика больше никогда не понадобится для 2FA, истечения сессии или повторного подключения. Подписка OM также не исчезает от смены клиента; фактический тариф и отдельную стоимость API в этой организации не проверял. Подключение аккаунта, Тарифы.

adapters/chatspace   — история, события, редактор, capabilities, media
adapters/fansly      — второй адаптер; добавляется после стабилизации первого
ui                   — панели, настройки, доступность, стили

Это границы ответственности, не требование заранее создавать десятки пакетов. Ядро не должно знать Vue/Pinia/Tiptap OnlyMonster; feature-модули не должны сами обращаться к DOM, токенам и чужим endpoints. Адаптер сообщает поддерживаемые возможности явно: history, draft insertion, voice attachment, follower discovery и другие.

Сохранение состояния операций

Страница и content script живут в разных JS-мирах. Доступ к editor internals требует узкого MAIN-моста; панели и токены Hub должны оставаться в мире расширения. Shadow DOM изолирует стили, но сам по себе не является границей безопасности. Модель Chrome content scripts.

  • Основной источник контекста — структурированные данные. Пассивно использовать ответы и WS страницы. Дочитывать только нужное окно истории; не сканировать весь DOM и не открывать второй WS ради дублирования событий.
  • Привязка к контексту обязательна. Любая операция несёт account + fan + route generation + draft revision. При переключении чата старый ответ может остаться в своём кеше, но не попасть в чужой редактор.
  • Историю объединять по платформенным ID. HTTP и WS нормализуются раздельно; deletion/edit/own echo не создают новые независимые сообщения. ID хранить строками и не смешивать OM ID, raw OF ID, Hub page label и OFAPI acct.
  • Один владелец отправки. На первом этапе — штатный ChatSpace. AI выдаёт черновик; вставка и отправка требуют действий человека. Наш второй send-loop не нужен.
  • Ограниченный кеш. Активное окно + LRU, лимиты объёма и срока жизни; долгую историю не держать сразу во всех вкладках. Финансы и архив — Hub, не локальная копия всего аккаунта.
  • Нормальная деградация. Несовместимый редактор отключает вставку, обрыв данных делает статус unknown, отозванные права закрывают функцию. Никаких тихих подстановок истории другого фана.
  • Без секретов в странице. Hub device token не передаётся через DOM/postMessage. Публичный OM key хранится только серверно через принятую инфраструктуру секретов. В диагностике — версии/коды/длительности, без переписок и signed URLs.

MAIN-мост нельзя считать доверенным только потому, что сообщение пришло из этой вкладки: код сайта способен воспроизвести его протокол. Нужны схемы, ограничения размера, проверка tab/frame/origin, список допустимых действий и серверная проверка доступа к модели. Использованный для исследования DevTools не нужен как permission готового расширения.

Chrome MV3 service worker может завершаться; globals не являются долговечным состоянием. Поток AI, отмену, переподключение UI и оплату повторного запроса нужно проектировать с учётом рестарта. В существующем Fansly manifest — Firefox background scripts, поэтому простая смена host permissions не даст корректную Chrome-сборку. Lifecycle Chrome MV3.

Что переносить, а что переписать

Сохранить серверные feature-контракты, схемы ошибок, AI/accounting, правила Hi/Recap, обработку неизвестного результата отправки, хоткеи и тестовые сценарии регрессий. Клиентский UI, состояние, хранилище и адаптеры можно реализовать заново. Старый Fansly bundle не нужен как фундамент; его текущие правила и опыт эксплуатации нужны как спецификация.

Не следует обещать «идеальный код» или переписывать уже работающий Hub ради эстетики. Качество здесь проверяется изоляцией адаптеров, отсутствием гонок, явными состояниями, измеренной стоимостью расширения и возможностью обновить один адаптер после релиза OM. Минимальный фреймворк не всегда быстрее или дешевле поддержки, чем небольшой компонентный UI; выбор стоит закрепить после профиля первого вертикального сценария.

Главное изменение понадобится в контракте Hub

Наш код В hub/apps/runtime/src/modules/ai/features/index.ts:468 явно запрещён clientContext для всех платформ, кроме Fansly. Комментарий объясняет причину: OnlyFans-контекст собирается сервером, а свободно присланный клиентом transcript/spend позволил бы подделывать данные. Обработка media client-context тоже содержит Fansly-специфику.

Поэтому модель OnlyFans нельзя помечать как Fansly ради обхода проверки. Не следует и просто убрать условие. Нужен отдельный договор о происхождении данных: нормализованное окно сообщений, источник и время получения, покрытие истории, доступ оператора к странице, ограничения размеров и конфликтов. Финансовые значения остаются серверными. Клиентские сообщения полезны для AI, но не должны автоматически становиться авторитетным архивом или основанием финансового учёта.

При возврате нового OM-провайдера нельзя просто оживить исторический код. transactions-writer-gate.ts назначает единственного писателя транзакций для страницы: параллельное начисление одних доходов двумя провайдерами недопустимо.

Как сделать действительно быстро

Самое медленное из уже измеренного — получение истории, а не наша будущая отрисовка. Переписывание UI не сократит ответ сервера с 12 секунд до 100 мс. Нужны reuse данных страницы, кеширование, общие незавершённые запросы, отмена ненужной загрузки и быстрый показ уже известного результата.

Предлагаемый бюджетКак проверять
Первичная загрузка расширения ≤100 КБ gzipБез ленивых Voice/Vault/Followers. Отдельно считать весь загруженный набор модулей; не скрывать перенос веса в следующий чанк.
Открытие уже подготовленной панели: p95 ≤100 мсНа реальном Windows-ПК чаттера; холодный и тёплый сценарии отдельно.
Нет собственных long tasks >50 мсПрофиль с/без расширения, ввод и переключение чатов; обработчики событий короткие, тяжёлая работа разбита.
Добавочный heap в обычном сценарии ≤25 МиБФиксированный набор данных, повторные проходы, cleanup после 100 переключений; абсолютную память Chrome считать отдельно.
Нет постоянного полного DOM-сканирования и polling истории в idleОграниченный MutationObserver, WS/route-события, bounded reconnect reconciliation.
Глубокие функции загружаются по запросуИстория, Voice, vault и followers — с собственной очередью, лимитом и отменой; без параллельного шторма страниц.

Это начальные критерии приёмки, а не достигнутые показатели. Сначала измеряется реальная базовая страница; затем стоимость расширения на том же сценарии. Снижать объём истории ради красивой скорости без явного статуса покрытия нельзя.

Порядок реализации

  1. Один вертикальный сценарий: идентификация модели/фана → подтверждённая история → Hub Reply → показ черновика → безопасная вставка. Одновременно измерить Chrome MV3 и проверить подход к контексту Hub. Отправку испытать только в разрешённом тестовом чате.
  2. Общее ядро функций: Reply/Fix/Coach/Recap/Review/Ping, настройки, hotkeys, Spenders, отмена и кеш. Принимать по поведению и производительности.
  3. Сложные адаптеры: Voice, «Новые», vault; роль чаттера, Mimic и фоновые события. Закрыть матрицу паритета.
  4. Ограниченный рабочий запуск: выбранные модели/операторы, диагностика ошибок без содержимого переписок, сохранённый способ вернуться к десктопу.
  5. Fansly как второй адаптер: переносить те же feature-модули, с отдельными нормализаторами, редактором и discovery. После доказанного паритета выводить прежнее расширение из эксплуатации.
  6. При желании — отдельная миграция провайдера Hub: только после проверки полноты OM Public API, webhook reconciliation, качества архива, атрибуции и цены.
