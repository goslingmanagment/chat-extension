# R20 P16b: долгий прогон на ПК владельца

Это ручная задача агента с проверкой отчёта координатором. P16b остаётся открытым,
пока **480 минут событий** не пройдут все пороги. Пятиминутный smoke проверяет
работоспособность harness и имеет статус `smoke-passed`; строку плана он не закрывает.
Само добавление harness тоже не закрывает строку. Done marker добавляет координатор.

## Перед запуском

- [ ] PR с harness слит; выбрать точный merged SHA. После слияния координатор сначала
  запускает `minutes: 5`, затем при зелёном smoke — `minutes: 480` на том же SHA.
- [ ] Выделить один раннер ПК на всю задачу: `runs-on: [self-hosted, ci-pc]`, как
  [обычный e2e](../../.github/workflows/ci.yml) и [release §2](../release.md).
  Две сессии headless Firefox (испытуемая и база), стенды, fake hub, короткие окна
  профайлера. Восемь часов — окно событий; установка, сборка, подготовка и завершение
  идут дополнительно, общий timeout — 540 минут. Mac этот прогон не выполняет.
- [ ] Не запускать второй долгий прогон одновременно. Workflow ставит такие задачи
  в общую очередь и не отменяет уже идущую. Если обычный CI занял ПК, выбрать свободное
  окно: CPU зависит от соседней нагрузки.
- [ ] Убедиться, что выбран workflow **R20 long run**, а не CI. Единственный trigger —
  `workflow_dispatch`; push, pull request и PR-шарды его не запускают.

Пример для координатора **после merge** (эти команды не являются частью PR):

```sh
gh workflow run long-run.yml --ref main -f ref=<merged-SHA> -f minutes=5
# После проверки smoke artifact:
gh workflow run long-run.yml --ref main -f ref=<тот-же-SHA> -f minutes=480
```

`--ref main` выбирает определение workflow; input `ref` — код под испытанием.
Отчёт хранит и запрошенный ref, и фактически извлечённый SHA. Допустимы только целые
5…480 минут; `CG_LONG_RUN_MINUTES` по умолчанию равен 480.

Workflow использует `tools/ci/e2e-docker.sh long-run`: тот же digest из
`tools/ci/e2e-image.sh`, проверка версий Firefox/geckodriver, headless, временные профили,
`--network none`, только loopback. Установка зависимостей идёт до контейнера.
Авторизация, данные, изображения и тексты — синтетические; секреты не нужны.
При отмене wrapper удаляет контейнер, дополнительный шаг убирает оставшийся.

## Что агент проверяет на стенде

Harness: `packages/testing/e2e/long/long-run.e2e.ts`, отдельный конфиг рядом.
`pnpm long-run` собирает только тестовое расширение и стенды. Обычный `pnpm e2e`
и `CG_E2E_SHARD` перечисляют только `e2e/specs/`; long-run находится вне этого дерева.
Ручной конфиг отказывается работать на macOS и с заданным `CG_E2E_SHARD`, повторов spec нет.

Подготовка выполняет все виды действий один раз до начала окна событий; поэтому
smoke тоже проверяет весь сценарий. Она не входит в 5/480 минут. Все этапы и их время
пишутся в `journal.jsonl`, счётчики успешных этапов — в `report.json`.

- [ ] **Два хоста рядом.** Fansly с FBuddy-подобным соседом `after`, окно 1728 × 936;
  ChatSpace открыт в отдельной вкладке той же сессии расширения. В другом Firefox
  без расширения открыты оба тех же стенда с тем же соседом — база для вычитания.
  Обе сессии получают одни и те же серверные события.
- [ ] **320+ чатов.** Исходные 120 плюс 200 новых через control API fake Fansly.
  Кэш страниц прогревается до нулевого замера. В начале измеряемого окна — полный
  проход typing + входящее по 320 чатам; дальше каждые 10 секунд следующая пара
  событий по кругу. В течение окна — переключения Fansly, переключения ChatSpace
  и Reply через fake hub. Стенд проверяет доставку событий обеим сессиям.
- [ ] **Смена аккаунта.** В подготовке настоящий control стенда меняет creator и его
  session token: основной → другой синтетический creator → основной. Вкладки уходят
  с прежнего документа, fake hub перепривязывает страницу, bootstrap обновляется;
  готовый док обязан назвать новый account id. Модель браузера или отчёт не подменяются.
  Мир fake Fansly при смене пересоздаётся; 320 чатов создаются уже после возврата.
- [ ] **Сон/пробуждение фона.** В подготовке и каждые 15 минут — Firefox
  `terminateBackground` с `runtime.onSuspend` и выгрузкой event page, затем RPC,
  восстановление и готовый док. Это принудительный эквивалент сна event page;
  сон Windows/потеря питания ПК этим не проверяются.
- [ ] **Операции и admission.** В подготовке и раз в 30 минут три AI-заполнения
  заметок удерживаются независимыми SSE gates в трёх чатах. Четвёртая операция
  получает лимит; явная отмена трёх освобождает слоты. Все три слота снова заполняются
  одновременно и освобождаются, затем каждая из трёх новых
  генераций должна закончиться. `diagnostics.ops.active` и потоки fake hub между
  действиями обязаны опустеть.
- [ ] **Проход «Новые».** Открыть из палитры, дождаться проверенного фана,
  поставить очередь на паузу, продолжить и закрыть окно; в подготовке и каждые
  30 минут. Это проверка работы очереди, а не требование прочитать до конца всех
  исторических фоловеров за один цикл.
- [ ] **Приветствия.** Новый фоловер и пустой чат, Hi из настоящего дока через SDK
  и fake hub, готовый текст, затем один явный тестовый click через существующий
  P9d send probe. Журнал fake Fansly подтверждает POST/receipt/echo, fake hub —
  `sent` custody. Каждый цикл берёт нового фана. Повторных отправок нет.
- [ ] **Заметки.** AI `notes-fill` проверяется настоящим scheduler. Нативные заметки:
  create → edit → read-back → delete → read-back через TEST-only API probe,
  настоящие allowlist/pacer/transport и fake Fansly. Probe возвращает только ответ
  notes при явном запросе, без session/header. В этой базе панели P11b и UI-send
  P10c ещё нет: harness проверяет эти нижние пути, **не заявляет проверку будущих
  панелей** и не реализует их вместо соседних PR.
- [ ] **Vault и reload.** В подготовке и раз в 30 минут два маленьких файла выбираются
  в настоящей панели и загружаются через форму страницы; нужны завершённый run
  и обе карточки альбома. Возврат в чат, reload Fansly и ChatSpace в обеих сессиях,
  восстановление готовности. Никакой upload через наш HTTP-клиент.

## Замеры и пороги

Метод памяти и профайлер переиспользованы из P3d
(`e2e/perf/fansly/{memory,profiler}.ts`). P16a не требуется для запуска.
МБ здесь — MiB (байты / 1024²), как в исходной perf-пробе. База измеряется в том же
прогоне; старые абсолютные размеры стенда не вычитаются из нового измерения.

| Проверка | PASS | FAIL |
|---|---|---|
| Длительность | Полное заданное окно, процесс дошёл до завершения | Обрыв, timeout, неполное окно |
| Сценарий | ≥320 разных чатов получили события; ≥320 typing и входящих; каждый обязательный этап прошёл | Нет доставки обеим сессиям или пропущен этап |
| Вкладка Fansly и вкладка ChatSpace после GC | Прирост `explicit` процесса к одновременной базе **≤15 МБ** на каждом замере | >15 МБ; 25 МБ — аварийная граница из спецификации, разрешением PASS она не является |
| Страница фона после GC | Собственный документ background **≤30 МБ** | >30 МБ; пропавший reporter не считается нулём |
| Рост памяти после прогрева | Максимальный прирост к первому замеру того же document epoch **≤5 МБ**, для обоих приростов вкладок и фона | >5 МБ; абсолютные бюджеты действуют и после reload |
| Покрытие памяти | Начало, конец, каждые ≤5 минут; допускается до 6 минут между замерами на действия | Пустая серия, null/NaN, пропуск >6 минут |
| CPU в простое с трафиком | Добавленный CPU к базе: Fansly ≤**210 мс/мин**, фон ≤**500 мс/мин** | Выше минимума собственного бюджета 500 и старого P3d: вкладка 210, фон 833 мс/мин |
| Таймеры кода расширения в простое | **0** во вкладке и фоне | Любой callback таймера; старое P3d: 328–330 / 7 в минуту |
| Пробуждения главного потока процесса расширений | ≤**10 439/мин**, как нижняя граница старого P3d с соседом | Выше P3d или нет показаний |
| Операции / admission | **0** зависших операций и открытых/uncertain отправок между действиями; новый start после освобождения слотов проходит | Операция не завершилась за 30 с, занятый после отмены слот, живой поток после дренирования |
| Отправки | Ровно столько POST и записанных сообщений, сколько тестовых clicks, уникальные requestId и groupId; **дубликатов 0** | Лишний POST, повтор requestId или приветствие той же группе, нет messageId/receipt/echo |
| Ошибки и сеть | **0** неожиданных errors, нарушений схем/FS-NET-1, чужих вызовов ChatSpace, запросов вне стенда и дыр в серверных журналах | Любое из перечисленного; артефакт отсутствует — доказательства PASS нет |

Рост считается **внутри жизни документа**: reload/снова открытый маршрут начинает
новый epoch. Это не измерение непрерывно живущей восемь часов вкладки без reload.
Сырые `explicit`, память realm, размеры процессов и document breakdown сохраняются
рядом с парными замерами; сам процесс расширений не подменяет бюджет страницы фона.

В начале и конце окна — по 30 секунд CPU **без** профайлера и по 30 секунд Firefox
Profiler (как P3d, но короче; нормализация к минуте есть в JSON). Фоновый трафик не
останавливается. Профайлер не работает восемь часов. Сохранены gzipped профили,
числа по таймерам/пробуждениям и исходные CPU delta обеих сессий. Пороги P3d —
историческая справка с Mac/Docker, а не новый одновременный замер старого расширения
на ПК: [база и её ограничения](baseline.md). Пограничный CPU при загрузке ПК требует
разбора профиля; автоматически повысить порог или переписать отчёт нельзя.

Ошибки собираются из BiDi browser log, экспорта журнала расширения, ответов fake hub,
fake Fansly и egress sink. Ожидаемые сообщения `CG-OP-INTERRUPTED` при принудительном
сне сохраняются для проверки; предупреждения тоже сохраняются. Внешняя сеть
физически недоступна внутри контейнера. Это проверка синтетического Firefox MV3,
не доказательство поведения живого Fansly/настоящего FBuddy и не проверка Chrome.

## Отчёт и решение координатора

- [ ] Скачать Actions artifact `r20-long-run-<minutes>m-<run-id>-<attempt>`.
  Внутри `.cache/e2e/long-run/`: `report.json`, `summary.md`, потоковый `journal.jsonl`,
  `idle-0.json.gz`, `idle-1.json.gz` и синтетические файлы vault; рядом WDIO/geckodriver logs.
  Краткая записка есть и в Actions Job Summary. Retention — 14 дней.
- [ ] Сверить SHA, образ, длительность и отсутствие ошибок; просмотреть warnings,
  сравнение памяти, рост по epochs, CPU и таймеры. Отчёт обновляется атомарно по ходу
  работы, поэтому отменённый run оставляет последний `incomplete` snapshot. Отсутствие
  финального `passed` нельзя трактовать как успех даже при зелёных старых числах.
- [ ] Для smoke нужны зелёная job и `smoke-passed`; P16b остаётся открытым.
  Для P16b нужны зелёная job, `status: passed`, `minutes: 480`, `rowComplete: true`
  и проверенный координатором полный артефакт. Сохранить ссылку на run/artifact и SHA
  в датированной записи `docs/releases/`, затем координатор добавляет done marker P16b.
- [ ] Если FAIL: передать координатору конкретный check, SHA, run URL и журнал/профиль.
  Не запускать восемь часов заново до разбора причины; не менять пороги ради зелёного.

Локально исполнитель запускает только unit-тест построителя отчёта и разрешённые
статические проверки. Ни smoke, ни Docker, ни браузеры на Mac для этой задачи не нужны.
