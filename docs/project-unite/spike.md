## 1. Ленивые чанки фона

**Вопрос.** Можно ли грузить `bg/<сайт>.js` через `import(runtime.getURL(…))` из классического event page Firefox, или
нужен `background.type: "module"` с WXT 0.21.4; цена; что бывает при ошибке импорта и перезапуске фона.

**Как.** Тестовое расширение в двух вариантах манифеста (классический фон и `type: "module"`), чанки: пустой, 200 КБ
синтетического кода и настоящий `background.js` сборки 0.2.4 (811 597 Б), обёрнутый в модуль. По пять холодных загрузок
каждого (каждый раз новый адрес, чтобы не попадать в карту модулей), повтор, параллельная загрузка, чанки с ошибками
(нет файла, ошибка исполнения, синтаксис, нет зависимости, падает только при первом исполнении), перезапуск фона
(сон через 3 с по `extensions.background.idle.timeout`, пробуждение сообщением). Отдельно — сборка WXT обоих вариантов на
настоящем исходнике (без браузера).

**Результат.**
- Классический event page принимает `import()` модуля расширения. Сборка WXT 0.21.4 (IIFE) оставляет
  `import(t.runtime.getURL("/bg/fansly.js"))` как есть: `background.js` вырос на 69 Б.
- Холодная загрузка (медиана из пяти, два прогона, классический / модульный фон): пустой чанк — 1,5–3 / 3–6 мс;
  200 КБ — 8–23 / 20–54 мс; 812 КБ — 64–80 / 50–382 мс (большой разброс — нагрузка машины, а не вид фона). Повтор того же
  адреса — 0,1–0,4 мс (карта модулей). Две одновременные загрузки одного адреса — обе успешны за одно время. Первая
  загрузка 812 КБ сразу после пробуждения фона — 95–330 мс.
- Ошибки: нет файла и нет зависимости — `TypeError: error loading dynamically imported module`; синтаксис —
  `SyntaxError`; исключение при исполнении — само исключение. Повтор отсутствующего файла снова идёт за файлом (ошибка
  загрузки не кэшируется). **Ошибка исполнения кэшируется по адресу в этом реалме:** повтор того же адреса за 0,1 мс
  возвращает ту же ошибку, не исполняя модуль; тот же файл по новому адресу (`?retry=1`) исполняется заново. После сна
  и пробуждения фона (новый реалм) всё грузится заново. В консоли браузера ошибок от нас нет — только отклонённый промис.
- `background.type: "module"` в Firefox 156 работает (статический `import` тоже), но WXT 0.21.4 переводит такой фон в
  одну ESM-группу со страницами расширения: `background.js` — 615 КБ плюс два статически подключённых общих чанка со
  страницами (`page-contracts` 185 КБ, `_virtual_wxt-plugins` 32 КБ), нарезку делает `splitPageChunks` страниц, имена
  чанков — с хешами. Динамический `import('…')` в такой сборке сам становится чанком в общей папке `chunks/`.

**Вердикт.** Подтверждено: классический фон + вторая сборка Vite + `import(runtime.getURL(…))`. Модульный фон
отвергнут: байты и состав ядра фона зависели бы от страниц, а строку бюджета «ядро фона» и `archive-check` по одному
файлу пришлось бы переписать.

**Для PR.** F1 строит загрузчик так: повторный старт чанка в том же реалме — по новому адресу (`?attempt=N`), иначе
второй старт после ошибки исполнения молча вернёт ту же ошибку; состояние «сайт не запустился» в «Статусе»; при
следующем пробуждении фона — новая попытка. Цена 200-килобайтного `bg/fansly.js` — десятки миллисекунд на первое
использование после старта фона, на бюджет не влияет. Пробу F1 на настоящем `BackgroundKit` это не отменяет.

## 2. Регистрация рядом с MAIN, обновление, WAR, баннер

**Вопрос.** Порядок изолированного и MAIN-скриптов при регистрации; `persistAcrossSessions`; что после обновления; WAR
Fansly без выданных прав; `executeScript` баннера в уже открытые вкладки.

**Как.** Расширение с `optional_host_permissions` на страницу и API, `optional_permissions: ["webRequest"]`, WAR на
`lazy/*` для страницы. Вкладка Fansly открыта до установки. «Включить Fansly» — доверенный клик по кнопке страницы
расширения, `permissions.request` синхронно в обработчике (запрос прав в тестовом профиле подтверждается без окна:
`extensions.webextOptionalPermissionPrompts = false`). Обновление — переустановка временного дополнения с версией 1.1
(для Firefox это `ADDON_UPGRADE`). Отзыв — `permissions.remove`, затем повторная выдача.

**Результат.**
- `permissions.request` без жеста — «may only be called from a user input handler», и со страницы, и из фона. По клику —
  выдано; `permissions.onAdded` пришёл в работающий фон; `browser.webRequest` появился в нём без перезапуска.
- До выдачи: `permissions.getAll().origins` пуст — WAR на fansly.com права не добавляет; `tabs.query({url: fansly})`
  возвращает **пустой список**; регистрация проходит (адреса не проверяются), но после перезагрузки вкладки скриптов в
  ней нет.
- После выдачи: синхронизация зарегистрировала оба скрипта за 5–76 мс; `tabs.query` вернул вкладку с адресом и
  заголовком без права `tabs`; `executeScript` баннера в вкладку, открытую до выдачи, сработал за 10–230 мс.
- Порядок исполнения — порядок регистрации: `[main, isolated]` одним вызовом → `main, iso, page`; `[isolated, main]` или
  два вызова (сначала изолированный) → `iso, main, page`. Во всех случаях оба скрипта стоят до первого скрипта страницы,
  страница видит `WebSocket.toString()` без имени, то есть наш Proxy.
- `persistAcrossSessions: true` принимается и возвращается `getRegisteredContentScripts()`. Переживает ли регистрация
  перезапуск браузера, на стенде не проверить: временное дополнение удаляется при выходе из браузера.
- Обновление: фон версии 1.1 стартует через 44–119 мс после начала установки (под нагрузкой — 3,7 с), регистраций нет,
  синхронизация на старте возвращает их ещё через 55–140 мс (под нагрузкой — 1,2 с); `onInstalled` — `reason: "update"`.
  Вкладка, загруженная через 0,2–0,55 с после начала установки, скрипты уже получила. В открытой до обновления вкладке
  баннер встал; там осталась старая MAIN-копия (маркер версии 1.0), старый изолированный скрипт мёртв (на события не
  отвечает), но его атрибуты в DOM остались. После перезагрузки — скрипты 1.1.
- Отзыв: `onRemoved` → регистрации сняты за 20 мс → после перезагрузки скриптов нет. Повторная выдача — снова стоят.
- WAR: страница fansly.com **до выдачи прав** получает файл из WAR (`fetch` — 200, `<script>` грузится); файл вне WAR —
  отказ. `import()` из изолированного мира грузит файл из WAR за 1–62 мс, файл вне WAR — отказ.
- Сбой гонки: команда регистрации, совпавшая со стартовой синхронизацией после пробуждения фона, упала с «Content
  script with id "fansly-main" is already registered». После того как обе пошли одна за другой, сбоев нет.

**Вердикт.** Подтверждено с уточнениями (правки в §4).

**Для PR.** P9a: регистрировать одним вызовом `[fansly-main, fansly]`; все изменения регистраций (старт, `onAdded`,
`onRemoved`, переключатель) — строго по очереди; счёт «ждут перезагрузки» возможен только после выдачи прав;
`fansly-notice.js` нужен — старая копия MAIN в открытой вкладке живёт без партнёра. P7g: изолированный скрипт старой
версии после обновления мёртв, но его узлы остаются — уборку делает баннер. WAR на fansly.com — поверхность отпечатка
(UUID расширения случайный на установку), не данных; держать в WAR только то, что нужно вкладке.

## 3. Предикат жеста (А7)

**Вопрос.** Работает ли на geckodriver правило «последнее доверенное событие жеста ещё доставляется
(`eventPhase !== NONE`) в момент нативного `loadstart` XHR».

**Как.** Прототип MAIN (п. 4) стоит на `document_start`. Страница отправляет разными путями (`?s=`), ввод — доверенный
клик указателем и Enter. В каждом сценарии записано: фаза события на `loadstart`, шёл ли `loadstart` внутри `send()`
страницы, вердикт, `fx.sent` в MAIN и в изолированном мире.

**Результат** (оба прогона одинаковы):

| Сценарий | Фаза на `loadstart` | Исход |
|---|---|---|
| клик / Enter, `POST` синхронно | 2 (у цели) | атрибутировано |
| отправка в микрозадаче; три `await` подряд | 2 | атрибутировано |
| слушатель страницы последним (на `window`, всплытие) + микрозадача | 3 (всплытие) | атрибутировано |
| `setTimeout(0)`; `MessageChannel` | 0 (`NONE`) | не атрибутировано |
| отправка с медиа (сначала загрузка, `POST` в её ответе) | загрузка — 2, `POST` — 0 | не атрибутировано (`no-receipt`) |
| смена маршрута в том же событии до `POST` | 2 | не атрибутировано (`route-mismatch`) |
| `ack` до или после `POST` в том же событии | обе — 2 | атрибутировано: квитанция одна |
| два `POST /message` в одном событии | обе — 2 | не атрибутировано (`ambiguous`) |
| два быстрых клика; два быстрых Enter (одна цепочка действий) | у каждого своя — 2 | атрибутированы обе, каждая к своему жесту |
| сосед «проглотил» отправку, затем обычная | первая — `loadstart` нет | первая — ничего, вторая атрибутирована |
| хук соседа на прототипе XHR, обычная отправка | 2 | атрибутировано |
| клик и Enter из скрипта страницы (`isTrusted: false`) | жеста нет | не атрибутировано |
| эхо раньше квитанции; позже; без эха | 2 | `fx.sent` в обоих порядках; без эха — нет |
| смена маршрута после клика при медленном ответе | 2 | атрибутировано к группе жеста |

- `loadstart` во всех случаях шёл внутри `send()` страницы (флаг страницы на нём — `true`).
- Микрозадачи между слушателями и после последнего слушателя исполняются до конца доставки: фаза в них — фаза последнего
  вызова (2 или 3), а не 0.
- «Один кандидат на жест» проверяется, когда закончились все XHR, помеченные этим жестом: их число окончательно уже к
  первому `loadend` — доставка к тому времени закончилась.
- По бандлу: `ack` страницы к отправке — пакет по таймеру 1–3 с (`main:28702-28716`, `:29138-29143`), в событие
  отправки не попадает. Ответ `POST /message` страница превращает в сообщение (`addGroupMessage(new Message(response))`,
  `main:28422-28429`, `:29012-29025`, `:28920-28923`): в нём есть `id`, `groupId`, `senderId`, `content` — всё, что нужно
  квитанции.

**Вердикт.** Подтверждено.

**Для PR.** P7f переносит прототип (`packages/testing/spike/main-proto/gesture.ts`) и эти сценарии в e2e стенда. В
`client_health` добавить счётчик порядка «эхо раньше квитанции / позже» — реальный порядок на Fansly стенд не покажет.
IME (`isComposing`) на geckodriver не проверить — остаётся юнитом.

## 4. Прототип полного MAIN

**Вопрос.** Реален ли один MAIN ≤ 16 КиБ gzip и ≤ 1 мс; сколько стоят кадр и ответ 115 КБ; насколько верен учёт памяти.

**Как.** Прототип `packages/testing/spike/main-proto/` (TypeScript, strict): загрузчик и мост host-kit байт в байт (из
`host-chatspace/src/main/bridge.ts`), Proxy только с `construct` над `WebSocket` и `XMLHttpRequest`, разбор кадров (три
уровня, `t:10001`, пределы, проекции), таблица ответов XHR, отложенная очередь в простое, кольца и тексты с единым учётом,
сертификаты, снимок генерации, жест, `fx.batch` с кредитами, контракт, булевы FBuddy, участники, bfcache. Собран как
вход MAIN у WXT (Vite, IIFE, minify, `firefox142`). Кадры — смесь самой нагруженной страницы (46 % печатания, 30 %
квитанций, 22 % сообщений, подписки), 10 000 через настоящий сокет и по типам в цикле. Ответ `/messaging/groups` —
117 379 Б. Память — отчёт `nsIMemoryReporterManager` по окну после `minimizeMemoryUsage`, разница до и после заполнения.

**Результат.**

| Что | Тихий прогон | Под нагрузкой |
|---|---|---|
| размер, gzip -9 | 8 800 Б (21,6 КБ без сжатия) | — |
| установка на `document_start` (оба Proxy и мост) | 0,28 мс | 7,2 мс |
| кадр, среднее по 10 000 | 4,5 мкс (макс. 2,1 мс) | 9,2 мкс (макс. 9 мс) |
| сообщение 1 КБ / 5 КБ | 5,8 / 16,7 мкс | 42 / 91 мкс |
| печатание, квитанция (полный разбор — 0,8–4 мкс) | 1,2–1,4 мкс | 1,5–2,1 мкс |
| ответ 115 КБ: `JSON.parse`, медиана (макс.) | 0,16 (0,5) мс | 0,88 (15) мс |
| ответ 115 КБ: наш разбор с обходом, медиана (макс.) | 0,18 (0,84) мс | 1,7 (20) мс |
| ответ вне таблицы — «не наш» | 0,7–1,1 мкс | 2,8–5,2 мкс |
| снимок: шаг MAIN / клик → ответ в изолированном мире | 0,02–0,74 / 1,3–19 мс | 0,3–5,7 / 5–49 мс |
| снимок с тремя ответами по 115 КБ в очереди | 0,74 / 13 мс | 3,4 / 15 мс |

- Мост: 10 000 кадров дали 2 405 событий в 19–22 пачках — не больше одной отправки на вызов слушателя. Потребитель без
  подтверждений: 8 пачек в пути, очередь растёт до предела, одно `fx.gap`, после него удержано 1 КБ — память ограничена.
- Память (одинаково в обоих прогонах):

| Что | Факт | Оценка прототипа |
|---|---|---|
| запись кольца, объект на запись | 167 Б (36 000 записей — 6,0 МБ) | 200 Б |
| запись кольца, компактно (id строкой, остальное в типизированных массивах) | 33 Б (36 000 — 1,18 МБ, из них 1,16 МБ — строки id) | — |
| текст 150 знаков латиницей | 220 Б (≈ 1,5 Б на знак) | 340 Б |

**Для PR.** P7b: кольца — компактной раскладкой (id строкой, время, тип и флаги — в типизированных массивах на чат), тогда
потолок 300 × 120 ≈ 1,2 МБ; оценка — 40 Б на запись, `64 + 2 × длина` на текст (кириллица — точно, латиница — с запасом).

(`frameParseMs`, `xhrParseMs`, `snapshotMs`) покажут реальные числа в пилоте.

## 5. `webRequest`: запросы другого расширения из той же вкладки

**Вопрос.** Как запросы скрипта другого расширения в той же вкладке выглядят в `webRequest` (`originUrl`, `documentUrl`,
`tabId`), приходит ли `onCompleted` для чужого 429 — и можно ли по этому держать предикат шаблона «только запрос
страницы».

**Как.** Наш фон с `webRequest` (`onBeforeSendHeaders` с `requestHeaders`, `onCompleted`, `onErrorOccurred`) на
`apiv3.fansly.test`. Во вкладке чата — запросы страницы и двух соседей (MV2 и MV3): `fetch` и XHR из контент-скрипта,
`content.fetch` (у MV2), запрос из фона соседа; поддельный API отвечает соседям 429, странице — 429 по команде. Отдельно —
запрос нашего фона.

**Результат.**

| Кто | `tabId` | `frameId` | `originUrl` / `documentUrl` | `Origin` | Видно в `webRequest` | 429 в `onCompleted` |
|---|---|---|---|---|---|---|
| страница (XHR) | вкладка | 0 | адрес страницы | страница | да | да |
| сосед MV3, контент-скрипт, `fetch` и XHR | вкладка | 0 | адрес страницы | страница | да | да |
| сосед MV2, контент-скрипт, `fetch` и XHR | −1 | −1 | нет | нет | да | да |
| сосед MV2, `content.fetch` | вкладка | 0 | адрес страницы | страница | да | да |
| фон соседа | — | — | — | — | **нет** | нет |
| наш фон | −1 | 0 | `moz-extension://<наш UUID>/_generated_background_page.html` | нет | да | да |

- Запрос соседа на MV3 отличается от запроса страницы только значениями заголовков (у нас — подставной `authorization`
  соседа). У всех `cookieStoreId: firefox-default`, `thirdParty: false`.
- Слушатель, добавленный в работающий фон по `onAdded`, после сна фона запрос страницы **не будит и не получает**.
  После следующего старта фона (слушатель поставлен синхронно на верхнем уровне) запрос страницы будит спящий фон и
  доставляется (`onBeforeSendHeaders` и `onCompleted`). Это подтверждает допущение §8.2 на стенде, на временном
  дополнении.
- Побочно: фон MV3 по умолчанию несёт CSP `upgrade-insecure-requests` — его `fetch` на `http://` не loopback-имени
  поднимается до `https` и падает. Для стенда P6a это значит: API Fansly на `localhost`/`127.0.0.1` или с TLS.

**Вердикт.** Частично опровергнуто: «не скрипт другого расширения» по полям `webRequest` не различить, если сосед на MV3
(или зовёт `content.fetch`). Чужой 429 `onCompleted` видит всегда, но у контент-скрипта MV2 он без вкладки.

**Для PR.** §8.2 и P9a: заголовки попадают в шаблон только после ответа 2xx на тот же запрос (`requestId`): устаревший
повтор соседа, который сервер отверг, шаблон не портит, принятый сервером — законный шаблон сессии этой вкладки. Свой
запрос узнаётся по `originUrl` своей страницы (фон, relay). 429 с `tabId −1` и чужим `originUrl` (или без него) —
охлаждение на всех креаторов профиля. P3b: какой манифест у сборки FBuddy для Firefox у чаттеров — от этого зависит,
какие его запросы мы видим как запросы страницы.

## 6. `navigation.currententrychange` в изолированном мире

## 7. Ответы `POST /vault/albums/media` и `POST /group/<id>/` (по коду бандла)

- **`POST /vault/albums/media {albumId, mediaIds}`** (`main:30320-30326`). Обе точки вызова (`addSelectedToAlbum`,
  `addMediaIdsToAlbum`, `main:12803-12827`) проверяют только отсутствие ошибки, то есть `success`; тело ответа не читается

  уникален: соседи — `/vault/albums/media/delete` и `/rename`; `GET /vault/albums/media` в бандле нет. Форма ответа по
  бандлу неизвестна.
- **`POST /group/<id>/ {groupId, groupUsers}`** (`addGroupUsers`, `main:28340-28346`) — добавить участников группового
  чата. Страница берёт из ответа только `response.users` и у каждого — `userId` (`main:28890-28904`). Тот же адрес у

**Вердикт.** Изменение: `fx.vaultAdded {albumId, mediaIds}` из ответа не собрать.

**Для PR.** P13a: подтверждение — один успешный `POST` ровно `/vault/albums/media` после передачи файла (файл на
`change`), альбом — из контрольной точки, плюс адрес перезагрузки альбома. P7a: ответ `/group/<id>/` — группа, только если
`id` совпадает, `type` — число и `users` — массив; неполный ответ знание о группе не понижает. Правки — §5.4, §6, §7.11.
