день перехода (сейчас 2.10.1, `fansly-chat` `ff30d00`) и пилотные функции ChatSpace, которые новое расширение несёт и на
Fansly, — получает требование `spec.md`, **один** PR-владелец из `plan.md` (версия 8) и проверку на Fansly или
исключение владельца. Планка — X34: новое ни в чём не хуже старого; сравнение — по существу (откуда данные, насколько
свежие, сколько шагов), а не по названиям строк (§3).

слит и остаётся. P12b1–P12c — после пилота; их строки переданы P17, как SP-044…049. Старое выключается в день
перехода, поэтому во время пилота войсов на Fansly нет.

Источники: `docs/parity/parity-checklist.md` и `parity-map.md` (строки и их итог), `spec.md` v7 (`FS-*`), `plan.md` v8,

## 1. Как читать

**Что вошло.** Все строки чек-листа со ссылкой на код старого Fansly-расширения (столбец «Fansly» чек-листа), все строки
с итогом `Fansly` и `пилот + Fansly`, пилотные строки ChatSpace, функция которых есть и на Fansly, новые строки карты
(`NEW-*`, `REC-01`), которые касаются Fansly, и новые строки FX-001…FX-024 — функции старого после 2.7.1 (с этой версии
снят чек-лист) и аватар Hi (§4). Строки, которые Fansly не касаются, — в §9 с причиной, чтобы было видно, что
пропусков нет. Требования `FS-*` без строки паритета — в §8 вместе со всеми остальными.

**Столбцы матрицы** (§7; формат строки фиксирован — его читает гейт P1b):

| Столбец | Что в нём |
|---|---|
| ID | строка чек-листа или карты; FX — новая |
| Откуда | `старое` — функция есть у старого Fansly-расширения; `ChatSpace` — пришла из пилота ChatSpace (десктоп), у старого её нет; `новое` — нет ни у того, ни у другого |
| Требование | `FS-*` из `spec.md`; `как ChatSpace` — общее правило спецификации («всё, что здесь не сказано, — как у ChatSpace»); `spec §1.2` — не в пилоте Fansly; `—` — функции нет по решению (отрицательная проверка) |
| PR | ровно один PR из таблиц этапов `plan.md` v8 — тот, в котором поведение строки на Fansly становится полным и появляется её проверка; e2e фичи — у последнего PR цепочки (`plan.md` §0) |
| Проверка | см. ниже |
| На Fansly | чем поведение на Fansly отличается от старого: откуда данные, свежесть, шаги; пусто — как у старого (или как на ChatSpace для строк `ChatSpace`) |

**Виды проверки.** Тест закрывает строку, только если в его названии есть id строки (`it('[FX-002] …')`), он на своём
хосте и на своём уровне (`plan.md` §0).

| Вид | Что значит | Где тест |
|---|---|---|
| `браузер · <спек>` | e2e на стенде Fansly в headless Firefox | `packages/testing/e2e/specs/<спек>.e2e.ts` (каталог — `plan.md` §3) |
| `браузер · галерея host=fansly` | снимки галереи дока и оверлеев с профилем Fansly в обеих темах (P8d) | e2e галерей с параметром `host` (F5) и меткой `[host:fansly]` |
| `юнит · <где>` | юнит- или интеграционный тест в коде Fansly: `host-fansly`, `fansly-api`, `hosts/fansly` (ядро и интерфейс); `метка fansly` — тест в общем пакете (`platform`, `core/application/pages`, звук, Spenders, контракты) с явной меткой хоста `[host:fansly]` в названии; `гейт` — тест `tools/gates` с той же меткой | путь или метка дают хост (`plan.md` §0) |
| `хаб · эталон в HF-*` | эталон сформированного контекста или правила в PR хаба: клиент этих данных больше не собирает (X4) | репозиторий `hub`, тест с id строки; подтверждение — строка §10 |
| `общий` | код строки не зависит от сайта (страницы расширения, вход, хаб, логи, общие правила ядра): её закрывает тот же тест без хоста, что и на ChatSpace (или тест на Fansly); если такого теста нет, его добавляет PR-владелец | общие пакеты, без метки хоста |
| `отрицательная · NEG-*` | функции нет по решению; проверка из реестра исключений (`packages/contracts/src/parity/exceptions.ts`) идёт и на Fansly | как в реестре |
| `после пилота` | не в пилоте Fansly (`spec.md` §1.2) | P17 |

Пометка ⚑ в столбце «На Fansly» ведёт к предложенному исключению (§5) — исключением строка не становится, пока его не
утвердит владелец; до тех пор её закрывает названная проверка.

**Гейт** (`pnpm parity`, P1b; все виды выше, `общий` и `хаб` — по §6 п. 2). Манифест паритета
(`docs/parity/parity-manifest.json`) выводится из карты паритета, этой матрицы (§7, §9) и реестра исключений: у каждой
строки — план на ChatSpace (пакет работ и проверка по модулю, как раньше) и план на Fansly (`R20/<PR>` и вид
проверки отсюда; строка §9 — без владельца, с причиной). Хост и уровень теста — по `plan.md` §0. PR отмечает себя
сделанным в своём диффе: добавляет `docs/project-unite/done/<PR id>` (например, `done/P7e`), пустой файл или одну
строку пояснения. Id должен быть в таблицах §2 плана, иначе гейт падает. Старые `✓` в `plan.md` сохраняются:
готовыми считаются PR с любой из двух отметок; переносить существующие отметки не нужно. С этой отметкой
каждая строка этого PR должна быть закрыта на Fansly: тестом на хосте Fansly и на её уровне (`общий` — ещё и тестом без
хоста), строкой §10 (`хаб`) или реестром исключений (`отрицательная`); иначе `pnpm parity` падает и называет строку.
Строки PR без отметки — план, не ошибка. Когда отмечен P16c (пилот), открытых строк Fansly быть не может, кроме «после
пилота»; строка «после пилота» у отмеченного PR — ошибка (её проверку называет сам PR). Отчёт по хостам и PR —
`docs/parity/coverage.{json,md}` (`pnpm parity:coverage`). PR не коммитит эти отчёты: координатор обновляет их
на main. Локальный отчёт можно построить для проверки, затем восстановить оба файла до коммита; гейт считает
покрытие по тестам и не проверяет сохранённый отчёт. Изменение §7 или §9 — `node tools/parity/generate.ts`.

Вопросы матрицы координатор решил так; всё ниже внесено в план v8 и в строки матрицы.

1. **Порог Hi в «Новых» (NF-015) — как у старого.** Старое считает личные среди последних 30 прочитанных сообщений

   история, `personalCount` — личные среди её последних 30 сообщений; у вкладки счёт по-прежнему идёт по всей
   доказанной истории (X36 п. 6). Записано в HF-5, P10b1 и архитектуре §5.8.

   этого им нужны искусственные тесты на стенде Fansly.
3. **Свежесть сохранённого имени (AI-146, FX-006) меряет HF-7б.** Старое берёт заметку 12002 при каждой генерации;
   хаб обновляет `page_alias` своей гидрацией фанов (`apps/runtime/src/sync/fansly/lib/fan-hydration.ts` →
   `packages/db/src/repositories/fan-page-identity.ts` на `a3449f77`), то есть правка имени в «Заметках» дойдёт до
   промпта не сразу. HF-7б меряет задержку на проде (только чтение); если она заметна — исключение владельца, или хаб
   перечитывает фана после нашей записи 12002 (новый маршрут хаба), или клиент передаёт сохранённое имя (против
   FS-NOTE-5).
4. **«Открыть в Fansly» из «Новых» (NF-011) — как у старого:** чат открывается в новой вкладке, окно «Новых»
   остаётся открытым. Это поведение P10a, не настройка; «Открыть и вставить» карточки (P10c) остаётся отдельным
   действием.

## 10. Подтверждения хаба

Строку вида `хаб` закрывает тест PR хаба с id строки в названии (`it('[REC-01] …')`) — внешнее подтверждение: в этом
репозитории такого теста нет, а гейт `pnpm parity` хаб не спрашивает (ни одного запроса к сети). Когда PR хаба слит в
`main` хаба, PR расширения, который отмечает его сделанным (файл `done/<PR id>`), пишет сюда по строке на каждую его строку
`хаб`: id строки, PR хаба, путь файла теста в репозитории `hub` с названием теста и коммит `main` хаба, на котором этот
тест есть. Гейт проверяет форму: строка матрицы вида `хаб`, PR — её владелец, в названии теста есть `[ID]`, коммит —
7–40 шестнадцатеричных знаков. Что тест на этом коммите действительно есть и проверяет строку, сверяет тот, кто пишет
строку, и ревью.
