# План: Agency Hub ↔ новое расширение ChatGoose (сведённый)

Дата: 2026-10-02. Источники: планы A (Opus 5.5) и B (astra), раунд сверки обоих,
проверки координатора по коду прода `85392728`. Ответы владельца: OFAPI остаётся
источником хаба; пилот = паритет с Fansly-расширением (без Voice и vault);
свежий текст из ChatSpace в AI-контекст разрешён; в OnlyMonster ничего не пишем,
по умолчанию «тихо».

## 0. Требование владельца к новому клиенту (2026-10-02)

Интерфейс расширения проектируется с нуля, но все функции переносятся: не только
AI-кнопки, но и логирование всего, отладка на фронте (режим отладки: эхо промпта,
профилирование стадий, токены и стоимость, журналы), настройки расширения, popup,
тосты с переходом в настройки по коду ошибки и всё остальное. Функционал — не хуже,
чем у Fansly-расширения и десктопа; исполнение (код, архитектура,
производительность) — лучше и правильнее.

Как это обеспечить: чек-лист паритета собирается из инвентаризаций
[fansly-extension.md](research/onlymonster-chatspace/fansly-extension.md) и [desktop-app.md](research/onlymonster-chatspace/desktop-app.md);
каждая функция либо переносится, либо убирается только с согласия владельца.
Производительность проверяется по бюджетам, снятым с базовой линии на рабочих
машинах чаттеров.

## 1. Вердикт

- **Хаб не переписываем.** Всё, что нужно расширению, в хабе уже есть и работает
  в проде: вход по device token, AI-полоса «контекст собирает хаб» для OnlyFans
  (2 397 завершённых генераций за 28 дней, 0,4 % сбоев), каталог персон,
  `/api/v2/spenders`, авто-листы трат, телеметрия. Переписывание поставило бы под
  удар двух живых клиентов (5 человек за 28 дней) и параллельную работу Sync
  Engine в тех же файлах (`features/index.ts`, `context/index.ts`).
- **Клиент пишем с нуля** в новом репозитории `chat-extension`. Старые клиенты —
  спецификация поведения, а не основа кода.
- **В хабе:** один срочный фикс безопасности, переделка проверки совместимости
  контрактов и набор аддитивных изменений за флагами. Старые клиенты не должны
  заметить ни одного изменения, кроме фикса безопасности.

## 3. Изменения хаба

### 3.0. Фикс безопасности: персоны и сырой AI-шлюз (сейчас, отдельной задачей)

- Полный текст персон, их запись и архивация, сырой `POST /api/v1/ai/gateway/stream`
  — только владельцу. Для всех device-токенов чаттеров, включая старые.
  Каталог персон без текста (`persona-catalog`) и AI-фичи работают как раньше.
- Одним изменением: закрыть для device-токенов старые маршруты (полный текст,
  `PUT`, `DELETE`) и сырой шлюз и в нём же включить правку персон из кабинета
  владельца (owner-session, проверка версий, аудит). Код держит кабинет
  выключенным именно до закрытия старой записи, чтобы не было двух полос записи
  (`modules/ai/index.ts:54-62`). Сразу после выкладки проверить, что владелец
  может править. Сейчас персоны меняются только через старый `PUT`.
- Перед закрытием сверить реальные вызовы в коде и версиях обоих клиентов
  (в коде вызовов нет: у десктопа есть только обёртка `streamAiGateway` в
  `packages/shared/src/hub/client.ts:472, 746`, её вызывают лишь тесты).
- Это ужесточение доступа, а не аддитивное изменение: описать его явно.

### 3.1. Совместимость контрактов (фаза 0)

- В CI хаба — набор совместимости: SDK всех выпущенных клиентов в замороженном виде
  (реестр по `contractHash` + `sourceCommit` из их vendor-манифестов) прогоняются
  на кандидате хаба: health, `me`, `pages`, AI-потоки с кадрами, используемые
  чтения, тела ошибок. Красный набор — нет выкладки. Набор ловит и SSE-кадры,
  которых общий хеш не видит.
- В набор входят и кандидаты: SDK готовящегося клиентского выпуска
  регистрируется (артефакт и vendor-метаданные) до релиза.
- В health — новый ключ верхнего уровня `compatibleClientSdks`: собственный
  `contractHash` сборки плюс хеши из реестра, прошедшие набор. `capabilities` не
  трогаем.
- Гейт выпуска клиента: «мой вендоренный хеш есть в `compatibleClientSdks` прода»
  вместо «хеши равны». Порядок выпуска: зарегистрировать SDK-кандидат → прогнать
  старые SDK и кандидата на кандидате хаба → выкатить хаб → выпустить клиент;
  его хеш остаётся в реестре для следующих выкладок хаба. Новый XPI — с первого
  дня; десктоп и Fansly — при своём следующем выпуске (две мелкие правки
  скриптов).
- Новые SSE-кадры выдаются только клиенту, объявившему токен в
  `x-kernel-ai-capabilities` (например `context-v1`).

### 3.2. `GET /api/v1/client/bootstrap` (до пилота)

Одна точка для нового клиента:
- identity пользователя и только разрешённые ему страницы;
- привязки страниц: `pageId`, `label`, `platform`, `platformAccountId`
  (`pages.external_page_id`), `bindingRevision`. Расширение сопоставляет аккаунт
  OnlyMonster по `platform_account_id` точно; при отсутствии или конфликте функция
  недоступна с понятной причиной, без тихого перехода к username. Равенство
  `platform_account_id` и `external_page_id` не проверено: до пилота сверить для
  аккаунтов OM 36408 и 36409. Если не совпадает — владелец задаёт привязку
  «аккаунт OM → страница» в конфиге хаба, bootstrap отдаёт её;
- протокол, возможности, доступность каждой функции с причиной, лимиты;
- аварийные флаги по странице и функции (`insertion`, `freshText`, `newcomers`,
  `spenders`, `sound`), `minVersion`, `configRevision`, срок жизни ответа.
  Источник — effective config с аудитом владельца. Выключенная функция
  отвергается и на сервере.

Плюс вид телеметрии `client_health` (версия хоста и адаптера, результат проверки
контракта хоста, выключенные функции; без текста) и различимые имена клиентов
в `x-client-version` и producer.

### 3.3. Узкий токен для нового расширения (до пилота)

- При выдаче токена новому расширению сервер сохраняет неизменяемый scope.
  Маршруты `/ofapi/read/*`, `/ofapi/commands*`, `/ofapi/media/*` и события для
  него закрыты (403 без `reason`, чтобы клиент не стирал вход). Это дополняет
  роли и доступ к страницам, а не заменяет.
- Старые токены не меняются.
- Честная граница: от человека с паролем, который выпустит обычный токен, это не
  защищает. Защищает от украденного из браузера токена и от ошибки в коде
  расширения: оно не сможет на сервере ни прочитать историю через OFAPI (это
  пометило бы чат прочитанным), ни отправить сообщение.

### 3.4. Свежий текст открытого чата OF (до пилота)

- Новое необязательное поле запроса AI-фичи (рабочее имя `liveTextContext`),
  только для OF-страниц; вместе с `clientContext` — 400.
- **Только Reply, Fix, Hi, Ping.** Для Recap (полного и короткого), Review, Coach,
  Help — 400, а не тихое игнорирование. Список проверяется в `features/index.ts`
  до загрузки контекста.
- Содержимое: тексты, направление, время, platform message id; не больше
  нескольких десятков сообщений (точные лимиты — в bootstrap). Без денег,
  подписки, медиа, HTML, ссылок, токенов.
- В снимок идут только подтверждённые сообщения с числовым id OF. Сообщения с
  `isFromQueue = true` (приветствие, рассылки) и неотправленные (pending/sending)
  не идут: иначе порог Hi закроется для фанов с рассылками в окне, а временный
  id неотправленного сообщения уронит запрос валидацией.
- Слияние: только по platform message id, без нечёткого сопоставления по тексту.
  Тот же id есть в архиве — побеждает архив (разница нормализации HTML и
  `text_plain` конфликтом не считается). Жёсткий конфликт — другое направление
  или id из чужого чата или страницы → 400 `context_conflict`. Tombstone архива
  клиент не воскрешает.
- Клиентский текст может только ужесточить гейт (например, порог Hi), но не
  ослабить.
- Сервер помечает генерацию `contextScope = principal-draft` и пишет в манифест
  `source = client-supplied`, число принятых и отвергнутых сообщений, видел ли
  архив голову. Текст живёт только в ограниченной записи этой генерации. Никогда:
  в архивах, `observations`, деньгах, досье, общих рекапах. `getFreshestUsableRecaps`
  и `getLatestPromptEligibleFanProfile` исключают строки с `contextScope`.
- Кадр `context_v1` (что видел архив, принят ли свежий текст) — только клиенту
  с токеном `context-v1`.
- Включение: фикстуры → проверка на тестовом чате владельца (id сообщений
  ChatSpace совпадают с id OF в архиве хаба; если нет — боевого режима нет) →
  короткий теневой режим как техническая проверка → боевой режим на пилотных
  страницах со старта пилота. Аварийный флаг на страницу.

### 3.5. Recap → досье (до пилота)

- Серверная операция `profile/from-generation {generationRef}`: текст берётся из
  сохранённой генерации, клиент текста не шлёт.
- Проверки: та же страница и фан, `fan-summary` в режиме full, завершена,
  вывод не исчерпан, тот же пользователь, нет `contextScope`. Повтор с тем же
  `generationRef` идемпотентен. Если кадр `done` пришёл раньше записи итога
  генерации, операция возвращает «ещё не готово», и её можно безопасно повторить.
- Старый `PUT` остаётся для старых клиентов.

### 3.6. Глубина Recap (до пилота)

- Для прежних серверных читателей (архив и OF union) потолок 1 500 остаётся;
  для нового OF-протокола полный Recap видит до 3 000, оба потолка управляются
  одной политикой окна. Старый Fansly `clientContext` не меняется: полный Recap
  у него и так до 3 000, короткий — до 300. В проверку обратной совместимости
  входит старый Fansly full Recap на 3 000 сообщений.
- До добавления индексов — планы запросов и p95 на реальных данных. 3 000 —
  верхняя граница, а не обещание полной истории: coverage и фактическое число
  сообщений показываются.

### 3.7. «Новые» на OnlyFans (до пилота, без них паритета нет)

- **Модель чтения `client/audience-new`:** фиксированное окно, стабильный курсор,
  виды событий new / renewed / returning, дата подписки из `subscribeAt`
  (не дата получения уведомления), coverage и unknown. Источники — уже
  собираемые хабом события подписок и аудитории; своих чтений OF у клиента нет.
- **На строку:** сводка переписки из `page_dm_threads` (последнее сообщение фана и
  модели, число сохранённых, coverage); ссылка на шаблон приветствия страницы
  (хаб раз в сутки читает его существующим действием `welcome_message_read`,
  1 кредит на страницу); состояние claim.
- **Claim — отдельный протокол в `client/`, не переделанный Fansly-маршрут:**
  владелец, аренда, явное снятие, явное продление (новая операция; сейчас
  повторный reserve срок не продлевает). Гарантия только одна: два экземпляра
  ChatGoose не предложат и не вставят приветствие одному фану в пределах аренды.
  Родную кнопку отправки claim не блокирует. «Поприветствован» ставится только
  по эхо конкретного сообщения в памяти страницы, а не по любому исходящему
  вебхуку в этот чат. Неопределённая отправка не повторяется.
- **Порог Hi:** отдельная классификация автоматики в хабе для пилота не нужна:
  автоматические сообщения OF в архив сейчас не попадают, и гейт их не считает.
  Защита — правило снимка из 3.4 (`isFromQueue = true` не передаётся).
- **Сосуществование с десктопом:** на пилотных страницах из десктопа не
  приветствуют (операционное правило; с 21.09 десктоп сделал 19 приветствий,
  все — один чаттер).

### 3.8. Без изменений хаба

- **Spenders:** `/api/v2/spenders` (страница, месяц) плюс `pageSpenderAutoLists`
  для тиров. Превью чужих чатов — только из архива хаба.
- **SSE хаба в расширении нет:** входящие — из памяти ChatSpace, новые
  подписчики — опрос `client/audience-new`.
- Каталог персон, статус рекапов, профиль разговора, квоты, ошибки CG-*, хоткеи
  (вендоринг в три клиента с одинаковым sha).

## 4. Расширение: слой работы с хабом

- `background/hub/`: вход по паролю → device token (как у Fansly: FIFO, стирание
  только на `token_revoked`/`token_expired` для того же токена, ответ на старый
  токен не стирает новый вход); bootstrap; поток AI с `context-v1`; свежий текст;
  recap и досье; spenders; «Новые» и claim; телеметрия (`ai_acceptance`,
  `client_health`).
- `hosts/chatspace/`: тонкий мост в контексте страницы (только чтение router,
  Pinia, кэша; вставка через `__omComposerBridge.setText/insertText`; сети нет) и
  изолированная часть (проверка контракта хоста, нормализация открытого чата).
- Каждая операция привязана к hubOrigin, пользователю и эпохе входа, странице и
  привязке, фану, поколению маршрута и ревизии черновика: ответ не вставится в
  чужой чат или поверх изменённого черновика.
- Никогда: `/ofapi/*`, события хаба, полный текст персон, сырой шлюз, свои запросы
  к OnlyMonster, отправка, история неоткрытых чатов.

## 5. Порядок

**Фаза 0 — сейчас, параллельно с каркасом расширения.**
1. Фикс безопасности 3.0.
2. Набор совместимости и `compatibleClientSdks` (3.1); перевендорить SDK обоих
   клиентов с задеплоенного хаба и перевести их гейты.

**Фаза 1 — до пилота.** Хаб выкатывается первым, новые флаги выключены.
- Хаб: 3.2, 3.3, 3.4, 3.5, 3.6, 3.7.
- Расширение: каркас (WXT, Firefox, вход, bootstrap, мост только на чтение,
  проверка контракта, флаги) → Reply, Fix, Hi, Ping, хоткеи, свежий текст →
  Recap полный и короткий, Review, Help, Coach → Spenders → «Новые» и звук.
- Приёмка на тестовом чате владельца; живые отправки — только тест-фану.
- Сверка привязки аккаунтов OM к страницам (3.2).
- Критический путь: «Новые» (3.7) и свежий текст (3.4), а не панель AI.

**Пилот.** Два чаттера десктопа на `lora-of` и `lora-vip-of`. Десктоп остаётся
установленным как путь отката.

**Фаза 2 — Fansly вторым адаптером.** Схема как на OnlyFans (решение владельца 4):
история — хаб, свежий хвост открытого чата — из страницы по контракту 3.4.
Замеры ниже нужны, чтобы убедиться, что истории хаба хватает для Recap, Review
и Coach, которые свежего хвоста не получают. Сравнение строится на структурированных метаданных окна
(id и время головы, упорядоченные id или их хеш, counts), а не на разборе
строк `[HH:MM] Fan:` из старого транскрипта. Старое расширение таких метаданных
не шлёт (`routes.ts:2127-2161`), поэтому источник: собственные чтения нового
Fansly-адаптера (тогда данные появятся после его переноса) либо необязательный
`windowMeta` в `clientContext` и релиз старого расширения, который его шлёт.
Первая миграция может оставить клиентское чтение в изолированном модуле.

**Фаза 3 — вывод десктопа** по критериям (раздел 8). Затем десктопные маршруты
выключаются флагом. Удаление их кода — отдельное решение после инвентаризации
потребителей и разбора неопределённых команд outbox, а не таймер. Перед выводом
проверить покрытие архива без чтений десктопа: свежий текст закрывает текущий
черновик, но не пополняет архив.

**Фаза 4 — вывод старого Fansly-расширения.** Полоса `clientContext` удаляется,
только если выбрано чтение хабом.

## 6. Приёмка (главное)

- Замороженные SDK обоих старых клиентов проходят на кандидате хаба, health
  разбирается без ошибок.
- Токен чаттера получает 403 на чтение и запись полных персон; владелец правит
  персоны из кабинета.
- За часовую сессию расширение делает 0 своих запросов к `*.onlymonster.ai`.
- Пометить тестовый чат непрочитанным, поработать в Spenders, «Новых» и AI на
  другом чате — тестовый чат остаётся непрочитанным.
- После быстрых переключений чата вставка не попадает в чужой чат.
- Свежий текст: сообщение, которого нет в архиве, учитывается; новых строк в
  архивах, `observations`, досье нет; рекап с `contextScope` не подхватывается
  другим пользователем; враждебный снимок получает `context_conflict`.
- «Новые»: продление не считается новой подпиской; два экземпляра не берут один
  claim; Hi доступен фану только с автоматическими сообщениями.
- Полный Recap на новом протоколе видит до 3 000 сообщений; старые запросы
  не изменились, включая Fansly full Recap на 3 000.
- `platform_account_id` аккаунтов OM 36408 и 36409 сверен с `external_page_id`
  (или привязка задана в конфиге).
- Сообщения из очередей и неотправленные в снимок свежего текста не попадают.

## 8. Решения владельца

1. **Фикс безопасности персон — делать сейчас, отдельной задачей.** Сейчас
   персоны меняются только через старый маршрут, открытый любому токену; фикс
   одним изменением закрывает его и включает правку из кабинета владельца.
2. **Свои запросы к OnlyMonster: не нужны ни одной функции паритета.** По
   умолчанию тихо. Вставка через их мост вызывает их же «печатает…» — как при
   наборе руками. Альтернатива — копирование в буфер, медленнее, и ChatSpace
   пометит сообщение `is_copied`.
3. **Свежий текст — только для черновиков** (Reply, Fix, Hi, Ping). Для Recap,
   Review и Coach нужны отдельные личные слоты рекапов; по умолчанию нет.
4. **Кто читает переписку Fansly для AI** — решено владельцем: так же, как на
   OnlyFans. Основную историю собирает хаб (архив ∪ живой оверлей), а свежий
   хвост открытого чата расширение берёт из того, что уже показывает страница
   Fansly, по контракту 3.4 (только для Reply, Fix, Hi, Ping). Отдельных чтений
   истории из браузера ради AI нет. Последнее сообщение — главное, поэтому
   свежий хвост обязателен, а не опционален.
5. **Критерии вывода десктопа:** 10 рабочих дней в расширении у двух чаттеров,
   не меньше 95 % их OF-генераций из расширения за последние 5 дней, ни одного
   P1 (вставка в чужой чат, пометка прочтения, двойное приветствие, отправка без
   человека), пройден чек-лист паритета.
6. **Voice и vault на OnlyFans** — после пилота.
