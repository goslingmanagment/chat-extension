# Выпуск расширения

Выпуск — одна команда, без PR, без заметок и без ручных правок `CHANGELOG.md`.
Прежняя версия этого документа (раннеры, история проверки инструмента, пилотные
чек-листы) — `git show c081f47f:docs/release.md`.

## 1. Как выпустить

Когда свой PR слит и CI `main` на этом коммите зелёный (`pnpm check` и `pnpm e2e`),
в чистом чекауте `main`:

```sh
cd ~/code/1-platform/chat-extension && git switch main && git pull
pnpm release --dry-run     # проверки, версия, заметки и план; ничего не меняет
pnpm release               # patch; или pnpm release minor | major | X.Y.Z
```

Команду запускает агент сам. Локальный `pnpm check`, perf и ручной чек-лист не нужны:
всё это — CI `main`, и команда сама требует его зелёным.

Что делает `pnpm release`, по порядку:

1. **Замок.** Ставит на origin тег `release-lock` (кто, версия, время). Если тег уже есть —
   идёт другой выпуск: команда сразу останавливается и называет, кто и с какого времени.
2. **Версия.** Последний тег `vX.Y.Z` + patch (или что попросили). `apps/extension/package.json`
   в git не поднимается: версия выпуска живёт в тегах.
3. **Проверки** (только чтение): CI `main` на коммите зелёный (и на последнем коммите не
   только с документами), тег свободен, вендоренный SDK из коммита в `main` хаба, прод-хаб
   его принимает (`compatibleClientSdks`), фид отдаёт версию ниже. Красная — выпуска нет.
4. **Что нового** — из коммитов `main` с прошлого тега: в `CHANGELOG.md`, «Что нового»,
   историю и анонс идут `feat`/`fix` и коммиты без префикса (без `docs`, `test`, `ci`,
   `chore`, `refactor`…); в GitHub release — все коммиты.
5. **Сборка.** Версия, `CHANGELOG.md` и страницы `site/` пишутся в дерево только на время
   сборки, `pnpm build`, затем файлы возвращаются как в git.
6. **Подпись AMO** (unlisted, `web-ext sign` с архивом исходников). Подписанный XPI
   сверяется со сборкой и ложится в `.release/<версия>/` с записью выпуска.
7. **Сервер:** XPI и запись → читаются обратно → одной заменой фид → страницы.
8. **Тег** `v<версия>` на коммите выпуска и **GitHub release** с заметками.
9. Замок снимается — и при ошибке тоже.

Анонс чаттерам команда не делает (раздел 5).

## 2. Ключи

Команда сама подхватывает переменные из окружения, а чего нет — из файлов, первый,
где есть значение: `~/.config/agency/secrets.env`, затем
`~/code/1-platform/fansly-chat/.env.deploy`. Печатаются только имена.

| Переменная | Что это |
|---|---|
| `WEB_EXT_API_KEY`, `WEB_EXT_API_SECRET` | ключи API AMO (JWT issuer и secret); получает только `web-ext sign` |
| `CG_RELEASE_SSH`, `CG_RELEASE_REMOTE_DIR` | сервер и папка сайта; по умолчанию `root@152.53.191.242` и `/var/www/ext/chat-extension` |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID` | бот и канал анонсов (только `announce`) |
| `CG_RELEASE_HTTP_TIMEOUT_S` | сколько ждать один ответ сервера при чтении обратно (по умолчанию 120) |

`op://fansly/Mozilla` в 1Password — вход на сайт AMO, а не ключи API (с ним — 401 «Unknown JWT iss»).

## 3. Если выпуск остановился

- **Просто запустить ещё раз.** Подписанное второй раз не подписывается, выложенное не
  выкладывается заново, тег, который не ушёл на origin, ставится снова. Версия та же,
  пока нет её тега.
- **Замок остался от упавшего процесса** — `pnpm release unlock` (только если тот выпуск
  точно мёртв).
- **AMO подписал позже, чем ждал `web-ext`.** Скачать подписанный XPI в кабинете
  разработчика, `pnpm release sign --import <файл.xpi>`, затем `pnpm release <версия>`.
  Пока такая версия не закончена, другую команда не выпустит.
- **Красный CI `main`** чинит тот, кто выпускает: PR с исправлением, потом выпуск.
- `pnpm release status` — что лежит в этом чекауте: теги, сборка, незаконченные версии.

## 4. Откат

Firefox версию не понижает. От быстрого к долгому:

1. **Флаг в хабе** (по странице или главный выключатель) — минуты, без выпуска.
2. **Фид на прошлую версию** — останавливает распространение; кто уже обновился, остаётся
   на новой:
   ```sh
   pnpm release rollback --to <прошлая> --confirm <прошлая>
   ```
   Без `--confirm` команда только печатает план. Страницы обновит следующий выпуск.
3. **Исправление более высокой версией** — обычный выпуск (`git revert` + `pnpm release`).

## 5. Анонс — только по слову владельца

```sh
pnpm release announce --dry-run
pnpm release announce --confirm <версия>      # раз на версию; ещё раз — --again
```

Пост — заметки последнего выпуска. Ответ «indeterminate» значит, что сообщение могло уйти:
сначала посмотреть канал.

## 6. Как обновление доходит до чаттеров

Firefox читает фид `https://ext.gosling-agency.ru/chat-extension/firefox/updates.json`
примерно раз в сутки и ставит новую версию сам; сразу — `about:addons` → «Проверить наличие
обновлений». Открытые вкладки остаются на старом коде и просят перезагрузку. Версия с новым
разрешением не встанет молча — о ней предупредить в анонсе. Минимальный Firefox — 142.

На сервере (`/var/www/ext/chat-extension/`): страницы сайта, `firefox/updates.json`,
`firefox/updates.previous.json`, `firefox/chatgoose-chatspace-<версия>.xpi` и `.json`
(по файлу на версию, не удаляются — нужны для отката). Сайт виден как
`https://chatgoose.gosling-agency.ru/chatspace/`.

## 7. CI

- PR: только джоба `pnpm check` (её требует правило `main`), PR сливается сам по зелёному.
- Push в `main`: `pnpm check` и e2e пятью частями на ПК (`e2e 1/5`…`5/5`, над ними
  `pnpm e2e`); на раннерах GitHub — одной частью. Это и есть гейт выпуска. Правка только
  `docs/`, `site/` и `*.md` в корне e2e не гоняет.
- Где крутится CI (ПК или GitHub) — переменная `CI_POOL`, скилл `ci-pool`.
- `.github/workflows/perf.yml` — `pnpm perf` ночью и вручную; в выпуск не входит.
- e2e у себя, как в CI: `tools/ci/e2e-docker-local.sh` (нужен Docker; одна часть —
  `CG_E2E_SHARD=2/5`). Образ Firefox закреплён по digest в `tools/ci/e2e-image.sh`.
- Подписанные тестовые сборки P3b — `pnpm release test-builds`, `pnpm release sign
  --test-builds --confirm <версия N>` (`docs/project-unite/spike.md`, «P3b: как прогнать»).
