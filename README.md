# chat-extension

Браузерное расширение ChatGoose для чаттеров: AI-ответы, правка черновика,
приветствия, пинги, рекапы, разбор чата, коучинг, доска Spenders, «Новые»,
хоткеи и звук — поверх веб-чата OnlyMonster ChatSpace (`chat.onlymonster.ai`,
OnlyFans), потом и на fansly.com.

После пилота заменяет оба нынешних клиента: десктоп для OnlyFans
(`onlyfans-chat`, Electron) и Fansly-расширение (`fansly-chat`). Пока пилот
не пройден, оба работают как раньше. Весь AI и все данные платформ идут через
Agency Hub (`hub`).

**Статус:** расширение собрано и соединено. Первая живая проверка на настоящем
ChatSpace 0.172.0 с прод-хабом прошла 2026-10-04: мост и контракт хоста, док,
тема, вход с узким токеном, bootstrap, привязка, персоны, Reply со вставкой,
Ping, Review и короткий Recap работают; что она нашла и что из этого исправлено
— [docs/pilot-readiness.md](docs/pilot-readiness.md), «Первая живая проверка».
Пакеты волн 1 и 2 сведены в одну ветку: фон, вкладка
ChatSpace (док, оверлеи, доски, хоткеи, звук, бронь «Новых») и страницы
расширения (popup, настройки с экраном входа, страницы отладки) работают вместе
на стенде против поддельного хаба — см. [«Что уже работает»](#что-уже-работает)
и [«Как собраны вкладка, фон и страницы»](#как-собраны-вкладка-фон-и-страницы).
Общие интерфейсы заморожены (`@cg/contracts` версии 1.15.0): что внутри —
[docs/protocols/README.md](docs/protocols/README.md), правила изменений —
[docs/contracts-changelog.md](docs/contracts-changelog.md). Спайк M0 пройден —
[docs/spike-m0.md](docs/spike-m0.md).

Коммит и хеш контракта вендоренного SDK записаны в
[vendor manifest](vendor/kernel-sdk/kernel-sdk.vendor.json). Через SDK идут все вызовы
хаба: лента архива, статистика Spenders и «ждут ответа», бронь и учёт отправки, «Новые»;
поток AI объявляет `context-v1` и `split-all-v1`. Совместимость с продом проверяет
`pnpm release preflight --online` перед выпуском; что включено на странице, решает
владелец её флагами. Подробно — [«Вендоринг»](#вендоринг). Впереди: отправка из
превью (X8, решает владелец), следующие живые проверки владельца на тестовом чате (X9)
и Fansly (R20). Выпуски и их проверки записаны в Git-тегах и [docs/releases/](docs/releases/),
версия дерева — в [apps/extension/package.json](apps/extension/package.json).
Порядок выпуска — [docs/release.md](docs/release.md). Что
координатор и интеграторы решили без владельца — решение X12 в
[docs/decisions.md](docs/decisions.md).

## Как устроен репозиторий

Монорепозиторий pnpm, TypeScript в строгом режиме, Firefox MV3 (WXT), Preact.

| Папка | Что там |
|---|---|
| `apps/extension` | точки входа, манифест и три корня композиции — фон, вкладка, страницы (`src/composition/`): в них только сборка зависимостей. Ленивые чанки вкладки — `lazy/entries` |
| `packages/contracts` | типы, схемы, реестр ошибок CG, ключи текстов, модели видов. Логики нет |
| `packages/core` | вся логика без DOM, `browser.*` и сети: `domain` (чистые функции), `services` (службы фона), `application` (контроллеры вкладки и страниц) |
| `packages/platform` | единственное место, где трогается `browser.*` |
| `packages/hub` | слой хаба поверх вендоренного SDK; только в фоне |
| `packages/host-kit` | общая механика страницы для любого сайта: загрузчик и мост MAIN, `guard`, клиент моста, наши закрытые хосты и слои, keep-bottom, щуп клавиш (R20 P5). Сайта не знает |
| `packages/host-chatspace` | рантайм и тап ChatSpace в мире страницы и адаптер хоста поверх `host-kit` |
| `packages/ui` | интерфейс на Preact: кит, док, оверлеи, доски, страницы |
| `packages/testing` | стенд ChatSpace, поддельный хаб, e2e. В расширение не попадает |
| `vendor/` | вендоренные `@kernel/sdk` и `@chatgoose/hotkeys` |
| `tools/` | бюджеты размера, гейты, паритет, проверка архивов, запуск dev-профиля, выпуск (`release`), джоба e2e для CI (`ci`) |
| `site/` | страницы сайта расширения: установка, «Как начать», руководство, «Что нового», история версий, «О данных» |
| `.github/workflows/` | CI: `pnpm check` и `pnpm e2e` на готовом PR и на `main` |
| `docs/` | архитектура, вид, протоколы, решения, паритет |

Границы пакетов проверяет `pnpm lint` (ESLint и dependency-cruiser).

## Для разработчика

### Что нужно

- **Node 26** (`.nvmrc`; на Mac владельца 26.7.0). Если какой-то инструмент
  перестанет работать на 26, запасной вариант — Node 24 LTS: в `package.json`
  поменять `engines.node` на `>=24`, в `.nvmrc` — `24`; спайк M0 показал, что
  сейчас это не нужно.
- **pnpm 10.33.1**, поставленный явно: `npm i -g pnpm@10.33.1` (corepack не
  используем — в Node 26 его нет). Версию закрепляет `packageManager`.
- **Firefox 142+** (проверено на 157). Для e2e нужен доступ в интернет один раз:
  WebdriverIO сам скачивает geckodriver. Путь к Firefox можно задать
  переменной `FIREFOX_BIN`.

```sh
pnpm install --frozen-lockfile
```

### Команды

| Команда | Что делает |
|---|---|
| `pnpm check` | всё, что должно быть зелёным перед коммитом, по порядку и до первой ошибки: `typecheck` → `lint` → `test` → `build` → `webext-lint` → `size` → `gates` → `parity` → `archive-check` |
| `pnpm typecheck` | `tsc -b` по всем пакетам (project references) |
| `pnpm lint` | ESLint (граф пакетов, запрещённые глобалы) и dependency-cruiser (граф, циклы, достижимость: `hub` и SDK не достижимы ни из одной точки входа, кроме фона; ядро фона не достигает чанков сайтов и служб одного сайта, чанк сайта — хаба, SDK и `platform`; два сайта: код Fansly импортирует только код Fansly, бандлы ChatSpace и ядро фона до него не достают, у `host-kit`, `host-fansly`, `fansly-api`, кадра relay и чанков фона — свой разрешённый граф, `docs/project-unite/architecture.md` §1.8) |
| `pnpm test` | Vitest: юнит-тесты, тест манифеста (сам собирает обе сборки), проверка вендоринга |
| `pnpm build` | выпускная сборка: `wxt zip -b firefox --mv3` (из корня репозитория) → `apps/extension/.output/firefox-mv3/`, XPI и архив исходников для AMO; архивы прошлых версий удаляет |
| `pnpm build:test` | тестовая сборка (`CG_TEST_HOSTS=1`) → `.output/firefox-mv3-test/` |
| `pnpm webext-lint` | `web-ext lint --self-hosted` по выпускной сборке |
| `pnpm size` | бюджеты размера из architecture.md §11 (gzip); доля `ui/kit` в первом чанке дока (то, что док берёт из кита, с Preact) — не больше 27 КиБ, на код самого дока остаётся не меньше 18 КиБ из 45 (`packages/testing/src/kit/size.test.ts`); настоящий док с тостами и ленивыми частями (Recap и Review, отладка, Coach, шпаргалка, «Развернуть ↗») меряет `packages/testing/src/dock/size.test.ts`: первый чанк ≤ 45 КиБ, каждая ленивая часть ≤ 30 КиБ сверх него. Ленивые чанки самого расширения меряются слоями (`apps/extension/lazy/entries/names.ts`, `LAZY_LAYERS`): то, что грузит каждая вкладка с чатом, — док, схемы моста, протокол, приложение, контроллеры AI, навигация — стоит друг на друге, и каждый слой весит то, что он добавляет к предыдущим; остальные точки входа грузятся по требованию и меряются сверх всех слоёв. Предел прежний: первый чанк дока ≤ 45 КиБ, любой другой слой или чанк ≤ 30 КиБ. Фон меряется без сжатия: ядро `background.js` — до сигнального порога 800 КиБ (строка печатает запас в байтах — число реестра байтов, `docs/project-unite/architecture.md` §3.2), чанк сайта `bg/<сайт>.js` — до своего потолка из реестра хостов. У каждого сайта своя сборка ленивых чанков (`lazy/<сайт>/`, план слоёв — в реестре хостов `apps/extension/src/hosts`), и меряется она сама по себе: строки названы сайтом (`chatspace: …`). Пробы контрактов — общая (`contracts: limits only`) и пробы сайта из его записи реестра |
| `pnpm gates` | статические инварианты: нет `onlymonster.ai` вне списка (строки, шаблоны, регулярки), нет `innerHTML`, `browser.*` только в `platform`, нет слов token/key/API/bearer в текстах UI, очередь отправки только из порта отправки, выпускной манифест и бандл без тестовых адресов, код SDK только в `background.js` (маркеры — имя класса ошибки, заголовки `x-kernel-*`, пути API хаба, хеш контракта — берутся из `vendor/kernel-sdk` при запуске), мост MAIN и тап без API расширения и zod, код вкладки ChatSpace не подписан на `storage.onChanged`. И гейты двух сайтов (`tools/gates/sites.ts`, `docs/project-unite/architecture.md` §1.8): общий код (`core`, `ui`, `hub`) не называет сайт — ни значением `HostKind` / `Platform`, ни сравнением, ни ключом таблицы, — кроме списка долга, где у каждой записи PR-владелец и который может только сокращаться; файлы ChatSpace в выпускной сборке совпадают с закрепами `tools/gates/chatspace-bytes.json` (размер и sha256 — сравнение с `main` без второй сборки), и PR только с файлами Fansly закрепы переписать не может; в файлах ChatSpace нет строк, которые несут только модули Fansly; в бандлах нет полей сборки реестра хостов и строк паритета |
| `pnpm gates:bytes` | переписывает закрепы `tools/gates/chatspace-bytes.json` по выпускной сборке (сначала `pnpm build`) и печатает, какой файл ChatSpace на сколько байт сдвинулся. Нужна только PR, который намеренно меняет общий код: закрепы коммитятся вместе с ним, дельта по строкам реестра байтов называется в PR. PR только с файлами Fansly её не запускает: если `pnpm gates` просит у него новые закрепы, код Fansly протёк в бандл ChatSpace. `--check` ничего не пишет |
| `pnpm parity:coverage` | отчёт: читает метки `[ID]` и `[host:…]` в названиях всех тестов (юнит и e2e) и переписывает [docs/parity/coverage.md](docs/parity/coverage.md) и `coverage.json` — на ChatSpace сколько строк паритета названо в тестах по этапам и по пакетам работ и какие пилотные строки без теста; на Fansly — сколько строк закрыто по видам проверки и по PR-владельцам. В `pnpm check` не входит; `node tools/parity/coverage.ts --check` говорит, устарел ли отчёт. Новый тест называют по строке: `it('[ST-042] …')` |
| `pnpm parity` | манифест паритета `docs/parity/parity-manifest.json`: у каждой строки план на ChatSpace (владелец — пакет работ, проверка) и на Fansly (владелец — PR плана R20 из [матрицы паритета](docs/project-unite/parity-matrix.md), её вид проверки, или причина, почему строка Fansly не касается), у строк «не нужно» / «убрано владельцем» — отрицательная проверка из реестра исключений; манифест должен совпадать с выводом из карты и матрицы (`node tools/parity/generate.ts`). Затем гейт Fansly: у PR, отмеченного сделанным (`✓` в `docs/project-unite/plan.md`), каждая строка закрыта тестом на хосте Fansly и на её уровне, подтверждением хаба или реестром исключений; с отметкой пилота (P16c) открытых строк Fansly нет. Сеть не нужна. Контракты заморожены, поэтому без манифеста — ошибка |
| `pnpm archive-check` | архивы последней сборки (по версии в её манифесте): XPI совпадает с папкой сборки байт в байт; потолок каждого JS-файла — по файлу (ядро фона 800 КиБ, чанк фона сайта — из реестра хостов, остальные 400 КиБ), и чанк фона каждого сайта в XPI есть; в XPI и архиве исходников нет кода/шрифтов/картинок OnlyMonster, реальных id (сверка по sha256) и секретов; в архиве исходников нет стенда и ни один файл не ссылается на то, чего в нём нет |
| `pnpm e2e` | обе сборки + стенд ChatSpace + поддельный хаб + WebdriverIO 9 и geckodriver: Firefox без окна ставит выпускной XPI (id, ответ фона, страница журналов, экран входа и popup — без единого запроса к хабу) и тестовую сборку временными дополнениями. На тестовой сборке: старт скриптов на `document_start` и его время (`spike-m0`), смоук на стенде (`stand-smoke`), расширение целиком — вход, выбор персоны и выход через настоящую страницу настроек в поддельный хаб, bootstrap, привязка, док над полем ввода, тап WS по флагу страницы — он зарегистрирован, хотя общий флаг хаба `false`, и снимается, только когда флаг выключен на всех страницах, — режим совместимости (`integration-m1`), страницы расширения — состояния popup, одна вкладка настроек, нестандартный адрес хаба, «Сохранено ✓» только после ответа фона, ссылка по коду с подсветкой, кнопка popup во вкладке ChatSpace, файлы диагностики, согласие на замеры, страницы отладки (`pages-wiring`), подключённая вкладка — док из своих контроллеров, Reply потоком из поддельного хаба, «Вставить» в поле нужного чата, клавиша через ранний диспетчер, палитра, тема и язык на лету, Recap, Coach и его чип-пресет, Spenders (`tab-wiring`), подключённый фон — три генерации сразу и отказ четвёртой со списком, решения звука по кадрам сокета стенда, команда со страницы расширения во вкладку, выгрузка фона и выход посреди потока, генерация в режиме совместимости (`background-wiring`), жизнь фона под открытой вкладкой — выгрузка по простою, пробуждение, восстановление, рассылка настроек (`lifecycle`); сквозной набор §12 п. 4 на собранном расширении, всё руками (указатель и клавиши): место дока и низ ленты, Б2, Fix и «Вернуть мой текст» (`suite-dock`), 200 быстрых переключений чатов без единой вставки в чужой чат и клики «Вставить», которые обгоняет смена чата, — каждый с отказом (`suite-switches`), превью Spenders и «Открыть и вставить» — успех, таймаут, отмена, свой текст в поле (`suite-preview`), матрица отправки из превью X8 с хабом (`suite-x8`), бронь «Новых» двумя настоящими Firefox (`suite-newcomers`), клавиши перед редактором ChatSpace, в наших закрытых корнях и в раскладке Windows (`suite-keys`), деградация, страница, выключенная владельцем, перезапуски и отказ старта, который фон не принял (`suite-degrade`), отправка человеком — эхо раньше ответа, две записи с одним временем, занятая очередь (`suite-human-send`), целая смена и полный сетевой учёт (`suite-shift`), боковые панели над доком, блок «Отладка», тон в превью одним кликом по капсуле, «Обновить» и S на доске (`suite-panels`), «Онлайн» палитры без открытого чата — наше превью в своём окне, чат не открыт и не прочитан, J/K по списку палитры, Ping, «Отправить» X8 (без открытого чата — недоступна с причиной, при своём открытом чате — уходит), Esc и возврат фокуса (`suite-online`); ### Тестовая сборка

`CG_TEST_HOSTS=1` собирает **другое** дополнение: имя «ChatGoose для ChatSpace
(тест)», id `chat-extension-test@gosling.agency`, без адреса обновлений. Оно
дополнительно работает на `http://127.0.0.1/*` и `http://localhost/*` (стенд и
поддельный хаб) и принимает адрес хаба по `http`. На стенде (и только на нём:
страница с адресом `127.0.0.1` или `localhost`) она пишет отладочный отчёт в
`<html data-cg-spike>` — что ответил мост, зарегистрировалась ли вкладка, что
показывает док (WebDriver не видит внутрь закрытых корней) — и ставит метки
времени в начало и конец обоих скриптов `document_start` (замер раннего
старта: MAIN ≤ 1 мс, изолированный ≤ 3 мс). Там же страница стенда может
попросить придержать вставку на пути к MAIN (`<html data-cg-spike-hold="мс">`,
`composition/tab/probe.ts`): так e2e ставит смену чата между нашей проверкой
чата и проверкой MAIN (`suite-switches`). На настоящем ChatSpace (`pnpm dev`)
ни отчёта, ни меток, ни этой задержки нет. Тап WebSocket тестовая сборка
регистрирует там же, где работают её контент-скрипты, — на ChatSpace и на
стенде (выпускная — только на ChatSpace); в обеих он включается флагом `wsTap`
из bootstrap. Иначе dev-профиль владельца на настоящем ChatSpace не видел бы ни
входящих, ни отправки из превью. Ещё в тестовой сборке есть карта
разработчика для режима совместимости (`dev.compatPageAccounts`, см. «Живые
проверки»). В выпускной сборке ничего этого нет — это проверяют тест манифеста
и `pnpm gates`.

### Что уже работает

Пакеты волн 1 и 2 соединены в работающее расширение. Всё ниже проверено на
стенде против поддельного хаба; на настоящем ChatSpace — ещё нет. Что доказано
сквозными тестами, что ждёт хаба и что владельцу проверить руками —
[docs/pilot-readiness.md](docs/pilot-readiness.md).

- **Фон** (`apps/extension/src/composition/background.ts`): хранилища с
  бюджетами, настройки и рассылка их изменений, вход и хранение токена, слой
  хаба (bootstrap, каталог персон, поток AI), планировщик операций и
  координатор отправки из превью (X8), одноразовые токены действий, логи в
  IndexedDB, очередь телеметрии, диагностика, выключатель тапа WebSocket по
  флагу `wsTap`, звук и бронь «Новых». У каждого из 51 запроса протокола
  вкладки и страниц есть обработчик — это проверяет тест
  (`apps/extension/test/wiring-background.test.ts`). Запрос ждёт, пока фон
  поднимется (не дольше 10 с). Как фон собран — в
  [«Как собраны вкладка, фон и страницы»](#как-собраны-вкладка-фон-и-страницы).
- **Выгрузка фона.** Firefox выгружает фон (event page) через 30 с без
  событий; открытый порт вкладки его не держит. Поэтому зарегистрированная
  вкладка раз в 10 с повторяет по порту свой отчёт присутствия
  (`composition/tab/runtime.ts`, `KEEPALIVE_MS`): пока ChatSpace открыт, фон
  живёт. Без вкладки он выгружается, а новый экземпляр восстанавливает
  настройки, вход, операции (оборванная — `interrupted`), журнал отправок
  (`uncertain`) и очередь телеметрии; свежие bootstrap и каталог из хранилища
  заново не читает. В логе запись о старте называет причину (`install`,
  `update`, `browser-start`, `reload`, `wake`), выгрузка — отдельная запись.
- **Вкладка ChatSpace** (`composition/tab.ts`, `composition/tab/`): на
  `document_start` стартуют адаптер ChatSpace и ранний диспетчер клавиш; через
  один такт — соединение с фоном и регистрация вкладки. Приложение (тексты,
  контроллеры, интерфейс) — ленивые чанки, которые грузятся, когда ChatSpace
  показал поле ввода или человек нажал нашу клавишу. Интерфейс получает данные
  через роутер контроллеров (`packages/core/src/application/router.ts`), и
  каждое действие интерфейса идёт через него же. Как вкладка собрана — в
  [«Как собраны вкладка, фон и страницы»](#как-собраны-вкладка-фон-и-страницы).
- **Токен действия** (вставка, переход, отправка, генерация) вкладка просит у
  фона только пока идёт настоящее действие человека: клик в нашей видимой
  поверхности или нажатие клавиши (хоткей; отправка — только клик)
  (`composition/tab/action-gate.ts`). Действие открывает токены только своего
  вида (Reply — генерацию, «Вставить» — вставку, «Отправить» — отправку) и
  только на 10 с: за это время контроллер успевает спросить фон и хост, а
  чужой вид токена по этому клику получить нельзя. Фон со своей стороны не
  выдаёт токен вставки или перехода, если bootstrap истёк, а хаб не отвечает,
  или если владелец выключил функцию (`composition/background/token-gate.ts`):
  отказ приходит с кодом и причиной, готовые результаты остаются.
- **«Онлайн» палитры** (CS-030, решение X24): в ⌘K группа «Онлайн» — фаны, которых
  ChatSpace сам показывает онлайн (своего опроса нет). Выбор открывает наше превью фана
  в отдельном окне — то же превью, что в Spenders: лента из архива хаба, Reply · Fix ·
  Hi · Ping, «Отправить» (X8) и «Открыть и вставить». Чат в ChatSpace не открывается и
  остаётся непрочитанным. J и K ходят по списку, который показала палитра; Esc
  закрывает окно, фокус возвращается туда, где был.
- **Страницы расширения** (`composition/pages.ts`, [docs/pages.md](docs/pages.md)):
  popup, настройки с восемью разделами, экран входа с чек-листом первого
  запуска, страница промпта и страница журналов. Страница ничего не знает о
  хабе и о ChatSpace — всё идёт запросами к фону. С X32 страницы одеты в
  айдентику агентства (бумага, тушь, Literata и Golos Text, логотип с гусёнком,
  вывод «Готово к смене» на сцене с гусятами), а настройки устроены кабинетом из
  карточек, как у Fansly-расширения; панель в ChatSpace — прежняя (X28).

### Как собраны вкладка, фон и страницы

Три корня композиции: вкладка (`apps/extension/src/composition/tab/`, ленивые
точки входа `apps/extension/lazy/entries/`), фон
(`apps/extension/src/composition/background.ts` и `composition/background/`) и
страницы (`apps/extension/src/composition/pages.ts`).

Как собрана вкладка:

- **Адаптер хоста** (R20, `docs/project-unite/architecture.md` §1.3). Общий
  корень вкладки сайт не называет: вход сайта собирает адаптер хоста и передаёт
  его в `composeTab(env, adapter)` (`composition/tab/adapter.ts`). Ранняя
  половина адаптера лежит в изолированном скрипте сайта: запуск хоста (мост,
  монтирование, тема, `HostPort`), проба клавиш, маршрут по адресу и где
  лежит ленивая сборка сайта. Половина приложения — в его чанке `tab-app`:
  что bootstrap включает в порте хоста (у ChatSpace — часть B,
  `composition/tab/hosts/chatspace/app.ts`). Ранний адаптер ChatSpace
  собирается в `entrypoints/chatspace.content.ts` из стартера
  `@cg/host-chatspace` (`isolated/starter.ts`).
- **Порядок загрузки.** С первым кадром моста — схемы моста (`bridge-validation`).
  С первым полем ввода или нашей клавишей — протокол, приложение, тексты, док,
  контроллеры AI и навигация. Сразу после появления дока — Recap, Review, Coach
  и сборщик здоровья вкладки. Доски (Spenders, превью, «Новые», панель фана)
  — с первым открытием. Каждая поверхность-оверлей — свой чанк, грузится при
  первом показе. Ленивый чанк грузится через `import()` с одним повтором; если
  не загрузился, человек видит `CG-UI-FAILED`, а поверхность закрывается.
- **Поверхности.** Док — в закрытом корне над полем ввода, один на жизнь
  вкладки. Боковые панели (Coach, панель фана) — слой 900; панель кончается там,
  где начинается док (`composition/tab/panel-geometry.ts`), поэтому Send, поле
  ввода ChatSpace и наша полоса остаются свободны. Вкладка Recap панели фана
  сама читает сохранённый Recap, пока открыта
  (`composition/tab/recap-tab.ts`). Окна (Spenders,
  «Новые», палитра, окно превью фана из «Онлайн» палитры, быстрый переход,
  шпаргалка, «Развернуть ↗», вопросы) — 950, тосты — 960. Что открыто, знает одно место — `OverlayState` из R17: по
  нему монтируются оверлеи, его читает диспетчер клавиш, его зеркалит
  `data-dismissible-open` на хостах. У каждой поверхности своя граница ошибок:
  сбой отрисовки показывает «Сбой интерфейса» (`CG-UI-FAILED`) на её месте, а
  «Перезагрузить панель» монтирует её заново.
- **Клавиши.** Ранний диспетчер стоит на `window` в фазе capture с
  `document_start`. Нашу клавишу, нажатую до загрузки ленивой части, он держит
  (последнюю, не дольше 5 с) и выполняет, как только контроллеры готовы; чужие
  не трогает. Удержанный Enter, нажатый в нашем интерфейсе, до ChatSpace не
  доходит: после «Вставить» фокус уходит в поле ввода, и автоповтор клавиши
  иначе отправил бы сообщение.
- **Хост.** Отправка из превью и контрольная точка идут через порт хоста;
  факты «человек отправил» и «пришло входящее» уходят в фон (звук, отметка
  «отправлено» у вставленного из доски текста). Отчёт «человек отправил»
  вкладка повторяет до четырёх раз, если фон в этот момент был недоступен
  (`composition/tab/host-facts.ts`). Профили квитанций для отправки из превью
  берутся из `limits.previewSendReceiptProfiles` в bootstrap.
- **Хранилище.** Вкладка не слушает `storage.onChanged`: запись входа лежит в
  том же `storage.local`, и подписка доставляла бы её в процесс страницы
  ChatSpace. Черновики превью, которые пишет другая вкладка, перечитываются
  при возврате во вкладку (`composition/tab/runtime.ts`, `draftStoreOf`); за
  этим следит `pnpm gates`.
- **Настройки на лету.** Тема (как у ChatSpace / системная / светлая / тёмная),
  язык и «Вид ответа» меняются по событию `settings.changed` без перезагрузки.
  После обновления расширения док показывает «Перезагрузите вкладку»
  (`CG-RUNTIME-RELOADED`).
- **«Настройки» из вкладки.** Контент-скрипт не может открыть страницу
  расширения, поэтому просит фон (`settings.open`): открытая вкладка настроек
  получает фокус и нужный раздел, иначе открывается новая. Так же открывается
  страница промпта по кнопке «Промпт» в режиме отладки (`debug.open`): во
  вкладку попадает только непрозрачный токен снимка, сам промпт читает страница.
  «Выгрузить диагностику» у сломавшейся поверхности ведёт в раздел
  «Диагностика» настроек — файл сохраняет страница расширения.

Как собран фон:

- **Запросы.** Сверх того, что было в каркасе M1: `recap.save` (одна
  идемпотентная запись ссылки досье на готовую генерацию, новой генерации нет),
  `send.list` (попытки отправки этому фану из журнала этой установки),
  `newcomers.claim`, `sound.event` и `sound.preview`, `tab.command`,
  `data.clear`.
- **Бронь «Новых»** (`@cg/core/services`, `GreetingLeases`). Токен брони знает
  только фон: один на фана, тот же для всех вкладок этого браузера, поэтому
  вторая вкладка присоединяется к брони, а не проигрывает самой себе. Продление
  без токена хаб не спрашивает («бронь истекла»). Токены переживают выгрузку
  фона (`storage.session`) и стираются при выходе. Сам фон ничего не продлевает:
  раз в 40 с просит вкладка, пока человек работает с фаном; закрытая вкладка
  перестаёт просить, и бронь истекает на хабе.
- **Отправка человеком после «Открыть и вставить».** Вкладка сообщает
  `op.reportSent` (квитанция и эхо с одним id); если часть была из превью или из
  карточки «Новых», фон регистрирует отправку в хабе (`registerNativeSend`):
  фан считается поприветствованным, часть нельзя отправить второй раз. Это
  отчёт о случившемся, а не отправка. Запрос сначала пишется в `storage.local`
  (`send.native`, `NativeSendRegistrar`), потом шлётся, и повторяется с тем же
  id, пока хаб не ответит: выгрузку фона и обрыв сети он переживает, следующий
  фон находит долг и досылает. Долг привязан к человеку — после выхода под
  чужим входом не шлётся; не больше 200 записей и не дольше 7 дней.
- **Звук** (`composition/background/sound.ts`). Один арбитр на всё расширение
  решает, звучать ли. Факты о входящих приходят из тапа WebSocket любой
  вкладки. Новых подписчиков арбитр узнаёт из двух источников: медленного
  опроса «Новых» раз в минуту, пока открыта хотя бы одна вкладка ChatSpace, и
  списка, который вкладка сама читает раз в 30 с при открытом окне «Новых»;
  страницу, которую только что прочла вкладка, опрос не трогает. Хаб, который
  «Новых» отдать не может, не опрашивается вовсе.
- **Команда со страницы расширения** (`tab.command`). Фон выбирает вкладку
  ChatSpace, выводит её вперёд и передаёт ей команду событием; вкладка
  исполняет её как переход — открыть Spenders, «Новых», шпаргалку или аккаунт.
- **Смена человека.** Вход, выход, другой адрес хаба или другая персона
  страницы отменяют операции, привязанные к прежнему. Выход или другой человек
  ещё и стирают результаты, журналы отладки, локальный счётчик расходов, токены
  брони, базу «уже виденных» подписчиков, черновики превью на диске и события
  телеметрии прежней привязки. Истёкший bootstrap запрещает новые генерации,
  вставки, переходы и отправки, пока хаб не ответит, но результаты не трогает.
- **«Очистить локальные данные»** (`data.clear`): кэши и журналы — готовые
  результаты, журнал, журналы отладки, кэши слоя хаба. Вход, настройки, идущие
  операции и открытые попытки X8 остаются.
- **Обновление.** Фон запоминает, когда и с какой версии обновился, и считает
  вкладки, которым новые скрипты достались поздно (им нужна перезагрузка).
- **Один экземпляр каждой службы.** Дубликаты волны 1 (вторые барьер
  готовности, присутствие вкладок, хранилище снимков промпта) удалены из
  `@cg/core/services`.
- **Хаб без входа не спрашивается.** Связь с хабом для «Статуса» и popup
  читается, только пока кто-то вошёл: без входа страницы её не показывают.
- **Первый запуск.** После настоящей установки фон один раз открывает страницу
  настроек — экран входа с чек-листом. Временная установка (`pnpm dev`, e2e)
  ничего не открывает.

Как собраны страницы:

- **Одна вкладка настроек.** «Настройки» из popup, из дока и из тоста ошибки
  находят уже открытую вкладку и переводят её на нужный раздел; вторая не
  открывается. Раздел, выбранный на самой странице, — запись истории той же
  вкладки, «Назад» возвращает прежний.
- **Ссылка по коду.** `options.html#<раздел>:<КОД>` открывает раздел с плашкой
  «КОД · описание» и на две секунды подсвечивает то, к чему код относится. Код
  без раздела сам находит раздел по реестру ошибок.
- **«Сохранено ✓»** появляется только с ревизией из ответа фона. Пока ответ в
  пути — «Сохраняю…»; фон не ответил — «Не сохранено» с кодом и «Повторить».
- **Доступ и согласие.** Доступ к адресу хаба (в том числе нестандартному) и
  согласие на технические замеры страница запрашивает у браузера сама, внутри
  клика; отказ виден с кодом.
- **Файлы и ссылки.** Диагностика сохраняется через Blob, без права
  `downloads`. «Что нового», «История версий» и «Нужна помощь со входом»
  открывают страницы сайта выпуска в новой вкладке (`apps/extension/src/site.ts`);
  страницы находятся в `site/`, версию и тексты выпуска обновляет `pnpm release site`.
- **Сборка.** Общий бандл страниц режется на три файла — тексты, контракты,
  сами страницы (`apps/extension/build/page-chunks.ts`): одним файлом он не
  проходил проверку архива (JS-файл больше 400 КиБ).

Известные ограничения:

- Хаб бывает старше вендоренного SDK (прод выкладывают позже, чем сливают
  `main`). Поток AI объявляет хабу только то, что назвал его bootstrap: пока хаб
  не объявил `context-v1` и `split-all-v1`, генерация идёт по архиву хаба,
  свежий текст страницы не уходит, Split в Ping, Hi и Coach не запрашивается, а
  у этих функций причина «хаб пока не умеет эту функцию». Когда хаб их объявит,
  всё включится само ([docs/hub-layer.md](docs/hub-layer.md)).
- Факты о входящих сообщениях адаптер ChatSpace отдаёт только из тапа
  WebSocket, а тап включается флагом `wsTap` из bootstrap. Без входа в хаб и на
  вкладке, открытой до входа, звука сообщений нет, пока вкладку не
  перезагрузят.
- Самое первое сообщение в только что открытой вкладке нового профиля может
  не прозвучать: арбитр звучит только для аккаунтов, которые браузер уже видел,
  а вкладка называет свои аккаунты через долю секунды после регистрации.
- На стенде при каждом переключении чата док на 25–30 мс исчезает и ставится
  заново: адаптер ChatSpace в середине переключения не видит активного поля
  ввода и снимает док. На настоящем ChatSpace это не проверено (X9); если
  повторится, док будет мигать при смене чата.
- Открытая страница расширения (настройки, журналы, промпт) фон не будит: после
  выгрузки по простою её порт событий «паркуется» и открывается заново при
  первом действии на странице или возврате на неё. Пока фон спит, страница
  событий не слышит; открывшись заново, она перечитывает настройки и вход.
- Связь вкладки с фоном, оборвавшаяся не из-за обновления, сама не
  восстанавливается: док говорит «Перезагрузите вкладку»
  (`CG-RUNTIME-UNREACHABLE`).
- Popup читает статус при открытии и по «Обновить статус»: пока он открыт,
  смену чата во вкладке он сам не заметит (вход и выход — заметит).
- Страницы показывают «фан <номер>» вместо имени и не знают даты входа
  устройства: фон этого страницам не отдаёт ([docs/pages.md](docs/pages.md)).

Контракты после сведения — одна версия 1.2.0 с одной записью в
[журнале](docs/contracts-changelog.md). Галереи интерфейса на стенде:
`/kit-gallery/`, `/dock-gallery/`, `/boards-gallery/`, `/pages-gallery/`.


### Стенд ChatSpace (R02)

`packages/testing/fixture-chatspace` — наше маленькое приложение на Vue 3 + Pinia +
vue-router + TipTap, которое повторяет **только те контракты** ChatSpace, на которые
опирается расширение (architecture.md §6, §12 п. 3): `#app.__vue_app__`,
маршрут `chat`, сторы `pendingMessages`, `composerTranslator`, `accounts`, `chats`,
кэш `_pc_query` с ключами `chatMessages`, `fansMap`, `chatList` и др., DOM поля ввода
со слотом и `__omComposerBridge`, по полю ввода на вкладку чата (`v-show`), черновики
`chat-space:draft:of:*`, Esc и Alt+S, имена `--color-om-*`, `.dark`, фиксированную
ширину, WebSocket с `authenticated`, `account_new_message` и фоновыми сводками,
нативную отправку через клиент, который берёт `fetch` при создании запроса.

Откуда это взято. Кода, CSS и данных ChatSpace в репозитории нет: код наш, цвета,
тексты и id — свои и синтетические. Но не всё написано только по наблюдаемому
поведению: очередь отправки, HTTP-клиент, кэш запросов, вкладки чатов, сокет,
горячие клавиши, мост поля ввода и черновик своим кодом пересказывают логику,
прочитанную в бандле 0.172.0, потому что расширение опирается именно на неё. Такие
модули помечены `re-expressed` в `fixture-chatspace/src/metadata.ts` (там же, где что
подсмотрено, с номерами строк). Детали, которые видны только в их коде и ничем не
наблюдаются (например, формат запасного id очереди), не переносим. В архив исходников
для AMO стенд не попадает: для сборки XPI он не нужен (приложение, сервер и точка входа
`@cg/testing/stand`, страница спайка, DOM-тесты фикстуры и e2e-обвязка перечислены в
`apps/extension/build/sources-archive.ts`; `pnpm archive-check` падает, если что-то из
них оказалось в архиве). Остаются только tsconfig фикстуры и типы её протокола — без них
не собирается `tsc -b`. В распакованном архиве работают `pnpm install --frozen-lockfile`,
`pnpm typecheck`, `pnpm lint` и `pnpm build` (XPI получается тот же байт в байт); тестов в
нём нет — WXT их не кладёт. `pnpm archive-check` падает и тогда, когда файл архива
импортирует то, чего в архиве нет (`dangling-import`: относительные импорты, экспорты
пакетов рабочей области, `extends` и ссылки tsconfig).

- Сервер стенда (`packages/testing/src/stand-server.ts`) — только 127.0.0.1, на двух
  адресах, как у ChatSpace (страница на `chat.`, API и сокет на основном домене):
  на одном страница, управляющие адреса `/__stand/*` и журнал, на другом её API
  (с CORS) и сокет. В журнале у каждого вызова подписано, кто его сделал: `native`
  (клиент страницы), `control` (тесты), `asset` (переходы и подресурсы страницы),
  `foreign` (всё остальное — то есть расширение, в том числе запрос страницы или
  бандла из скрипта и повтор чужого нативного запроса; должно быть ноль).
- Ответы отправки задаются сценарием: 200 с id и эхо до или после ответа, Message
  Guard, любой статус (401, 403, 5xx), «завис», «оборвал соединение».
- Страница даёт тестам `window.__stand` (протокол — `fixture-chatspace/src/protocol.ts`):
  открыть чат (в новой вкладке), сменить тему, заблокировать фана, включить Mimic,
  переводчик, права, «удержать» наблюдателя кэша, прислать сообщение фана, перезагрузить
  страницу как «новую сборку» без нужных якорей (`?stand-break=…`).
- Обвязка e2e: `e2e/support/stand.ts` (стенд, журнал, поиск активного поля ввода),
  `e2e/support/network-trap.ts` (ловушка: после каждого теста и в конце набора любой
  запрос мимо стенда и поддельного хаба валит тест; журнал BiDi видит страницы и
  контент-скрипты, но не фон расширения, поэтому ловушка читает и приёмник
  `src/stand/egress-sink.ts`, куда профиль шлёт все внешние запросы браузера; свой
  трафик Firefox выключен префами и `MOZ_REMOTE_SETTINGS_DEVTOOLS=1`),
  `e2e/support/visual.ts` (снимки в светлой и тёмной теме
  при 1440×900 и 1280×800 в `.cache/e2e/`), `e2e/support/shift.ts` (смена: тестовая
  сборка, вход, персона, вкладка стенда рядом со страницей расширения),
  `e2e/support/world.ts` (фаны стенда на доске Spenders поддельного хаба, профиль
  квитанций стенда), `e2e/support/ours.ts` (наш интерфейс в закрытых shadow root:
  WebDriver достаёт его сам, клики настоящие), `e2e/support/chat.ts` (поле ввода,
  лента и журналы стенда), `e2e/support/second.ts` (второй настоящий Firefox). Сборка стенда — в `.cache/fixture-chatspace/`,
  галерей — в `.cache/kit-gallery/`, `.cache/dock-gallery/`, `.cache/boards-gallery/` и `.cache/pages-gallery/`; в git
  и в архив исходников для AMO они не попадают.

**Чем стенд не является.** Это не копия ChatSpace: нет виртуальных списков, медиа,
шаблонов (кроме простой панели), Side Panel, уведомлений, счётчиков `chatCounts`,
повторного чтения всех страниц истории при обновлении; перевод синтетический (`[EN] …`);
у очереди нет кнопок «вставить в поле» и «удалить»; формы данных — только поля, которые
читаем мы. Кто из фанов онлайн, стенд спрашивает, как ChatSpace: про строки списка на
экране, через 2 с после того, как они показались, и снова через 5 минут; ответ ложится
в стор `chats`, а не в кэш (`fixture-chatspace/src/ui/fans-online.ts`), кто онлайн —
задаёт тест (`standServer.presence`). Совпадение со стендом не доказывает совпадения с
настоящим ChatSpace: это проверят `tools/host-contract-check` (R02, следующая часть) по
копии бандлов и ручной smoke владельца.

### Поддельный хаб (R02)

`packages/testing/src/fake-hub` (`@cg/testing/fake-hub`) — хаб, на котором расширение
живёт, пока настоящие маршруты H-* не выкачены (architecture.md §8.6, §12 п. 2):

- **Все маршруты** таблицы контрактов (`HUB_ROUTES`) по путям вендоренного SDK: вход по
  паролю и отзыв, health, me, bootstrap, каталог персон, поток AI, рекапы, досье, Spenders
  v2 / карточка / пачка / корзины, статистика, «ждут ответа», лента, «Новые», бронь и
  опека, свои расходы AI, ingest. Запросы проверяются схемами контрактов, нарушение — 400
  `bad_request`, как у хаба. Тело запроса AI проверяется ещё и так, как его проверяет
  сам хаб: правилами его обработчика (Coach — вопрос или пресет, но не оба; черновик для
  Fix; поля Coach только у Coach) и, если схему передали (`streamBodySchema`: e2e и тесты
  проводки передают схему тела из вендоренного SDK), настоящей схемой тела хаба. Так же
  маршруты `client/*`: если передали `routeSchemas` вендоренного SDK (e2e и тесты
  проводки передают), запрос проверяется схемами хаба — параметры пути, query, тело, — а
  ответ модели — схемой ответа хаба.
- **Модель хаба**: bootstrap из настроек владельца (пресеты `pilot-pages` — по умолчанию:
  пилот включён строкой каждой страницы, строка `"*"` пустая, все верхнеуровневые флаги
  `false`, как у владельца на проде; `pilot-on` — то же через `"*"`; `all-off`,
  `master-off` — `configRevision` при смене только растёт, флаги по страницам,
  возможности — маршрут необъявленной возможности не выкачен, 404), выдача страниц по
  пользователю (`grantPages`; невыданная страница — 404, `me` и bootstrap — только
  выданные), токены (узкий `chat-extension` и его эхо, отзыв и истечение с причинами
  401, лимит попыток входа), бронь и опека H-7 только на страницах OnlyFans — с арендой,
  одноразовым билетом и `uncertain-held`, который сам не снимается; статус брони (GET)
  и сводка в «Новых», как у хаба, не называют установку: своя живая бронь читается
  `held` · `you-elsewhere`, `owned` и токен отвечает только POST с токеном брони),
  подписанные курсоры (лента привязана к
  пользователю, поколению архива и снимку: `archiveRebuild` делает старые курсоры
  `cursor_invalid`, новые сообщения проход не ломают), часы (ручные в юнит-тестах,
  системные в e2e).
- **Сценарии**: `useHttpScenario` / `useSseScenario` проигрывают сценарии
  `@cg/testing/hub`, `scriptHttp` / `scriptSse` — свои ответы; поток AI с задержками,
  «воротами», которые тест открывает, обрывом кадра, сбросом соединения, зависанием и
  503 до первого кадра.
- **Журнал** каждого вызова: маршрут, запрещённая операция (`/ofapi`, события, сырой шлюз,
  полные персоны…) или неизвестный путь, кто ответил, типы кадров потока. Запрос в нём
  скрыт по умолчанию: остаются только id, перечисления, даты и курсоры под известными
  ключами, любая другая строка — её длина (и в отклонённом запросе, и в открытом `payload`
  ingest). Текстов (черновики, вопросы, свежий текст, ответ модели, пароль) и токенов в
  нём нет. `violations()` / `assertClean()` — «клиент не сделал ничего запрещённого».
- **Хаб до выкладки H-2/H-3** (для режима совместимости): настройка `clientBootstrap: false`
  — `client/bootstrap` отвечает 404, `narrowTokens: false` — токен полный, без эха. Список
  страниц хаба `GET /pages` отдаётся только полному токену (в журнале — `legacy`), узкому
  — 403 и нарушение. Команда `pageAccount` привязывает страницу к аккаунту платформы
  (или отвязывает): так страница поддельного хаба совпадает с аккаунтом стенда.
- **Команды управления** проверяются: неизвестная команда, поле с опечаткой или не того
  вида — ошибка теста (в процессе — исключение, по адресу управления — 400), а не
  молчаливый `{ ok: true }`.
- **Два режима**: `createFakeHub().fetch` — реализация `fetch` для юнит-тестов (в том числе
  для вендоренного SDK), `startFakeHub()` — сервер на 127.0.0.1 для e2e. В e2e его
  поднимает `wdio.conf.ts`, адрес — в `CG_FAKE_HUB_ORIGIN`; `e2e/support/fake-hub.ts`
  даёт клиент управления, `useFakeHub()` (тест падает на запрещённом вызове) и
  `pointTestBuildAtFakeHub()` — адрес хаба тестовой сборки (настройки v1). Адрес по
  умолчанию — настоящий хаб, поэтому e2e сначала меняет адрес со страницы журналов
  (`debug-journal.html`: без отладки она спрашивает у фона только настройки и вход) и
  только потом открывает настройки. Без входа ни одна страница хабу ничего не шлёт;
  после входа настройки и popup читают его состояние при открытии.

### Живые проверки (X9)

Только Firefox, только dev-профиль из `pnpm dev`, только тестовый чат владельца
(какой — в решении X9, `docs/decisions.md`). Чужие чаты не открывать: открытие
помечает чат прочитанным в OnlyFans. Номера реальных чатов в код и в README не
пишем — `pnpm archive-check` их ловит.

**Как `pnpm dev` запускает Firefox.** На macOS агент не запускает из своей
оболочки Firefox с окном — ни бинарник напрямую, ни `web-ext run`. После двух
таких запусков на этой машине пропадало разрешение «Универсальный доступ» для
Orca Computer Use, сразу для всей системы. Позже оно пропало ещё раз без
всякого прямого запуска (похоже, после перезапуска Orca), так что причина не
доказана; запуск через систему оставлен как более аккуратный. Firefox без окна,
которым `pnpm e2e` управляет через geckodriver, под это правило не подпадает.
На macOS `pnpm dev`:

1. следит, чтобы в `user.js` профиля были нужные настройки (удалённая отладка
   включена и не спрашивает подтверждения, неподписанное дополнение ставится,
   всплывающий перевод страниц выключен) и метка профиля — его абсолютный путь;
   остальные строки файла не трогает;
2. смотрит, отвечает ли порт отладки этого профиля. Если отвечает — спрашивает
   у Firefox на этом порту, какой у него профиль, и идёт дальше, только если
   это профиль этого запуска;
3. собирает тестовую сборку;
4. если порт не отвечал — просит систему запустить Firefox: `open -n -a Firefox
   --args -profile <профиль> -no-remote -start-debugger-server <порт>` (процесс
   Firefox принадлежит системе, а не этой команде), ждёт порт и так же
   проверяет профиль;
5. ставит сборку временным дополнением через порт (тот же запрос, что шлёт
   `web-ext`) и перед этим, в том же соединении, ещё раз спрашивает профиль;
   после каждой пересборки ставит ещё раз — Firefox перезагружает дополнение.

**Один профиль — один порт отладки, и порту на слово не верим.** Раньше у всех
профилей был общий порт 6111, а «на порту кто-то отвечает» считалось «это наш
dev-Firefox»: обычный `pnpm dev` из любой рабочей копии поставил бы свою сборку
в тот Firefox, который занял порт, — например, в постоянный профиль владельца
со входом в ChatSpace. Теперь:

- порт по умолчанию считается из абсолютного пути профиля (число из диапазона
  49152–65535, одно и то же для одной папки), поэтому у двух профилей — двух
  рабочих копий, рабочей копии и постоянного профиля — порты разные. Какой порт
  выбран, `pnpm dev` печатает первой строкой;
- перед установкой Firefox на порту отвечает, какой у него профиль: метка из
  `user.js` (точный абсолютный путь), а у Firefox, запущенного до появления
  метки, — имя папки профиля. Профиль другой — команда останавливается, называет
  оба профиля и ничего не ставит; выход — другой порт (`--debugger-port`) или
  закрыть тот Firefox;
- на порту отвечает что-то, что не отладчик Firefox, — «порт N занят не нашим
  dev-Firefox: освободите порт или задайте другой». Слежение за кодом в таком
  случае не продолжается: бесконечных попыток установки нет;
- папка профиля не может быть домашней папкой (`CG_DEV_PROFILE=~`) и не может
  лежать внутри собственных профилей Firefox
  (`~/Library/Application Support/Firefox` и подобных): в повседневный профиль
  неподписанную сборку не ставим.

Ctrl+C останавливает только слежение за кодом: Firefox остаётся открытым, и
следующий `pnpm dev` того же профиля найдёт его по порту и не запустит второй.
Флаги: `--no-watch` — собрать и поставить один раз; `--debugger-port <n>` (или
`CG_DEV_DEBUGGER_PORT`; по умолчанию — порт профиля); `--firefox-app <имя или
путь к .app>`; `--url <адрес>` — открыть страницу при запуске. Без `--url`
ничего не открывается: сам `pnpm dev` на настоящий сайт не ходит. На других
системах всё по-прежнему делает `web-ext run` (`--firefox <бинарник>` или
`FIREFOX_BIN`). Код — `tools/dev/`, тесты там же (кадры протокола отладки и
поддельный сервер отладки, настройки и метка профиля, запуск — на подделках, без
Firefox).

**Чего не нажимать на живой вкладке ChatSpace во время проверок.** ⌘1–9, J, K и
⌘U — наша навигация по чатам: она открывает чаты других фанов, а открытый чат
OnlyFans помечает прочитанным. Флаг `navigation` на живых страницах на время
проверок остаётся выключенным; клавиши проверяются на стенде.

Флаг `navigation` — это только наши переходы между чатами: J/K, ⌘U, ⌘1–9, быстрый
переход и чаты в палитре. Клик человека по конкретному фану на доске под него не
попадает: «Открыть чат» в строке Spenders, «Открыть» и «Открыть и вставить» в превью
и карточка «Новых» проверяют флаг самой доски на этой странице (`spenders`,
`preview`, `newcomers`), а вставка — ещё `insertion` этой же страницы. Поэтому с
выключенным `navigation` «Открыть и вставить» на проверяемой странице работает —
в тестовом чате его и проверяют.

**Где лежит dev-профиль.** По умолчанию — `.dev-profile/` в корне репозитория
(в git не попадает). Он пропадает вместе с рабочей копией, а вход в ChatSpace
живёт именно в профиле. Поэтому постоянный профиль владельца лежит вне
репозитория — `~/Documents/ChatGoose/firefox-dev-profile` — и задаётся
переменной `CG_DEV_PROFILE`:

```sh
CG_DEV_PROFILE=~/Documents/ChatGoose/firefox-dev-profile pnpm dev --debugger-port 6111
```

У постоянного профиля порт закреплён — 6111, и он всегда называется явно
(`--debugger-port 6111` или `CG_DEV_DEBUGGER_PORT=6111`): Firefox этого профиля
слушает именно его. Без флага команда взяла бы порт, посчитанный из пути, не
нашла бы там Firefox и попробовала бы запустить второй на занятом профиле.
Ветки старше этого исправления по умолчанию ставят сборку в Firefox на порту
6111, не спрашивая профиль; пока такие рабочие копии есть, `pnpm dev` в них не
запускать при открытом постоянном профиле — либо один раз перезапустить его
Firefox на собственном порту (без флага) и дальше флаг не указывать.

Путь может быть абсолютным, начинаться с `~/` или считаться от корня
репозитория. Папка создаётся сама, изменения профиля сохраняются. Один профиль —
один запущенный Firefox: второй `pnpm dev` с тем же профилем и тем же портом
находит уже запущенный и ставит сборку в него. Если Firefox с этим профилем
открыт без порта отладки или на другом порту, его нужно закрыть и запустить
`pnpm dev` снова — или назвать его порт.

**Вход в хаб из dev-сборки.** Страница настроек расширения (значок расширения →
«Настройки», или about:addons → ChatGoose → «Настройки») — экран входа: логин и
пароль хаба; адрес хаба — там же, в «Дополнительно». Прод-хаб с 2026-10-04 выдаёт
узкий токен и отвечает на `client/bootstrap`: первая живая проверка вошла обычным
путём, привязка нашлась по id аккаунта платформы у страницы. Всё, что ниже в этом
разделе, нужно только для хаба без H-2 и H-3 (старый или локальный): с ним
расширение работает в режиме совместимости
([docs/hub-layer.md](docs/hub-layer.md)) — он есть только в тестовой сборке и
только при включённой отладке, нужно и то и другое, статус — «degraded».
Выключатель отладки — в настройках, а они открываются после входа, поэтому перед
первым входом отладку включают в консоли страницы настроек расширения (открыть
настройки — там экран входа — и нажать F12; запрос принимается только от этой
страницы):

```js
await browser.runtime.sendMessage({ v: 1, kind: 'req', id: 1, type: 'settings.patchRestricted', payload: { patch: { debug: { enabled: true } }, baseRevision: null } });
```

Без этого вход на такой хаб кончится отказом «Расширение устарело» (`CG-HUB-OUTDATED`) —
как в выпускной сборке, где режима совместимости нет при любых настройках. У страниц
такого хаба нет id аккаунта платформы, и по имени мы ничего не подбираем, поэтому
привязку для проверки задаёт карта разработчика в хранилище расширения —
`метка страницы → id креатора`. Задать её можно в консоли любой страницы
расширения (в той же консоли):

```js
await browser.storage.local.set({ 'dev.compatPageAccounts': { '<метка страницы хаба>': '<id креатора в OnlyFans>' } });
```

Карта читается при следующем получении bootstrap (выйти и войти). В выпускной
сборке её нет.

Правило выпуска: в выпуск SDK берётся только из коммита хаба, который стоит в проде
(гейт выпуска сверяет хеш со списком `compatibleClientSdks` прод-хаба). Нынешний
вендоринг ему отвечает: `bd3eec06` стоит в проде с 2026-10-14 00:55 UTC, прод отдаёт
контракт `9137410d…` и держит его в `compatibleClientSdks`. Если хаб выложат снова с другим
контрактом — перевендорить из выложенного коммита (так было перед выпуском 0.2.0: хаб
переехал и встал с новым контрактом, прежний хеш из списка выпал; и перед 0.2.2: хаб
выложили с новым маршрутом через час после слияния выпуска). SDK расширения в реестре
замороженных SDK хаба (`client-sdk-registry.ts`) нет: совместим только хеш, совпадающий с
контрактом выложенного хаба (прежний `03012453…` хаб держит лишь потому, что из того же
коммита вендорен SDK Fansly-расширения 2.8.1 и 2.9.0). Записать туда SDK расширения можно
только вместе с полосой расширения в проверке совместимости хаба
(`tests/helpers/client-sdk-compat.ts`: узкий токен, тела запросов расширения) — её пока нет.
Хаб клиента по версии SDK не отвергает (хеш
контракта по сети не ходит), а слой хаба вызывает маршрут только тогда, когда bootstrap
объявил его возможность, поэтому на хабе старше SDK всё прежнее работает, а новое читается
как «хаб пока не умеет эту функцию»
([docs/pilot-readiness.md](docs/pilot-readiness.md), раздел 3).

Как перевендорить: отдельный рабочий каталог хаба на нужном коммите (`git worktree add
--detach`), `pnpm install --frozen-lockfile` там, `node scripts/vendor-sdk.mjs
<этот репозиторий>/vendor/kernel-sdk`; затем обновить `tests/vendor-pins.json` тем же
коммитом. Маршрут контракта, которого нет в SDK, не отправляется вовсе; когда он
приходит в SDK, у него в `packages/contracts/src/hub/routes.ts` ставят `since: 'sdk'` —
тест `sdk-alignment` скажет, каким.

`pnpm archive-check` смотрит и на вендоренный код в архиве исходников для AMO: настоящий
id или имя файла сборки ChatSpace в комментарии хаба роняет проверку. Такое правится в
хабе (пример в комментарии заменить на выдуманный), потом перевендоринг. Так было один
раз, исправлено PR хаба #482: [docs/pilot-readiness.md](docs/pilot-readiness.md),
раздел 5, п. 19.
